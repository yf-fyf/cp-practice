# 教材品質管理ガイド

各回の教材と参考資料を作成・公開・改善するときの、最小限の品質管理手順を定める。
メンテナと AI が共同で利用し、日常的に継続できることを優先する。

このガイドの目的は、教材を細かく採点することではない。
学習者の進行を妨げる重大な問題を公開前に見つけ、利用後の改善材料を残すことである。

記録には非公開リポジトリ `../cp-practice-design/teacher/quality/template.md` を使う。

---

## 1. 運用原則

1. 記録は**回**の単位で作る。複数回で1つの題材になる束には、束としても1本作る。
2. 公開前に、学習者経路と技術・実行の2回だけ AI レビューを行う。
3. AI の指摘はメンテナが確認し、公開判断はメンテナが行う。
4. 公開を妨げる問題と、将来の改善候補を分ける。
5. 実際の利用で得た観察を、次の改善に利用する。
6. 運用上の効果が確認できない項目は増やさない。

完成解答や自動テストは必須ではない。
ただし、学習者とメンテナが到達を判断できる完了条件は必須とする。

---

## 2. 記録単位

記録は `../cp-practice-design/teacher/quality/template.md` から作成し、
`../cp-practice-design/teacher/quality/records/<record-id>.md` に保存する。

記録名の例: `session-03` / `session-08-10-roster` / `references-setup`

回の単位にするのは、この科目では回ごとに題材が変わる回が多いためである。
第08〜10回（勤務表）のように3回で1つの成果物になる束は、
各回の記録に加えて束の記録も1本持ち、束の記録で「3回を通した一貫性」を見る。

### 記録の状態

| 状態 | 意味 |
|---|---|
| `Draft` | 制作または修正中 |
| `Ready` | 必須確認を終え、メンテナが公開可能と判断した |
| `Validated` | 実際の利用後に改善要否を確認した |
| `Needs revision` | 公開または継続利用を止める問題がある |

束を `Ready` にできるのは、今回の公開対象に含まれる回がすべて
`Ready` または `Validated` である場合とする。
公開対象の回が一つでも `Needs revision` になった場合は、
修正または公開対象からの除外まで束も `Needs revision` にする。

## 3. 必須品質基準

公開対象について、次の8点を必須確認とする。
前半5点はどの教材にも共通、後半3点はこの科目に固有である。

| 観点 | 確認すること |
|---|---|
| 目標と完了条件 | 学習目標・前提・完了条件が明確である |
| 学習者経路 | 学習者向け資料だけで開始し、次の作業を判断できる |
| 技術的正確性 | 中心的な説明・コード・期待結果が正しい |
| 実行可能性 | 記載された実行・確認手順が動く |
| 公開範囲 | 完成解答の意図しない混入や不要な内部情報がない |
| **モデルが実際に解ける** | 必須・標準演習の解答モデルを実行し、期待する解が得られること、UNSAT にすべき例が UNSAT になることを確かめた記録がある |
| **実行時間が授業時間内に収まる** | 実測した。特に第01〜02回の Tau Prolog と、第10回の規模拡大 |
| **架空データであることが明示されている** | 勤務表・テーマ割当が実在の機関・個人に由来しないこと（`curriculum-2026.md` §4.4・§4.5） |

難しいこと、長いこと、他教材に依存すること、自動テストがないことは、
それだけでは品質上の問題ではない。

指摘は次の2種類に分ける。

| 種別 | 扱い |
|---|---|
| `Blocker` | 解消または公開対象から除外するまで `Ready` にしない |
| `Improvement` | 公開を妨げない。必要性と優先度をメンテナが判断する |

## 4. 標準ワークフロー

### Step 1: 基本情報を記述する

対象学習者・学習目標・前提・完了条件・構成物・今回の公開対象を記録する。
学習目標は「理解する」だけで終わらせず、
モデル化・説明・比較・実験・デモなど観察可能な形にする。

制作中に実行した確認は「制作時確認」として区別して書く。
制作時確認は AI レビューの代替にならない。

**この科目では、ここで実行結果を必ず添える。**
必須演習と標準演習の解答モデルを実際に走らせ、
「どのソルバーで」「何秒で」「どんな解が」出たかを書く。

### Step 2: 学習者経路を AI レビューする

学習者向け配布物（`workbook/` 内）と、公開される教材ページだけを AI に見せる。
レビューは、教材を制作した会話とは別の、制作文脈を持たないセッションで行う。

確認する内容:

- どこから開始するか分かる
- 次に読む・編集する・実行する場所が分かる
- 未記載の前提がない（実行環境の用意を含む）
- 失敗時に最初の調査を始められる
- 完了条件が学習者から見える
- 必須演習のヒントが段階的で、最終段にだけ解答がある

### Step 3: 技術・実行を AI レビューする

教材原稿（`materials/`）・配布物（`workbook/`）・`design/curriculum-2026.md` を照合する。
このレビューも、制作文脈を持たないセッションで行う。

確認する内容:

- 中心的な技術説明と期待結果
- 原稿と配布物の対応（`% TODO` の数と位置、ファイル名）
- 記載された実行手順が動く
- 未完了を成功扱いする経路がないか
- 完成解答や不要な非公開情報が公開側へ混入していないか

**AI が実行していないコマンドを、成功したものとして扱わない。**
特に、ソルバーを走らせていない状態で「解ける」と書かせない。

### Step 4: Blocker を処理する

AI の指摘をメンテナが確認する。
誤った指摘は採用せず、採用した `Blocker` だけを修正または公開対象から除外する。

`Improvement` は、効果が見込める場合だけ対応する。
網羅性のために説明・テスト・記録を増やさない。

修正後は、変更した範囲について学習者経路または技術・実行を再確認する。

### Step 5: メンテナが Ready を判断する

リビジョン・公開対象・実行したコマンドと結果・`Blocker` 修正後の確認結果・
未解決 `Blocker` がないこと・判定者と日付を記録する。
公開対象に未解決 `Blocker` がある場合、`Ready` にしない。

### Step 6: 利用後に短く記録する

実際に観察できたものだけを記録する。

- 学習者が止まった場所
- 追加説明が必要だった場所
- 完了条件を適用できたか
- 実行時間が想定内だったか
- 次回直すこと

改善要否を確認できたら `Validated` にする。
継続利用を止める問題が見つかったら `Needs revision` にする。
**個人を特定できる情報は記録しない。**

## 5. 簡易レビュー

既に `Ready` または `Validated` の教材に対する、意味と動作を変えない変更だけに使う。

対象例: 誤字脱字、体裁、意味を変えない言い換え、
原稿が変わっていない状態での図の再生成。

次は標準ワークフローを使う。

- 学習目標・前提・完了条件の変更
- 演習手順や `% TODO` の変更
- モデル・データ・期待結果の変更
- 前提となる概念（`requires:`）の変更
- 学習者の解法や判断に影響する説明・ヒント・例の追加

簡易レビューでは次だけを行う。

1. 意味と動作が変わらないことを差分で確認する。
2. `make check`（サイト生成・リンク・文書検査）を通す。
3. 実施した確認と状態維持の判断を、記録の変更履歴へ1行書く。

### 共有ファイルの変更

`site/boxes.lua`・`site/style.css`・`materials/references/`・`workbook/README.md` など
複数の回が依存するものを変更した場合は、
依存する各回について再確認の要否を判断する。

---

## 6. 参考資料の補足

`materials/references/` の各ページでは、5つの共通基準に加えて次を確認する。

- 「最初に読むもの」（環境構築）と「必要なときに引くもの」（早見表・概説）の
  どちらであるかが冒頭で分かる
- 環境構築のページは、**実際に1つの OS で手順どおりに実行し、
  最小動作確認まで到達した**記録がある
- 早見表は、各回の原稿から参照される項目をすべて持っている
- 用語集の項目は、初出回へのリンクを持っている

## 7. このリポジトリでの前提

| パス | 役割 |
|---|---|
| `materials/sessions/` | 各回の資料の Markdown 原稿 |
| `materials/references/` | 参考資料の原稿 |
| `materials/figures/` | 図の TikZ ソースと生成 SVG |
| `materials/guides/style-sample.md` | 表示部品の見本（原稿を書く人向け） |
| `workbook/` | 学習者向け配布物。この範囲だけで演習を実施する |
| `workbook/sessions/NN-xxx/` | 各回の穴埋め前のモデル・入力データ・動作確認 |
| `design/curriculum-2026.md` | 回割り・目標・演習3段階・完了条件の**正本** |
| `design/site-design.md` | 教材サイトの方針 |
| `design/maintaining.md` | 保守手順・表記規約・検査の種別 |
| `../cp-practice-design/teacher/answers/` | 非公開の完成解答。存在しない回もある |
| `../cp-practice-design/teacher/tests/` | 非公開の隠しテスト・反例データ |
| `../cp-practice-design/teacher/rubric/` | 非公開の評価ルーブリック |
| `../cp-practice-design/teacher/quality/` | 非公開の品質記録（`template.md` と `records/`） |

完成解答・隠しテスト・ルーブリック・品質記録はこの公開リポジトリに置かず、
非公開リポジトリ `../cp-practice-design/` だけで管理する。

監査では、対象外の既存変更を修正・削除・巻き戻ししない。
メンテナの許可なく commit しない。

### 主なコマンド

リポジトリルートから実行する。

```bash
make site          # 資料サイトを .site/ に生成
make serve         # 生成して http://127.0.0.1:8000/ で配信
make check-links   # 内部リンク切れを検査
make check-docs    # 原稿・配布物の整合を検査
make check         # 上の3つをまとめて
make check-publish # 公開範囲と個人情報だけを検査
```

演習モデルの実行はソルバー側で行う。

| 実行環境 | 確認のしかた |
|---|---|
| MiniZinc | [MiniZinc Playground](https://play.minizinc.dev/) にモデルを貼って実行する |
| Prolog | 教材サイトの Prolog 実行ページ（`web/prolog/`。同梱の Tau Prolog で動く） |
| Z3 | `python3 <ファイル>`（`z3-solver` を固定版で入れる） |

**CI ではモデルもコードも走らせない。**動作確認はローカルで行い、
結果を品質記録に残す。これがモデルの正しさを担保する唯一の経路である。

## 8. AI レビューの出力形式

2回の AI レビューでは、次の短い形式を使う。

```text
Blockers:
- 最大5件。ファイルと行番号、学習者への影響、最小修正を記載する。

Improvements:
- 最大3件。公開を妨げない改善だけを記載する。

Commands:
- 実行したコマンドと結果を記載する。

Not verified:
- 確認できなかったことを記載する。

Recommendation:
- Ready または Needs revision
```

問題がない場合も、確認範囲と未確認事項を記載する。

`Recommendation` は AI による推奨であり、メンテナの `Ready` 判定そのものではない。
最終判断は Step 5 でメンテナが行い、記録には推奨と判定を区別して書く。

## 9. リポジトリ専用 AI プロンプト

### 9.1 学習者経路レビュー

```text
この教材リポジトリの教材を、学習者経路という観点でレビューしてください。読み取り専用で調査し、ファイルを変更しないでください。

対象: 第NN回 <題材>
今回の公開対象: <workbook/ 配下の学習者向けパスと materials/sessions/NN-xxx.md>
対象学習者の前提: 論理回路（AND/OR/NOT）程度の知識と Python の経験。命題論理の記法・Prolog・MiniZinc の経験は仮定しない
完了条件: <curriculum-2026.md の該当回の完了条件>

参照してよいのは、workbook/ 内の学習者向け配布物と、公開される教材ページ（materials/sessions/NN-xxx.md、materials/references/）だけです。非公開リポジトリ ../cp-practice-design/、完成解答、品質記録は参照しないでください。

次を確認してください。
- 開始地点が分かるか（実行環境の用意を含む）
- 次に読む、編集する、実行する場所が分かるか
- 未記載の前提がないか
- 失敗時に最初の調査を始められるか
- 完了条件が学習者から見えるか
- 必須演習のヒントが段階的で、最終段にだけ解答があるか

難しいことや他の回への依存自体を問題にしないでください。意図した難しさと、記述不足による偶発的な難しさを区別してください。

出力は Blockers（最大5件）、Improvements（最大3件）、Commands、Not verified、Recommendation（Ready または Needs revision）だけにしてください。各指摘にはファイルと行番号、学習者への影響、最小修正を含めてください。
```

### 9.2 技術・実行レビュー

```text
この教材リポジトリの教材を、技術的正確性と実行可能性という観点でレビューしてください。監査対象以外の既存変更を修正、削除、巻き戻ししないでください。ファイルは原則として変更せず、commit は行わないでください。

対象: 第NN回 <題材>
今回の公開対象: <workbook/ 配下の学習者向けパス>
原稿: materials/sessions/NN-xxx.md
関連仕様: design/curriculum-2026.md の該当回
メンテナ用資料: ../cp-practice-design/teacher/answers/NN-xxx/（あれば）
完了条件: <curriculum-2026.md の該当回の完了条件>

materials/ の原稿、workbook/ の配布物、curriculum-2026.md を照合してください。次を確認してください。
- 中心的な技術説明、モデル、期待する解が正しいか
- 原稿と配布物が矛盾していないか（% TODO の数と位置、ファイル名、初期値データ）
- 記載された実行手順が動くか
- 未完了を成功扱いする経路がないか
- 完成解答や不要な非公開情報が公開側へ混入していないか
- 使用しているデータが架空であると明示されているか

実行していないコマンドを成功したと表現しないでください。特に、ソルバーを走らせていない状態で「このモデルは解ける」と書かないでください。仕様外の内容は、MiniZinc / Z3 / Prolog の一次資料と照合してください。

出力は Blockers（最大5件）、Improvements（最大3件）、Commands、Not verified、Recommendation（Ready または Needs revision）だけにしてください。各指摘にはファイルと行番号、学習者への影響、最小修正を含めてください。
```

### 9.3 簡易変更レビュー

```text
この教材リポジトリの教材変更が簡易レビューの対象か確認してください。ファイルは変更しないでください。

対象差分: <diff or revisions>

簡易レビューを使えるのは、意味と動作を変えない変更だけです。学習目標、前提、完了条件、演習手順、% TODO、モデル、データ、期待結果、requires: の概念、学習者の解法に影響する説明が変わる場合は標準ワークフローを推奨してください。

次だけを返してください。
- Decision: Quick review または Standard review
- Reason: 判断理由
- Minimum checks: 必要な差分確認、make check の実行など
- Not verified: 確認できなかったこと
```

## 10. このガイドの改善

このガイド自体も、運用しながら改善する。

- 記入されない項目は削除を検討する
- 判断に使われない記録は必須にしない
- 繰り返し発生する重大問題だけを新しい確認項目にする

網羅性より、継続して利用できることを優先する。
