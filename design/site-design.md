# 「実践・制約プログラミング」教材サイト設計

> **状態: 実装済み（2026-08-22）。** この文書は当初「これから作るサイトの方針」として
> 書かれたが、全15回の原稿・参考資料・自由課題の支援物・ビルド系・Prolog 実行ページが
> 揃った時点で、**実装した事実に合わせて全面的に書き換えた**。
> 「どう作るか」の手順は [`maintaining.md`](./maintaining.md)、回割り・各回の目標・
> 演習3段階・完了条件の正本は [`curriculum-2026.md`](./curriculum-2026.md) である。
> この文書は「サイトが何を満たすか」と「なぜそうしたか」を書く。

## 1. この文書について

この文書は、2026年度「実践・制約プログラミング」のウェブ教材の設計方針をまとめたものである。

サイト全体の骨格、教材の標準形式、表示部品、公開範囲の考え方を定める。
個々の講義内容は `curriculum-2026.md`、実装の手順とコマンドは `maintaining.md`、
Prolog 実行環境を選んだ根拠は `prolog-environment.md` にある。同じ事実を二重に書かない。

## 2. 目的

教材サイトには、次の役割を持たせる。

- 学習者が授業中の説明と演習手順を一つの場所で確認できる
- 欠席時や復習時にも、学習者が自力で演習を再現できる
- Prolog、MiniZinc、SAT、SMT、Z3の関係を科目全体の流れとして理解できる
- 教材本文、演習用ファイル、参考資料を継続的に更新できる
- 年度終了後も公開教材として閲覧できる
- 教員用資料や模範解答を誤って公開しない

授業中の対話や個別対応は引き続き重視する。ただし、授業中に口頭で補っていた前提、操作手順、課題の完了条件は、可能な限りウェブ教材にも記載する。

## 3. 基本方針

### 3.1 静的なウェブサイトを基本とする

教材本文は静的HTMLとして生成する。JavaScriptが利用できない環境でも、説明、コード、図、課題を閲覧できるようにする。

段階的ヒントは `<details>` 要素、完了チェックは無効化したチェックボックスで出す。
どちらもJavaScriptを要さない。JavaScriptを使うのは図の拡大表示（`site/lightbox.js`）だけで、
これが動かなくても図はそのまま表示される。

ブラウザ上でのモデル実行は、教材本文とは分離した補助ツールとして追加した。
Prolog 実行ページ（`web/prolog/`）がこれにあたり、教材サイト本体はビルド工程も配信も
このページから独立している。教材サイト全体を複雑なウェブアプリにはしない。

### 3.2 1回の授業を1ページにする

各回の授業に対応するページを一つ用意する。授業中は、そのページを上から順に読みながら演習を進められる構成にする。

長くなりすぎる理論説明、環境構築、言語仕様、API一覧などは独立した参考資料へ分離し、講義ページから必要な箇所へリンクする。

### 3.3 教材本文と演習ファイルを分離する

説明はMarkdown原稿（`materials/`）、学習者が編集・実行するファイルは演習用ディレクトリ
（`workbook/`）で管理する。

演習用ファイルには、例えば次のものを含める。

- 穴埋め前のプログラム
- 入力データ
- 実行例
- 簡単な動作確認
- 演習固有のREADME

詳細な作業手順はウェブ教材を正本とし、演習用READMEには起動方法と教材ページへの導線だけを記載する。説明を二重管理しない。

### 3.4 学習目標と完了条件を明示する

各回の冒頭には「この回の目標」、末尾には「完了チェック」を置く。

目標は「理解する」だけでなく、次のように観察可能な行動として記述する。

- 問題から変数、定義域、制約を取り出せる
- MiniZincモデルを実行し、得られた解を説明できる
- SAT符号化に必要な「少なくとも一つ」と「高々一つ」の制約を書ける
- Z3のモデルから変数の値を取得できる

### 3.5 読む・予想する・試す・振り返るを区別する

制約プログラミングでは、完成コードを読むだけでなく、制約を追加したときの変化を予想し、実行結果と比較することが重要である。教材上でも、説明、予想、作業、結果確認を視覚的に区別する。

### 3.6 学ぶ人の呼称は「学習者」に統一する

公開・非公開を問わず、学ぶ人は「学習者」と呼ぶ。`受講者`・`学生` は使わない。
`学生` が第07回の題材名（架空データの登場人物の区分）として正当に現れる箇所だけを、
`tools/doc_check_allowlist.yaml` に理由つきで除外する。

## 4. サイト構成

サイトは4つのセクションと1つの補助ツールで構成する。並びと群分けは
`site/nav.yaml` が単一の出典であり、上部メニューは「教材｜引くもの｜道具」の3群に見える。

### ホーム

`nav.yaml` から自動生成する。手で書く原稿を持たない。次を載せる。

- 科目の概要（`nav.yaml` の `description`）
- 各セクションの要約とページ一覧
- 演習ファイルのダウンロード
- 実行環境への入口

開講日程は載せない。年度の日程は授業運用側で管理し、公開教材には持ち込まない。

### 講義（`sessions`、全15回）

回ごとに1ページ、計15ページ。第01〜02回が Prolog、第03〜04回が MiniZinc、
第05〜06回が SAT・SMT と Z3、第07回が最適化、第08〜10回が勤務表の総合演習、
第11〜14回が自由課題、第15回が成果発表会である。
テーマ名と回番号の対応は `curriculum-2026.md` §7 が正本で、ナビゲーションは
原稿のファイル名（`NN-slug.md`）からそのまま導かれる。

独立した「導入」回は置かない。第01回が導入を兼ねる。

### 自由課題（`projects`）

第11〜14回で使う支援物。案内・企画書テンプレート・README テンプレート・
検証チェックリスト・提出物チェックリスト・発表の手引きの6ページ。
**説明は公開側（`materials/projects/`）、記入用の実体は配布物（`workbook/projects/`）**
に置く。評価ルーブリックの詳細（段階と配点）は非公開側に置き、公開側には観点名だけを出す。

### 参考資料（`references`）

「最初に読むもの（環境構築）」と「必要なときに引くもの（早見表・概説・用語集）」を
区別して案内する。索引ページを入口に置き、次の12ページを持つ。

| 区分 | ページ |
|---|---|
| 索引 | 参考資料の入口（知りたいこと → 該当ページ） |
| 環境構築 | Prolog 実行ページの使い方 ／ MiniZinc Playground ／ Python + Z3 |
| 早見表 | Prolog ／ MiniZinc ／ Z3Py |
| 概説・比較・手順 | 命題論理・SAT・SMT概説 ／ グラフ彩色の3表現比較 ／ 定式化の手順 |
| 引くもの | エラーへの対処 ／ 用語集 |

用語集の項目は `design/glossary-ledger.md`（用語初出台帳）からの導出値であり、
台帳と用語集の対応は機械検査する（§15）。

### 進め方・演習ファイル（`guides`）

科目の進め方（演習3段階・完了条件・合否要件）、演習ファイルの入手と実行、
教材を書く人向けの表示見本の3ページ。演習ファイルの案内は `workbook/README.md` を
そのままサイトへ載せているので、配布物とサイトで説明が食い違わない。

### 補助ツール

Prolog 実行ページを `/tools/prolog/` に置く。上部メニューの「道具」群から入れる。
MiniZinc と Z3 は科目専用ツールを持たず、参考資料から外部の公式環境へ案内する。

出力先は `<セクションの slug>/<原稿のファイル名>/index.html` で、原稿のファイル名が
そのままURLになる。回番号は2桁ゼロ埋め、区切りはハイフンである。

```text
/sessions/08-roster-hard/             第08回 勤務表: ハード制約
```

`archive/2026/` 方式を後付けする。教材本文からは相対URLを使う。

## 6. ディレクトリ構成

```text
cp-practice/
├── design/             設計・運用文書（curriculum / site-design / prolog-environment /
│                       maintaining / quality_guide / glossary-ledger）
├── materials/          教材本文のMarkdown原稿
│   ├── sessions/       各授業回
│   ├── references/     参考資料
│   ├── projects/       自由課題の支援物
│   ├── guides/         進め方・表示見本
│   └── figures/        図の TikZ ソースと生成SVG（両方コミット）
├── latex/              図の共通プリアンブル
├── workbook/           学習者向け演習ファイル
│   ├── sessions/
│   └── projects/
├── site/               ナビゲーション、HTMLテンプレート、Luaフィルタ、CSS
├── tools/              サイト生成、図の生成、検査、公開物作成
├── web/prolog/         Prolog 実行ページ（ビルド工程を持たない静的ファイル）
└── .github/workflows/  CIと公開処理
```

生成物はソースと混在させず、`.site/`（ローカル確認用）と `.pages/`（公開物）へ出す。
どちらもGitでは管理しない。**図のSVGだけは生成物だがコミットする**。
サイト生成にLuaLaTeXを要求しないためである。

## 7. 教材原稿の形式

原稿はMarkdownを基本とする。各回のページの先頭にはYAML frontmatterを置く。
frontmatterはpandocがメタデータとして消費するので、生成ページには出ない。

```yaml
---
session: 3
track: minizinc            # prolog | minizinc | z3 | project | presentation
tools:
  - MiniZinc
description: 数独を題材に、変数・定義域・制約・解の語彙をMiniZinc構文と対応付ける
introduces:                # この回が初出で導入する概念（用語初出台帳が出典）
  - csp_vocabulary
  - parameter_vs_decision_var
requires:                  # 前提となる概念（台帳からの導出値。手で足し引きしない）
  - declarative_description
---

# 第03回 数独: MiniZincで盤面を解く
```

`description:` は `<meta name="description">` とホームのカード説明に使う。
`introduces:` / `requires:` は `design/glossary-ledger.md` と突き合わせ、
概念の依存順（未導入の概念を先取りしていないか）を機械検査する。

次の項目は **frontmatterに置かない**。二重管理になり、必ずずれるためである。

| 置かない項目 | 正本 |
|---|---|
| `title:` | 原稿の先頭 H1（`build_site.py` が読む） |
| `duration:` | 全15回が100分で同一（`curriculum-2026.md` §2） |
| `objectives:` | 本文の「## この回の目標」 |
| `prerequisites:`（ページ単位） | `requires:`（**概念単位**）に置き換えた |
| `updated:` | 手書きの更新日は腐る。必要ならgitの最終更新から生成する |

自由課題の支援物・参考資料・進め方は各回の原稿ではないので、frontmatterは
`description:` だけでよい。

## 8. 講義ページの標準構成

基礎回（第01〜10回）は次のH2の並びを原則とする。`--toc-depth=2` なので、
この並びがそのままページ内目次になる。

```markdown
# 第NN回 タイトル

## この回の目標          ← 観察可能な行動で3〜4項目。枠で囲んで表示する
## 前提と準備
## 今回解く問題
## 変数・定義域・制約・目的へ分解
## 概念と構文
## 小さな実行例
## 予想してから試す
## 必須演習
## 標準演習
## 発展演習
## よくある誤り
## 完了チェック
## 扱わないこと          ← 先送り先を必ずリンクにする
## 次回への接続
```

第05・06回は `## 概念と構文` の前に `## 理論概説` を、冒頭に `## この回の進み方`
（時間配分の表）を置く。時間配分を明示するのはこの2回だけである。

第11〜14回（自由課題）と第15回（発表会）は演習3段階を持たないので簡略形とし、
`## この回の目標` / `## 今回やること` / `## 支援物` / `## チェックポイント` /
`## 扱わないこと` / `## 次回への接続` に絞る。第15回だけは送り先が次の回ではないので、
末尾を `## この科目のあと` にする。

間に別のH2を挟むことは許すが、この並び順は機械検査する（§15）。

## 9. 教材用の表示部品

書き方と見え方は表示見本ページ（`/guides/style-sample/`）に1ページで並べてある。

### 9.1 注釈

- 補足: 本筋ではないが理解を助ける情報
- 重要: 後の演習で必要になる要点
- 注意: 誤操作や誤解が起きやすい箇所
- 用語: 初出の専門用語

### 9.2 学習活動

- 予想: 実行前に結果を考える問い
- 演習: 実際にコードやモデルを変更する指示。**必須・標準・発展の3段階**を属性で持たせ、
  見出し語（「必須演習」「標準演習」「発展演習」）と左罫の色の両方で区別する
- チェックポイント: 途中段階の完了条件
- 考察: 結果の理由を説明する問い
- 完了チェック: 回末のチェックリスト

「発展」は独立した部品にせず、演習の段階として扱う。演習の本体（本文・完了条件・
ヒント）は段階によらず同じ形をしているためである。

### 9.3 ヒント

ヒントは段階的に開示できる `<details>` として出す。最初から答えを表示せず、
学習者が自分で考える時間を確保できるようにする。

解答の置き場は次のとおりとする。公開範囲を文書の運用ではなく**置き場で守る**。

| 資産 | 置き場 |
|---|---|
| 基礎的な実行例のコード | ページ本文 |
| 必須演習の解答 | ページ本文のヒント最終段 |
| 標準演習の中心部分の完成コード | 非公開リポジトリのみ（恒久非公開） |
| 発展演習の完成コード | 非公開リポジトリのみ（恒久非公開） |

### 9.4 コードと実行結果

次の情報を見分けられる表示にする。コードブロックには言語名を必ず付け、
入力と期待出力を同じブロックに混在させない。ファイル名は
`filename=` 属性でキャプションとして表示する。

| 区分 | フェンスの綴り | 表示 |
|---|---|---|
| MiniZincモデル | `minizinc` / `mzn` | 着色なし・ラベル「minizinc」 |
| MiniZincデータ | `dzn` | 着色なし・ラベル「minizinc data」 |
| Prolog | `prolog` / `pl` | 構文着色あり |
| Z3Py | `z3py` | Pythonとして着色 |
| 実行コマンド | `console` | プロンプト付き |
| ソルバーの解・統計 | `solver` | 着色なし・ラベル「ソルバー出力」 |
| エラー出力 | `{.text .error}` | 着色なし・警告色の左罫 |

MiniZincはpandocの構文定義に無いので着色されない。着色が要るようになったら
skylighting用の構文定義XMLを自作して渡す（`maintaining.md`）。

### 9.5 数式

命題論理、量化子、集合、制約式、目的関数をMarkdown原稿から記述する。
出力にはMathMLを用いる（`--mathml`）。次を確認した。

- インライン数式と独立した数式
- 長い制約式のモバイル表示
- 数式内の日本語
- 数式への参照

スクリーンリーダーでの読み上げは未確認である（§12）。

### 9.6 図と表

図はSVGとし、代替テキストを必須とする。図は `materials/figures/*.tex`（TikZ）を
正本とし、生成したSVGをコミットする。配色は本文のCSSと揃え、**色そのものが意味を
持つ図では色だけに頼らず記号も併記する**。

幅の広い表やスケジュールは、表単位で横スクロールできるようにする。

## 10. ナビゲーション

サイト構成とページ順は `site/nav.yaml` 一つで管理し、次を自動生成する。

- ホームの教材一覧
- 上部メニュー（`group` による3群の区切り）
- パンくず
- ページ内目次（H2まで）
- 同じセクション内の前後ページ
- セクション入口ページ

前後リンクは同じセクションの中だけで接続する。別系列へ移る場合は、本文中に
「次に進む候補」として明示的なリンクを置く。

**常設サイドバーは置かない。**全15回＋参考資料12本の規模では、上部メニューと
ページ内目次で足りる。

**サイト内全文検索は初年度は入れない。**ページ数が増え、上部メニューでは
目的のページに辿り着けなくなった段階で改めて判断する。

## 11. デザイン方針

### 11.1 全体

- 長文を読みやすい1カラムを基本とする
- 本文幅を制限し、一行が長くなりすぎないようにする
- 見出し、本文、コード、注釈の階層を明確にする
- 装飾よりも、教材上の役割の違いを伝えることを優先する
- 色だけに依存せず、見出しやラベルでも種類を示す

### 11.2 デスクトップ

本文領域を中心に置き、上部メニューとページ内目次から移動する。
常設サイドバーは採用しない（§10）。

### 11.3 モバイル

- 本文、コード、画像が画面幅を超えない
- 表だけを独立して横スクロールできる
- ナビゲーションを折り畳める
- 前後リンクを縦に並べる
- タップ対象に十分な大きさを確保する

### 11.4 印刷

印刷時にはナビゲーションと不要なフッターを除外する。コード、図、演習ボックスの途中で不自然に改ページされないようにする。

専用PDFは作らず、HTMLと印刷用CSSを正本とする。PDF配布が必要になった場合は、HTMLから再現可能な形で生成する。

## 12. アクセシビリティ

次を満たす。

- HTMLの言語を日本語に設定する
- キーボードだけで主要なナビゲーションを利用できる
- 本文へ移動するスキップリンクを設ける
- 見出し階層を崩さない
- 画像に適切な代替テキストを付ける
- フォーカス位置を視覚的に確認できる
- 色のコントラストを確保する
- 注釈や警告を意味のあるHTML要素として出力する
- 動きを加える場合は、動きを減らすOS設定を尊重する

代替テキストの有無と見出し階層は機械検査する。**キーボード操作とモバイル表示、
スクリーンリーダーでの読み上げは手動でしか確かめられない**ので、開講前に実機で行う
（`maintaining.md` の公開前チェックリスト）。

## 13. 配布物と公開範囲

公開サイトと演習用ファイルをまとめた版番号付きZIP
（`downloads/cp-practice-workbook-vX.Y.Z.zip`）を提供する。

公開物は**許可リスト方式**で組み立てる。許可した以外のトップレベルがあれば、
組み立てを実行時に中止する。次は公開物に含めない。

- 教員用メモ
- 標準演習の中心部分・発展演習の完成コード（恒久非公開）
- 評価用の非公開テスト・評価ルーブリックの詳細
- 学習者の個人情報・成績・提出物・授業ログ
- 公開許諾を確認できていない画像や成果物
- 開発環境だけで使う一時ファイル

これは文書の運用だけでなく、**リポジトリの分離**（教員用資産は非公開リポジトリに
しか存在しない）と、**組み立て時の検査**（`teacher` を含むパス、`answer` /
`solution` / `rubric` を名前に含むファイルがあれば中止する）で二重に守る。

学習者の成果物は初年度は掲載しない。掲載する場合は、本人の同意、氏名表示、
ライセンス、入力データの権利を確認する。

## 14. 生成と公開

- MarkdownからPandocでHTMLを生成する
- Pythonでナビゲーションとページ一覧を組み立てる
- YAMLでサイト構成を管理する
- 共通HTMLテンプレートとCSSを使う
- GitHub Actionsで生成と検査を行う
- GitHub Pagesへ静的ファイルを公開する

ローカルのコマンドは次のとおりである。**検査は失敗理由を切り分けられるように
分けてある**（当初案は `make check` の1本だった）。

```text
make site           サイトを .site/ に生成する
make serve          生成して配信する（保存すると作り直して自動再読み込み）
make check-links    内部リンク・ページ内アンカーの検査
make check-docs     原稿・配布物の整合（§15）
make check-publish  公開範囲と個人情報だけを検査
make check          site → check-links → check-docs をまとめて
make figures        図のSVGを作り直す（図を触ったときだけ）
make pages VERSION=vX.Y.Z   公開物を .pages/ に組み立てる
make clean          生成物を消す
```

ページ間のリンクはディレクトリ形式なので `file://` では辿れない。
ローカル確認は必ず `make serve` を使う。

公開は2ブランチ方式とする。開発は既定ブランチ `dev` で行い、`main` は
リリース用workflowが生成する公開専用ブランチで直接編集しない。
GitHub Pages の配信元は `main` である。手順は `maintaining.md` にある。

## 15. 自動検査

CI（push・pull request のたび）で次を確認する。

- サイトを最後まで生成できる
- 内部リンクとページ内アンカーが存在する
- Pythonスクリプトが構文として通る

`make check-docs` は検出種別ごとに分かれており、次を検査する。
除外は理由つきで許可リストファイルに書き、**一度も一致しなかった除外は
「死んだ除外」として検査自身が違反にする**。

| 種別 | 検査すること |
|---|---|
| `frontmatter` | 各回に必要な項目があり、型が正しく、回番号が重複・欠番しない |
| `nav` | `nav.yaml` に載っていない原稿がない。登録先に実体がある |
| `structure` | 各回の見出しが §8 の標準構成に沿っている |
| `codeblock` | すべてのコードブロックに言語名がある。実行コマンドと結果が混ざっていない |
| `figure` | すべての画像に代替テキストがあり、参照先のSVGが実在する |
| `style` | 回の呼称は「第NN回」、学ぶ人の呼称は「学習者」 |
| `publish` | 公開対象外ファイル・非公開側への参照が混入していない |
| `privacy` | 絶対パス・IPアドレス・学籍番号らしき連続数字がない |
| `numbers` | 派生する数値（ファイル本数・行数）を本文に書いていない |
| `concepts` | 用語初出台帳と各回の `introduces` / `requires` が一致する |
| `glossary` | 台帳の用語が用語集に項目を持ち、初出回への案内がある |

公開物の組み立て時には、これに加えて許可リスト・ZIPの中身・組み立て後のリンクを
検査する（§13・§14）。

次はCIに入れていない。

- **HTMLの妥当性・アクセシビリティの自動検査。** 外部ツールへの依存が増えるため、
  公開前の手動確認に委ねている。
- **外部リンクの生存。** 一時的な障害でCIが赤くなるのを避けるため、リリース前の
  手動確認に回す（`maintaining.md` の公開前チェックリスト）。
- **演習モデル（MiniZinc）・演習コード（Z3）の実行。** ローカルで実行し、
  結果を非公開側の品質記録に残す運用にした。

## 16. 作成順（実績）

サイトの骨格を検証するため、全回を一度に作らず次の順で作成した。
**ホームは `nav.yaml` から自動生成されるので、手で書く原稿ではない。**

| 順 | 作ったもの | 意図 |
|---|---|---|
| 1 | 表示見本 | 全表示部品・全コードブロック区分・数式・図・表を1ページで確認する |
| 2 | 第03回（MiniZinc・数独） | モデル・データ・実行結果・演習・外部実行環境へのリンクを一度に検証する |
| 3 | Prolog実行環境の同梱と検証 | 環境が変わると第01〜02回を書き直すので、原稿より先に確定させる |
| 4 | 参考資料12本と用語初出台帳 | 各回から参照する先を先に用意する |
| 5 | 科目の進め方 → 第01・02回 | 前提が固まった順。グラフ彩色が第03・05回の比較対象になる |
| 6 | 第04〜10回 | 題材の縦断関係を壊さない順に、束で作成する |
| 7 | 第11〜15回と自由課題の支援物 | 簡略形。支援物と同時に作る |
| 8 | 公開 | 許可リスト・ZIP・実行ページの確認を経てリリースする |

## 17. 決定した事項

当初「今後決める事項」として挙げていたものは、次のとおり決定した。

| 事項 | 決定 |
|---|---|
| 正式な授業回数と各回のテーマ | 全15回・各100分。`curriculum-2026.md` §7 が正本 |
| 年度別URLと過去年度の保存方針 | 年度別URLは切らない。最新版だけを公開する |
| 常設サイドバーの有無 | 置かない（§10） |
| サイト内検索の導入時期 | 初年度は入れない（§10） |
| Prologの実行環境 | Tau Prolog を同梱した実行ページ。CDNから読まない。根拠は `prolog-environment.md` |
| MiniZinc Playgroundとローカル環境の使い分け | **第03〜10回はすべてブラウザ版Playground**。ローカル導入は行わない。自由課題で選ぶ学習者向けに参考資料へ短く併記するだけ |
| Python環境管理方法 | 標準の `venv` + `pip`。参考資料に手順を置く |
| 使用するソルバーと固定するバージョン | Z3 は `z3-solver==5.1.0.0` に固定。MiniZinc は Playground の版に従う |
| ブラウザ上の実行・可視化機能の範囲 | Prolog 実行ページのみ。可視化機能は持たない |
| 模範解答を公開する時期と方法 | 必須演習の解答はヒント最終段に公開。標準・発展は恒久非公開（§9.3） |
| 自由課題の提出物と評価基準 | 提出物と評価の観点は公開。段階と配点は非公開（§4「自由課題」） |
| 教材およびサンプルコードのライセンス | コードはMIT、講義資料はCC BY-NC-SA 4.0 の二本立て |

残っているのは次の2件である。

- **OGP、サイトマップなど公開サイト向けメタデータ。** 初版では
  `<meta name="description">` だけを出している。SNSでの共有が必要になった時点で足す。
- **スクリーンリーダーでの読み上げ確認**（§12）。開講前の実機確認に含める。

## 18. 実装順序（実績）

次の順で実装し、いずれも完了した。

1. ディレクトリ構成と最小限のビルド処理
2. ナビゲーション設定とHTMLテンプレート
3. 基本CSSとレスポンシブ対応
4. 標準的な講義ページ1件
5. 注釈、演習、ヒント、コード、数式、図、表の表示
6. 演習用ファイルの配布
7. リンク、公開範囲、アクセシビリティの検査
8. GitHub Pagesへの公開
9. 残りの講義資料の作成

この順序により、教材を大量に移行する前に標準形式と運用上の問題を確認できた。
実際、表示部品とコードブロック区分の不足は 4・5 の段階で洗い出せている。
