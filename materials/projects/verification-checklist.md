# 検証チェックリストと実験記録

[第13回](../sessions/13-project-extension.md)と[第14回](../sessions/14-project-completion.md)で使う。
[第10回](../sessions/10-roster-verification.md)で勤務表に当てた検証を、自分の問題に当て直すための表である。

::: important
**ソルバーが解を返したことと、モデルが正しいことは別である。**

`SAT` も最適解も、「書いた制約を満たす解を見つけた」としか言っていない。
**書き忘れた制約**については何も言っていない。
検証は、その書き忘れを外側から探す作業である。
:::

記入用の実体は `workbook/projects/experiments.md`、
独立した検査の雛形は `workbook/projects/verify.py` にある。

## 検証チェックリスト

上から順に難しくなる。**4を飛ばして先へ進まない。**

::: check
**1. 正常例で、期待どおりの解が出るか**

- [ ] 答えが分かっている最小インスタンスがある
- [ ] 出た解が、手作業で作った答えと同じ条件を満たしている
- [ ] 解が1つしかないはずの入力で、2つ目が出ないことを確かめた（一意性を問う問題の場合）
:::

::: check
**2. 反例で、本当に「解なし」になるか**

- [ ] 解が存在しないはずの入力を作った（条件を1つきつくする、資源を1つ減らす）
- [ ] その入力で `UNSAT` または「解なし」が返る
- [ ] 返らないなら、**足りない制約がある**ことが分かった
:::

::: check
**3. 制約を1本外したとき、違反する解を探しに行くと見つかるか**

- [ ] ハード制約を1本ずつコメントアウトして実行した
- [ ] 外した条件の**否定を一時的に足して**、違反する解を能動的に探した
- [ ] 違反する解が出た → その制約は効いている（戻すとその解が消えることも確かめた）
- [ ] `UNSAT` になった → 冗長か、探し方が足りない。どちらなのかを1行書いた
:::

::: check
**4. モデルとは独立した検査があるか**

- [ ] 企画書のハード制約1条件につき、1つの検査関数がある
- [ ] 検査は**モデルを見ずに、企画書の文から**書いた
- [ ] 正常例で「合格」、反例で「不合格」が出る
- [ ] ソフト制約のペナルティを独立に数え直し、モデルの出力と一致した
:::

::: warning
**3 が最も見落とされる。そして、確かめ方を間違えやすい。**

書いたつもりの制約が実は何も縛っていないことは珍しくない。
添字を間違えている、範囲が空になっている、条件が常に真になっている——
どれも「エラーにならないまま、何もしない制約」になる。

ただし、**外して結果が変わらなかっただけでは判定できない。**
ソルバーが返すのは条件を満たす解の1つであって、解の全体ではないので、
制約を外しても**たまたま同じ解を返す**ことがある。

確かめるには、**外した条件に違反する解を能動的に探す**。
その条件の否定を一時的な制約として足すのがいちばん確実である。
否定が書きにくいなら、禁じているはずの値を出力に固定するか、
違反の件数を数えて `solve maximize` で最大化してもよい。

見つからなかった（`UNSAT` になった）場合は、
**その制約が他の制約から導かれている**（冗長である）可能性と、
探し方が足りていない可能性がある。**直ちに未作動とは断定しない。**
冗長制約は誤りではない
（[第05回](../sessions/05-sat-dependencies.md#標準演習)のヒント3）。
:::

::: important
**検査はモデルを見ずに書く。**

モデルを見ながら検査を書くと、モデルと同じ間違いを写してしまう。
「モデルが `i+1` と書いてあるから検査も `i+1`」では、
ずれていたときに両方ともずれる。
企画書の `H1` `H2` … の文を1つずつ読みながら書く。
:::

## 独立した検査の作り方

道具によらず、形は同じである。

| 使っている道具 | 解を取り出す | 検査する |
|---|---|---|
| MiniZinc | `output` に機械可読な行を足して出力する | 出力を Python で読んで数え直す |
| Python+Z3 | `model` から値を取り出す | 同じ Python の関数へ渡して数え直す |

MiniZinc の場合、`#` で始まる行を出すのがいちばん単純である
（[第09回](../sessions/09-roster-soft.md)の `#shift` と同じ手）。
`output` を1行足すだけで済み、画面の操作に依存しない。

```{.text filename="機械可読な行の例"}
#size 4 2
#assign 数学 1 大
#assign 物理 2 大
#assign 英語 1 小
#assign 歴史 2 小
#value penalty 3
```

この例は「時間帯と教室」の2つを決める題材なので、`#assign` の値が2つある。
雛形の `verify.py` が読むのは `#assign 名前 値` の**1つ**なので、
**値が2つ以上ある題材では `verify.py` の `parse_output` の正規表現も直す**。
値が1つの題材（`#assign 数学 1`）なら、雛形のまま読める。

検査関数は「見つけた違反を並べたリスト」を返す形にする。
空のリストが返れば、その検査は通ったという意味である。

::: note
**まだ書いていない検査は、空のリストではなく `None` を返す。**

空のリスト（違反なし）と区別できないと、
**検査を書き忘れたのに反例が合格した**状態が「正常」に見えてしまう。
`workbook/projects/verify.py` の雛形は、この区別を最初から持っている。
[第10回](../sessions/10-roster-verification.md)の検証器と同じ作りである。
:::

## 実験記録の書式

**その場で書く。**後からまとめて書き起こすことはできない。何を試したか忘れるからである。

1行に次を書く。

| 列 | 中身 |
|---|---|
| 日付 | 実行した日 |
| 入力 | どのデータファイルか。規模 |
| 設定 | 重み・制約の有無・ソルバー |
| 結果 | 目的関数の値、または解の有無 |
| 実行時間 | 測った値 |
| 最適 | 最適だと確かめた／打ち切った |
| 確認方法 | どう確かめたか（手作業・検証器・目視） |

```{.markdown filename="実験記録の例"}
| 日付 | 入力 | 設定 | 結果 | 実行時間 | 最適 | 確認方法 |
|---|---|---|---|---|---|---|
| 01-08 | small（4科目2枠2教室） | H1-H3 のみ | 解あり | 0.1秒 | 確かめた | 手作業の答えと一致 |
| 01-08 | infeasible（4科目1枠1教室） | H1-H3 のみ | 解なし | 0.1秒 | — | 期待どおり |
| 01-08 | small | H3 を外す | 収容超過の解が出た | 0.1秒 | 確かめた | H3 が効いていることの確認 |
| 01-15 | standard（10科目4枠3教室） | H1-H4 + S1 (w=1) | penalty 3 | 2.4秒 | 確かめた | verify.py 合格 |
| 01-15 | standard | H1-H4 + S1 (w=5) | penalty 15 | 3.1秒 | 確かめた | verify.py 合格。割当てが変わった |
| 01-22 | large（20科目4枠3教室） | H1-H4 + S1 (w=1) | penalty 9（最良） | 60秒で打ち切り | 打ち切り | ========== が出ない |
```

::: warning
**「最適だと確かめた」と「そこまでで一番良かった」を混ぜない。**

打ち切った結果を最適値として書くと、比較そのものが崩れる。
MiniZinc なら `==========` が出たかどうかで区別できる。
出ていないなら「打ち切り時点の最良解」と書く。
:::

## 実験の組み方

実験とは**2つ以上を比べること**である。1回動かして終わりではない。

| 比べ方 | 変えるもの | 分かること |
|---|---|---|
| 条件を変える | 目的関数の重み。制約の有無 | 「良い解」の意味が何で決まっているか |
| 規模を変える | 入力の大きさ | 規模と実行時間の関係。どこで解けなくなるか |
| 表現を変える | 同じ条件の別の書き方 | 記述の見やすさと速さの関係 |

::: important
**規模を変えるときは、変える軸を1つに絞る。**

[第10回](../sessions/10-roster-verification.md)で7日と14日を比べたとき、職員数は変えなかった。
2つ同時に動かすと、差がどちらのせいか言えなくなる。
:::

::: note
**速くなったのか、問いを易しくしたのか。**

目的関数の項を減らすと速くなる。しかしそれは同じ問いに速く答えたのではなく、
**別の（易しい）問いに答えた**のである。
記録には「何を緩めたか」と「そのとき結果がどう悪くなったか」を必ず並べて書く。
[第10回](../sessions/10-roster-verification.md)の締めがこの一行だった。
:::
