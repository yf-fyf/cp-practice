# 発表資料の構成ガイド

[第14回](../sessions/14-project-completion.md)で初版を作り、
[第15回](../sessions/15-presentation.md)で使う資料の構成である。

::: important
**聞き手は、あなたのコードを読んでいない。**

読んでいないのは、モデルの中身だけではない。
**何を決める問題なのか**も知らない。
最初の1分で「何を決める問題か」が伝わらなければ、残りは全部伝わらない。
:::

## 資料の構成

7節でできている。**この順に話す。**

| # | 節 | 話すこと | 枚数の目安 |
|---|---|---|---|
| 1 | 問題設定 | 何を決める問題か。背景。入力は何で、出力は何か | 1〜2 |
| 2 | モデル | 決定変数・定義域・主要なハード制約・ソフト制約・目的 | 2〜3 |
| 3 | 道具と実行方法 | MiniZinc か Python+Z3 か。版。どう実行するか | 1 |
| 4 | 結果 | 実験の表。最小インスタンスの解を1つ見せる | 1〜2 |
| 5 | 正しさの確認 | どう検証したか。何が合格し、何が不合格になったか | 1〜2 |
| 6 | 工夫した点 | 表現の選び方、制約の書き方、詰まったところと抜け方 | 1 |
| 7 | 未解決の点と改善案 | 扱えない規模。省略した条件。次にやるなら何をするか | 1 |

::: important
**5 を飛ばさない。**

「動きました」で終わる発表は、この科目では未完成である。
ソルバーが解を返したことと、モデルが正しいことは別だからである。
検証の結果は、うまくいかなかったものも含めて述べる。
**「反例が検出できなかった」も立派な報告**である。
:::

## 節ごとの作り方

### 1. 問題設定

最初の1枚に、次の1文を書く。

```{.text filename="最初の1枚に書く1文"}
この問題では、<何> を <どう> 決める。
```

背景（誰が困っているか）は、その1文のあとでよい。
入力と出力は、企画書の節2をそのまま使える。

### 2. モデル

**コードを読み上げない。**変数と制約を日本語で言う。

| 出すもの | 出さないもの |
|---|---|
| 決定変数の意味（「科目ごとに、時間帯と教室を1つずつ」） | 変数宣言のコード全文 |
| ハード制約の一覧（`H1`〜`H4` の日本語の文） | `forall` の入れ子 |
| 目的関数が何を最小化するか | 重み付き和の式の全項 |

コードを見せるなら、**1枚に1つの制約**だけにする。
「この1行がこの条件を表している」と言えるものに絞る。

::: note
**表現の選択を1枚入れると、発表が締まる。**
「対象ごとに値を1つ」にしたか「組ごとに真偽」にしたか、
その結果どの制約を書かずに済んだか。
[グラフ彩色の3つの表現](../references/graph-coloring.md)でやった比較を、自分の問題で述べる。
:::

### 3. 道具と実行方法

1枚でよい。README の節1・節2の要約である。
**版を言う。**「MiniZinc」ではなく「MiniZinc 2.10.0、ソルバーは Gecode」と言う。

### 4. 結果

最小インスタンスの解を**1つ、目に見える形で**見せる。
表でも図でもよい。数字の列だけを出しても伝わらない。

実験の表は [実験記録](verification-checklist.md#実験記録の書式)から必要な行を抜く。
全部は載せない。**比べたい2行が隣り合うように並べる。**

::: warning
**打ち切った結果を最適値として出さない。**
表に「最適だと確かめた／打ち切った」の列を残す。
MiniZinc なら `==========` が出たかどうかで区別できる。
:::

### 5. 正しさの確認

次の3つを述べる。

1. どう確かめたか（独立した検査か、手作業か）
2. 何が合格し、何が不合格になったか（**反例が不合格になったこと**が要点）
3. その検査が**何を保証していて、何を保証していないか**

3つ目が最も価値がある。
「H1〜H4 は数え直した。ただし S1 のペナルティは数え直していないので、
モデルの計算が正しいかは確かめていない」——これが言えれば十分である。

### 6. 工夫した点

「頑張った」ではなく、**判断**を述べる。

- なぜその表現を選んだか
- どの条件をハードにし、どの条件をソフトにしたか。その境目をどこで決めたか
- 詰まったとき、どう問題を小さくして切り分けたか

### 7. 未解決の点と改善案

**足りないと分かっていることを述べるのは、減点ではない。**
隠して「動きました」と述べることのほうが問題である。

| 述べること | 例 |
|---|---|
| 扱えない規模 | 20科目を超えると60秒で最適が出ない |
| 省略した条件 | 連続する時間帯を避けたいという条件は入れなかった |
| 次にやるなら | 二段階の最適化を試す。別のソルバーで比べる |

## 時間の目安

::: note
**発表10分・質疑4分**を目安とする（5名を想定した仮案である。入替を3分見込み、
1人あたり17分で組んである）。
入替を含めた第15回の時間割は [第15回](../sessions/15-presentation.md#今回やること)にある。
人数が変われば持ち時間も変わるので、確定した配分は授業中に案内する。
:::

10分は短い。7節を均等に割ると1節あたり1分半しかない。
配分の目安は次のとおりである。

| 節 | 目安 |
|---|---|
| 1 問題設定 | 2分 |
| 2 モデル | 3分 |
| 3 道具と実行方法 | 30秒 |
| 4 結果 | 2分 |
| 5 正しさの確認 | 1分30秒 |
| 6 工夫した点 | 30秒 |
| 7 未解決の点と改善案 | 30秒 |

::: important
**必ず一度、声に出して時間を測る。**

黙って読むと、実際の半分の時間で終わったように感じる。
たいてい長すぎるので、**削る場所を先に決めておく**。
削ってよいのは 2 の細部と 6 である。1・4・5 は削らない。
:::

## 発表練習会

授業日程とは別に行う。[第14回](../sessions/14-project-completion.md)と[第15回](../sessions/15-presentation.md)の間が基本候補である。
日時と参加方法は授業中に案内する。

資料は当日版のままでよい。目的は2つだけである。

| 見ること | 判定 |
|---|---|
| 持ち時間に収まるか | 測る。超えたら削る場所を決める |
| 「コードを読んでいない人」に通じるか | 最初の1分で「何を決める問題か」が伝わったか |

## 相互質問の観点

各発表につき、**発表者以外は最低1問**を出す。
次の4観点のどれか1つを選べばよい。

| 観点 | 問いの形 | 例 |
|---|---|---|
| **モデルの前提** | 現実にはあるが、モデルに入れなかった条件は何か | 「連続する時間帯を避けたい、という条件は入れていますか」 |
| **制約の不足** | この制約を外したら、どんな解が出てしまうか | 「収容人数の制約を外すと、どんな割当てが出ますか」 |
| **目的関数の意味** | この目的で「良い」とされる解は、誰にとって良いのか | 「合計を最小にすると、いちばん損をするのは誰ですか」 |
| **検証方法** | その検査を通ったことは、何を保証していて何を保証していないか | 「検証器が合格を返したとき、ペナルティの値も確かめていますか」 |

::: warning
**質問はモデルに対して行う。**

書き方の好みや、資料の体裁を問わない。
「変数名が分かりにくい」「フォントが小さい」は、この場の質問ではない。
:::

::: note
**答えられない質問が出るのは正常である。**

「そこは確かめていません」と答えてよい。
**確かめていないことを確かめていないと言えること**が、
[第10回](../sessions/10-roster-verification.md)から続けてきたことの中身である。

答えたあと、その項目を「未解決の点」に足すとよい。
:::

## 質問を作るこつ

聞きながら、次の1つを探しておくと質問が作れる。

1. **出てこなかった言葉**を探す。「公平」「上限」「連続」——現実にはありそうで、
   説明に出てこなかった言葉が、たいてい「省略した条件」である。
2. **数字が1つしかない結果**を探す。比較が1通りしか出ていなければ、
   「別の条件だとどうなりますか」が成り立つ。
3. **「合格しました」**を探す。何が合格したのか、
   合格が何を保証するのかを問える。
