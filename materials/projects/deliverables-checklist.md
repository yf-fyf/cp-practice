# 成果物チェックリスト

[第15回](../sessions/15-presentation.md)に提出するもの一式である。
[第14回](../sessions/14-project-completion.md)で上から順に当てる。
[第11回](../sessions/11-project-formulation.md)の時点で一度目を通しておくと、
何に向かって進んでいるかが分かる。

::: important
**「動くコードがある」だけでは、成果物一式にならない。**

書いたものが正しいと言える根拠（検証記録）と、
他の人が同じ結果を出せる手順（README）が揃って一式である。
[評価の観点](README.md#評価の観点)の5つのうち3つは、コードそのものを見ていない。
:::

## チェックリスト

::: check
**提出するもの**

- [ ] **1. 企画書** — 最新版。第11回の初版ではない
- [ ] **2. モデルまたはプログラム** — MiniZinc の `.mzn`、または Python+Z3 の `.py`
- [ ] **3. 入力データ** — 最小インスタンスと標準規模の両方
- [ ] **4. 反例データ** — 解が無いはずの入力（1つ以上）
- [ ] **5. README** — 実行環境と版・実行手順・データ・出力の読み方・検証方法・既知の限界
- [ ] **6. 検証記録** — 独立した検査のコードまたは手順と、その結果
- [ ] **7. 実験結果** — 条件または規模を変えた比較の表
- [ ] **8. 限界と改善案** — 扱えること・扱えないこと・省略した条件
- [ ] **9. 発表資料** — 第15回で使うもの
:::

| # | 成果物 | 完了の目安 | 作る回 |
|---|---|---|---|
| 1 | 企画書 | 9節すべてが埋まり、モデルの現状と食い違っていない | 第11回（以後更新） |
| 2 | モデル | 企画書のハード制約がすべて入っている。制約に `H1` などの番号のコメントがある | 第12〜14回 |

| 5 | README | **複製したディレクトリで、書いてあるとおりに実行して同じ結果が出た** | 第12〜14回 |
| 6 | 検証記録 | 正常例が合格、反例が不合格。制約を1本外して**違反する解を探しに行った**結果（出た／冗長だった）が書いてある | 第13〜14回 |
| 7 | 実験結果 | 2通り以上の比較が表になっている。打ち切りと最適が区別されている | 第14回 |
| 8 | 限界 | 「省略した条件」が書いてある | 第14回 |
| 9 | 発表資料 | 通しで話して時間を測った | 第14回 |

::: note
**2・4・6 が[第14回](../sessions/14-project-completion.md)の凍結条件である。**

全ハード制約の実装（2）、反例1つ（4）、独立した検査1本（6）が揃ったら、
仕様を凍結して実験へ移る。揃っていなければ、実験より先にそこを埋める
（第14回の「凍結条件が揃っていないとき」）。
**この3つを埋めるための修正は、凍結後でも行ってよい。**
:::

::: note
**5 の目安だけが「他人の視点」で書かれている。**
ほかは自分で判定できるが、README だけは
**自分の環境で動くこと**と**書いてあるとおりに動くこと**が別だからである。
下の「提出前に必ず行うこと」で機械的に確かめる。
:::

## 提出用ディレクトリの形

決まった形は無い。参考として、次の形なら迷いが少ない。

```{.text filename="提出用ディレクトリの例"}
<自分の題材の名前>/
├── README.md            実行環境・手順・データ・出力・検証・限界
├── proposal.md          企画書（最新版）
├── experiments.md       実験記録
├── model.mzn            モデル（または model.py）
├── verify.py            独立した検査
├── data/
│   ├── small.dzn        最小インスタンス
│   ├── standard.dzn     標準規模
│   └── infeasible.dzn   反例（解が無いはずの入力）
├── out/
│   ├── small.txt        実行結果（検証器にかけたもの）
│   └── standard.txt
└── slides.<拡張子>      発表資料
```

`workbook/projects/` がこの形の出発点になっている。
自分の作業用ディレクトリへ複製して、名前を題材に合わせて変える
（入手は [演習ファイルの使い方](../../workbook/README.md)）。

::: warning
**作業の途中版・壊れた版を混ぜない。**

`model_old.mzn`・`model2.mzn`・`model_final_2.mzn` が並んでいると、
読む人はどれを実行してよいか分からない。
提出用は README が指す1本だけにする。
**途中版は手元に残してよい**が、提出用ディレクトリには入れない。
:::

## 提出前に必ず行うこと

::: check
**複製して実行し直す**

1. 提出用ディレクトリを、まったく別の場所へ複製する
2. 元のディレクトリを**開かずに**、複製したほうで README を上から読む
3. 書いてあるとおりに打つ
4. README に書いた出力と同じものが出る
:::

自分の作業ディレクトリでは動くのに複製すると動かない、はよくある。
原因はたいてい次のどれかである。

| 原因 | 症状 |
|---|---|
| データファイルをコピーし忘れている | ファイルが無いというエラー |
| 手順に絶対パスを書いている | 別の場所では動かない |
| 仮想環境の作り方を書いていない | `z3` が見つからない |
| 既定から変えたソルバー名を書いていない | 動くが終わらない |

::: important
**「動きません」と言われる前に、自分で1度言われておく。**

複製実行は、第三者の再現性を機械的に確かめる唯一の方法である。
[評価の観点](README.md#評価の観点)の「成果物の再現性」は、これがそのまま基準になる。
:::

## 提出しないもの

| 提出しないもの | 理由 |
|---|---|
| 実在する個人の情報を含むデータ | 企画書の節7で確認済みのはずである。含んでいたら架空データに置き換える |
| 途中版・壊れた版のモデル | どれを実行してよいか分からなくなる |
| Python の `.venv/` や `__pycache__/` | 手順から作り直せる。README に手順があれば足りる |

::: note
**成果物は教材サイトに載せない。**
発表資料もモデルも公開しない。提出先と方法は授業中に案内する。
:::
