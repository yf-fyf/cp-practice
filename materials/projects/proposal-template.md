# 企画書テンプレート

自由課題の最初の成果物である。[第11回](../sessions/11-project-formulation.md)で埋め、
教員レビューを受けた版を提出する。

記入用の実体は `workbook/projects/proposal.md` にある。
自分の作業用ディレクトリへ複製して使う（入手は [演習ファイルの使い方](../../workbook/README.md)）。

::: important
**企画書は最後まで生きている文書である。**

第12〜14回で制約を足したり規模を落としたりしたら、企画書も直す。
提出するのは**最新版**であって、第11回に書いた初版ではない。
:::

## 最小版: 授業内で埋める3節 {#minimal-proposal}

**第11回の授業内で埋めるのは、次の3節だけでよい。**
残る6節は次回までの宿題にする。この3節が埋まっていれば、
第12回で最小モデルを書き始められる。

| # | 節 | 授業内で書く量 |
|---|---|---|
| 3 | 決定変数と定義域 | 2〜3行。「解が求まったとき何が決まっているか」と、その範囲 |
| 4 | ハード制約の一覧 | `H1` `H2` … と日本語の文で3〜5本 |
| 6 | 入力データと最小インスタンス | **数値まで**。紙の上で答えを1つ作れる大きさにする |

```{.text filename="最小版の見本（当番表）"}
3. 決定変数と定義域
   who[d] : d 日目の当番            定義域 1..4（4人の番号）

4. ハード制約
   H1. 同じ人が2日続けて当番にならない
   H2. 火曜が不都合だと申告した人を火曜の当番にしない

6. 最小インスタンス
   人 = [A, B, C, D]、日 = 月・火・水、各日の当番は1人
   不都合 = C は火曜が不都合
   → 紙の上で解ける。候補は 4 × 4 × 4 = 64 通り
```

::: {.important}
**3節のうち、いちばん時間をかけるのは節6である。**
最小インスタンスが数値まで決まっていないと、第12回が
「どんな数値にするか考える時間」で終わってしまう。
:::

節1（問題の背景）は1〜2行のメモでよい。**節5（ソフト制約と目的）は空でよい。**
目的関数が無くても課題は成立する（下の「節5と節6の『無い』も答えである」を見る）。

残る6節（1・2・5・7・8・9）は**次回までの宿題**として埋める。
第12回の冒頭で、埋まった企画書を持ってくる。

## 9つの節

企画書は次の9節でできている。
順序は [定式化の7手順](../references/modeling-steps.md)と同じで、
前後に「背景」と「計画」が付いた形である。

| # | 節 | 立てる問い | 語彙を導入した回 |
|---|---|---|---|
| 1 | 問題の背景 | 誰の、どんな困りごとか。なぜ手作業では苦しいのか | — |
| 2 | 入力と出力 | 何が与えられていて、何を出すのか | [第03回](../sessions/03-minizinc-sudoku.md)・[第04回](../sessions/04-sudoku-data-uniqueness.md) |
| 3 | 決定変数と定義域 | 解が決まったとき、何が決まっているのか。各変数はどの範囲を取るか | [第03回](../sessions/03-minizinc-sudoku.md)・[第08回](../sessions/08-roster-hard.md) |
| 4 | ハード制約の一覧 | 破ったら解として認められない条件は何か | [第05回](../sessions/05-sat-dependencies.md)・[第08回](../sessions/08-roster-hard.md) |
| 5 | ソフト制約と目的 | 破ってもよいが避けたい条件は何か。何を最小化・最大化するのか | [第07回](../sessions/07-theme-assignment.md)・[第09回](../sessions/09-roster-soft.md) |
| 6 | 入力データと最小インスタンス | どのデータを使うか。最小の例を数値まで書くとどうなるか | [第04回](../sessions/04-sudoku-data-uniqueness.md) |
| 7 | データの出所と権利 | そのデータはどこから来たか。使ってよいか | — |
| 8 | 主ツールと選択理由 | MiniZinc と Python+Z3 のどちらを使うか。もう一方を選ばない理由は何か | — |
| 9 | 検証の方法と段階計画 | 答えが正しいことをどう確かめるか。第12〜14回で何をどこまでやるか | [第10回](../sessions/10-roster-verification.md) |

::: note
**節5と節6の「無い」も答えである。**
「条件を満たす解が1つ欲しいだけ」の問題では、ソフト制約も目的も空でよい。
その場合は空欄にせず「**充足だけを求める**」と書く。
空欄は「まだ考えていない」と読まれる。
:::

## 各節の書き方

### 1. 問題の背景

3〜5行でよい。次の3つが分かればよい。

- 誰が、いつ、何を決めているのか
- 今はどうやって決めているのか（手作業・勘・前年の踏襲）
- 何が苦しいのか（時間がかかる・条件を見落とす・不公平になる）

架空の設定でよい。実在の組織を題材にする場合も、
**登場する人名・所属は架空のものに置き換える**。

### 2. 入力と出力

「与えられているもの」と「決めてほしいもの」を、はっきり2つに分ける。

```{.text filename="入力と出力の書き分け"}
入力（パラメータ）: 科目の一覧、教室の一覧と収容人数、受験人数、担当者の不都合な時間帯
出力（決定変数から作る）: 各科目の実施時間帯と教室
```

::: warning
**この2つが混ざったまま先へ進むと、決めてほしいものを先に決めてしまう。**

「担当者の都合のよい時間帯に入れる」と書いたとき、
都合のよい時間帯は**入力**で、そこに入れるかどうかが**出力**である。
1つずつ「これは与えられているのか、決めてほしいのか」と問う。
:::

### 3. 決定変数と定義域

決定変数は、**「解が求まった」と言えるとき何が決まっているか**である。
表現は一通りではない。書き方によって、後で書かずに済む制約が変わる。

| 表現 | 例 | 自動で保証されること |
|---|---|---|
| 対象ごとに値を1つ | 各科目に時間帯の番号を1つ | 1科目が2つの時間帯に入らない |
| 組ごとに真偽 | 科目と時間帯の組ごとに `Bool` | （何も保証されない。「ちょうど1つ」を書く必要がある） |

定義域は狭く正しく書くほどよい。
「時間帯は 5 以上にならない」を制約として書く必要はない。定義域を 1〜4 にしておけばよい。

比較の材料は [グラフ彩色の3つの表現](../references/graph-coloring.md)にある。

### 4. ハード制約の一覧

**自然言語の文のまま**書き出す。式にするのは第12回である。
`H1` `H2` と番号を振る。後で「`H3` を外すと解が出るか」と試せる。

```{.text filename="まず日本語で番号を振る"}
H1. 同じ時間帯に、同じ教室で2つの科目を実施しない
H2. 同じ担当者の科目を同じ時間帯に入れない
H3. 受験人数は教室の収容人数を超えない
H4. 担当者が不都合と申告した時間帯には入れない
```

::: note
**表現がすでに保証している条件は書かない。**
節3で「各科目に時間帯を1つ」と決めたなら、
「1つの科目は1つの時間帯にだけ入る」は書かなくてよい。
何が自動で保証され、何を明示的に書くかを分けるのが[第08回](../sessions/08-roster-hard.md)の中心だった。
:::

### 5. ソフト制約と目的

ハード制約と**分けて**書き、破ったときのペナルティを決める。

```{.text filename="ソフト制約とペナルティ"}
S1. 同じ受験者が同じ日に3科目以上受けない  → 超えた科目数 × 3 点
S2. 午前の時間帯を優先する                  → 午後に入った科目数 × 1 点

目的: S1 と S2 のペナルティの重み付き和を最小化する
```

::: warning
**ハードに入れるかソフトに入れるかで、解が出るかどうかが変わる。**
全部ハードにすると `UNSAT` になりやすい。
1つずつ「これは絶対に破れないか」と問い直す。
:::

### 6. 入力データと最小インスタンス

**数値まで書き下す。**「4科目・2時間帯」ではなく、4科目の名前と2時間帯の中身を全部書く。
ここが決まっていないと、第12回は数値を考える時間で終わる。

最小インスタンスの目安は、**紙の上で答えを1つ作れる大きさ**である。
授業で使った規模なら、数独は4×4、勤務表は4人・3日がこの水準にあたる。

標準規模のほうは、この時点では「だいたいこれくらい」でよい。
第13回で実際に上げてみて、動かなければ戻す。

### 7. データの出所と権利

| 書くこと | 例 |
|---|---|
| 出所 | 自分で作った架空データ／公開されているデータセット（名前と入手先） |
| 利用条件 | 自由に使ってよい／出典を書けば使ってよい／確認できていない |
| 個人情報の扱い | 実在する個人の情報を含まないこと |

::: warning
**確認できないデータは使わない。**

勤務表・時間割・名簿の類は、身の回りの実物を使いたくなる題材である。
しかし成果物は提出し、発表で画面に映る。
出所と利用条件を書けないものは、**架空のデータを自分で作って置き換える**。
授業で使った勤務表・テーマ割当のデータも、すべて架空である。
:::

### 8. 主ツールと選択理由

使う道具を1つ決める。もう一方を**選ばない理由**も1〜2文で書く。
選択そのものより、理由を言葉にすることに意味がある。

| 問題の性質 | 向いている道具 |
|---|---|
| 表・配列・割当てが中心。制約を宣言的に書き並べたい | MiniZinc |
| 「ちょうど1つ」「合計が上限以下」のような大域制約が要る | MiniZinc |
| 目的関数を1本立てて最適化する | MiniZinc |
| 入力の前処理・出力の整形を Python で書きたい | Python+Z3 |
| 真偽の組合せ・含意が制約の中心である | Python+Z3 |
| 解を1つ得るたびに条件を足して解き直したい | Python+Z3 |

迷ったら、**[第03回](../sessions/03-minizinc-sudoku.md)から[第10回](../sessions/10-roster-verification.md)までで自分がよく読めたほうの回の道具**を選ぶ。
自由課題は道具に慣れる場ではなく、問題を解く場である。

::: note
どちらでも書ける問題は多い。「どちらでも書ける」と分かったうえで
一方を選ぶのは、正当な選び方である。その旨を書けばよい。
:::

### 9. 検証の方法と段階計画

検証は**1行でよい**。ただし書けることが条件である。

```{.text filename="検証の1行"}
出力した時間割を Python で読み、H1〜H4 を1条件につき1関数で数え直す。
違反が0件で、かつ S1・S2 のペナルティがモデルの出力と一致すれば合格とする。
```

これが書けないなら、その問題は**まだ仕様が決まっていない**。
何を満たしていれば正解なのかが決まっていないということだからである。

段階計画は3行で足りる。

```{.text filename="段階計画"}
第12回: 4科目・2時間帯・2教室で H1〜H3 まで動かす
第13回: H4 と S1・S2 を足し、10科目・4時間帯・3教室へ上げる。検証器を書く
第14回: 重みを変えた3通りと、規模を2段階で比べる
```

## 記入例

次は、記入済みの企画書を短くしたものである。
**この題材をそのまま選んでもよい**が、その場合は制約か目的を1つ足す。

```{.markdown filename="記入例（抜粋）"}
# 企画書: 期末試験の時間割と教室割当

## 1. 問題の背景
架空の学科で、期末試験の日程を担当者が手作業で組んでいる。
科目・教室・担当者の都合を紙の上で突き合わせているため、
組み終わるまでに数日かかり、収容人数の見落としが毎年1件は出る。

## 2. 入力と出力
入力: 科目の一覧、各科目の受験人数、各科目の担当者、教室の一覧と収容人数、
      担当者ごとの不都合な時間帯
出力: 各科目を「どの時間帯」の「どの教室」で実施するか

## 3. 決定変数と定義域
slot[c] : 科目 c の時間帯     定義域 1..4
room[c] : 科目 c の教室       定義域 1..3
（科目ごとに1つの値にするので、「1科目が2か所で同時に」は起こらない）

## 4. ハード制約
H1. 同じ時間帯・同じ教室に2科目を入れない
H2. 同じ担当者の科目を同じ時間帯に入れない
H3. 受験人数 <= 割り当てた教室の収容人数
H4. 担当者が不都合と申告した時間帯には入れない

## 5. ソフト制約と目的
S1. 同じ時間帯に使う教室は少ないほうがよい → 使った教室数 × 1 点
目的: S1 のペナルティを最小化する

## 6. 入力データと最小インスタンス
最小インスタンス（第12回で使う）:
  科目 = [数学, 物理, 英語, 歴史]
  受験人数 = [30, 20, 45, 25]
  担当者 = [A, A, B, C]
  時間帯 = 1..2
  教室 = [大(50), 小(30)]
  不都合 = 担当者 C は時間帯 1 が不都合
  → 紙の上で解ける。英語(45名)は必ず大教室に入る
標準規模（第13回で使う）: 10科目・4時間帯・3教室

## 7. データの出所と権利
すべて自分で作った架空データ。実在の科目名・人名は使わない。

## 8. 主ツールと選択理由
MiniZinc を主に使う。科目ごとに1つの値を決める割当ての問題で、
「同じ時間帯・同じ教室が重ならない」を配列と forall で素直に書けるためである。
Python+Z3 を選ばないのは、入力の前処理も出力の整形も要らず、
Python 側で書くことが残らないためである。

## 9. 検証の方法と段階計画
検証: 出力を Python で読み、H1〜H4 を1条件につき1関数で数え直す。
      違反0件、かつペナルティがモデルの出力と一致すれば合格。
第12回: 最小インスタンスで H1〜H3 まで
第13回: H4 と S1 を足し、標準規模へ。検証器を書く
第14回: 教室数を 3→2 に減らした場合と、規模2段階を比べる
```

::: {.discuss}
この記入例で、**節3の1行のコメント**（「科目ごとに1つの値にするので…」）に注目する。
表現を選んだ時点で書かずに済んだ制約を、企画書に残してある。
第12回で「この制約を書き忘れたのでは」と迷ったときに、ここを読み返せる。
:::

## レビューと提出

第11回の授業内で、教員との短いレビューを行う。見るのは次の3点である。

| 見るところ | よくある指摘 |
|---|---|
| 制約の曖昧さ | 「なるべく」「できるだけ」がハード制約に入っている |
| 規模 | 最小インスタンスが紙で解けない大きさになっている |
| ツール選択 | 選んだ理由が「使ったことがあるから」だけになっている |

レビューを受けた版を提出する。以後の回で内容が変わったら企画書も直す。
