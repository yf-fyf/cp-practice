# README テンプレート

成果物に添える README である。
[第12回](../sessions/12-project-minimal-model.md)で4節ぶんを書き始め、
[第14回](../sessions/14-project-completion.md)で6節に仕上げる。

記入用の実体は `workbook/projects/README.md` にある。
自分の作業用ディレクトリへ複製して使う（入手は [演習ファイルの使い方](../../workbook/README.md)）。

::: important
**README の基準はただ1つ、「自分以外の人が同じ結果を出せるか」である。**

きれいに書けているかではない。書いてあるとおりに打てば動くかである。
[第14回](../sessions/14-project-completion.md)では、**別のディレクトリへ複製して実際に試す**。
:::

## 6つの節

| # | 節 | 書くこと | いつ書くか |
|---|---|---|---|
| 1 | 実行環境と版 | 使った道具と、その版 | 第12回 |
| 2 | 実行手順 | そのまま打てば動く形の手順 | 第12回 |
| 3 | データ | どのファイルが何のデータか。出所 | 第12回 |
| 4 | 出力と読み方 | 何が出れば成功か。出力の各行が何を表すか | 第12回 |
| 5 | 検証方法 | 正しさをモデルとは独立にどう確かめたか | 第14回 |
| 6 | 既知の限界 | どこまでなら解けるか。何を省いたか | 第14回 |

第12回の**暫定版**は 1〜4 の4節でよい。
第13回で検証を始めたら 5・6 を書き足す。

## 各節の書き方

### 1. 実行環境と版

版を書く。「MiniZinc」ではなく「MiniZinc 2.10.0（Playground の既定ソルバー Gecode）」と書く。

| 使った道具 | 書くこと | 調べ方 |
|---|---|---|
| MiniZinc Playground | 版とソルバー名 | 画面のソルバー選択欄（[使い方](../references/setup-minizinc.md)） |
| ローカルの MiniZinc | `minizinc --version` の出力 | [使い方](../references/setup-minizinc.md)の「ローカルに入れる」 |
| Python + Z3 | Python の版と `z3-solver` の版 | `python3 --version` と `z3.get_version_string()`（[使い方](../references/setup-z3.md)） |

::: warning
**同じソルバーでも、版が違えば返る解が変わることがある。**

最適値は変わらないが、同じ最適値を持つ解が複数あるとき、
どれが返るかはソルバーと版で変わる。
「実行したら README と違う解が出た」を読む人が誤解しないよう、
節4に**解が一意でないなら一意でないと書く**。
:::

### 2. 実行手順

**そのまま打てば動く形**で書く。「Playground で実行する」では足りない。

- どのファイルをモデルとして開くか
- どのファイルをデータとして指定するか
- ソルバーを既定から変えたなら、何に変えたか
- Python なら、仮想環境の作り方から書く

```{.console filename="Python + Z3 の場合（そのまま打てる形）"}
$ python3 -m venv .venv
$ source .venv/bin/activate
$ pip install -r requirements.txt
$ python3 model.py data/small.json
```

::: note
**打ち切りが要る実行は、打ち切り方も書く。**
「`==========` が出ないまま数分続くので、60秒で止めて最後の解を使う」のように
書いておくと、読む人が「壊れている」と誤解しない。
:::

### 3. データ

ファイルごとに1行ずつ書く。**規模も書く**。

| ファイル | 中身 | 規模 |
|---|---|---|
| `data/small.dzn` | 最小インスタンス。手作業で答えを確かめた例 | 4科目・2時間帯・2教室 |
| `data/standard.dzn` | 標準規模 | 10科目・4時間帯・3教室 |
| `data/infeasible.dzn` | 解が無いことを確かめるための反例 | 4科目・1時間帯・1教室 |

出所と利用条件は、企画書の節7と同じことを1行で書く。
架空データなら「すべて架空データ」と書く。

### 4. 出力と読み方

**何が出れば成功か**を書く。読む人は出力の意味を知らない。

```{.text filename="出力の説明の例"}
成功すると、科目ごとに1行ずつ「科目名 時間帯 教室」が出る。
最後に #penalty の行が出る。これがソフト制約の違反ぶんの合計である。
MiniZinc が最後に ========== を出していれば、それが最適解である。
出ていない場合は打ち切り時点の最良解であり、最適とは限らない。

同じペナルティを持つ割当ては複数あるので、
ソルバーや版が違うと別の割当てが出ることがある。
```

検証器へ渡すために機械可読な行を出しているなら、その書式もここに書く。
[第09回](../sessions/09-roster-soft.md)の `#shift` のように、
`#` で始まる行を足すのがいちばん単純である。

### 5. 検証方法 / 6. 既知の限界

**検証**は、何を、どう確かめたかを書く。

```{.text filename="検証の説明の例"}
verify.py がモデルとは独立に H1〜H4 を数え直す。
    python3 verify.py out/standard.txt data/standard.dzn
data/small.dzn の解は手作業でも確かめた。
data/infeasible.dzn では「解なし」になることを確かめた。
H3 を外したモデルでは、収容人数超過が検出されることを確かめた。
```

**既知の限界**は3つに分けて書く。それぞれ1〜2行でよい。

| 見出し | 書くこと |
|---|---|
| 扱えること | どの規模まで、どの条件までなら解が出るか |
| 扱えないこと | 規模の上限。打ち切りが起きる設定。表現しきれなかった条件 |
| 省略した条件 | 現実にはあるがモデルに入れなかったもの。なぜ入れなかったか |

::: important
**3つ目を書けることが、この科目の到達点の1つである。**

モデルは現実の一部を切り取ったものである。
**何を切り落としたかを言えるかどうか**が、モデルを理解しているかの目安になる。
「実装が間に合わなかった」も理由として正当である。隠すほうが問題である。
:::

## ひな形

`workbook/projects/README.md` の中身は次の形をしている。
見出しはそのまま使い、`<...>` を自分の内容に置き換える。

```{.markdown filename="workbook/projects/README.md（ひな形）"}

<1〜3行で、何を決める問題かを書く>

| 道具 | 版 |
|---|---|
| <MiniZinc / Python> | <版> |
| <ソルバー / z3-solver> | <版> |

## 実行手順

<そのまま打てば動く形で書く>

## データ

| ファイル | 中身 | 規模 |
|---|---|---|
| <path> | <説明> | <規模> |

出所: <架空データ／公開データセットの名前と入手先>

## 出力と読み方

<何が出れば成功か。各行が何を表すか。解が一意かどうか>

```

## よくある抜け

第14回の「複製して実行し直す」で見つかるのは、たいてい次のどれかである。

| 抜け | 症状 |
|---|---|
| データファイルをコピーし忘れている | ファイルが無いというエラーで止まる |
| 仮想環境の作り方を書いていない | `z3` が見つからないというエラーで止まる |
| 絶対パスを手順に書いている | 別の場所では動かない |
| ソルバーを既定から変えたことを書いていない | 動くが、いつまでも終わらない |
| 出力の読み方を書いていない | 動くが、成功したのかどうか読む人に分からない |
