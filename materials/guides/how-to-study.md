# 科目の進め方

このページは、この科目を最初から最後まで進めるための地図である。
各回の中身に入る前に一度読み、進め方に迷ったら戻ってくる。

::: important
この科目で身につけてほしいのは、**解き方の手順を書くのではなく、
解が満たすべき条件を書く**という考え方である。
道具（Prolog・MiniZinc・Z3）は、その考え方を試すための手段にすぎない。
:::

## 全15回の流れ

15回は4つのまとまりに分かれる。前半で道具を1つずつ増やし、
後半で総合題材に取り組み、最後は自分で選んだ問題を解く。

| まとまり | 回 | 何をするか | 道具 |
|---|---|---|---|
| 宣言的記述と探索 | 第01〜02回 | 論理グリッドパズルを、事実と関係の記述だけで解く | Prolog |
| 制約モデリングの基本 | 第03〜06回 | 数独で変数・定義域・制約の語彙を作り、依存関係解決でSATとSMTに触れる | MiniZinc / Python+Z3 |
| 最適化と総合題材 | 第07〜10回 | テーマ割当で目的関数を、勤務表で形式化・最適化・検証を通す | MiniZinc |
| 自由課題と発表 | 第11〜15回 | 自分で選んだ問題を定式化し、実装し、検証し、発表する | どちらでも |

道具は3つ出てくるが、**毎回すべてを使うわけではない**。
Prolog は第01〜02回だけで完結し、第03回以降は使わない。

回ごとの目標・演習・完了条件は、各回のページに書いてある。
[講義の一覧](../../sessions/)から入る。

::: note
回の順序と題材の全体像は [カリキュラム](../../design/curriculum-2026.md)が正本である。
この科目の設計意図まで知りたい場合はそちらを読む。
:::

## 1回100分の使い方

題材を扱う回は、おおよそ次の配分で進む。

| 時間 | 活動 |
|---|---|
| 15分 | 今回の問題と、前回から増える条件を確かめる。結果を予想する |
| 20分 | 問題を変数・定義域・制約・目的へ分解する |
| 15分 | 必要な概念と書き方の説明。小さな実行例を動かす |
| 40分 | 必須演習・標準演習に取り組む。個別に相談する |
| 10分 | 結果を確かめ、制約の抜けを探し、完了チェックを付ける |

第05回・第06回は理論の概説に20分を使うので、演習の時間が少し短くなる。

**授業時間内にすべてを終えることは求めていない。**
標準演習が残ったら自習で続ける。次回の前提になる部分は必須演習として
はっきり分けてあるので、そこだけは次の回までに終わらせる。

::: warning
教材ページの本文が自習の正本である。
欠席しても、ページを上から読めば同じところまで進める作りにしてある。
:::

## 演習の3段階

どの回の演習も3段階に分かれている。**上から順に手を付ける。**

| 段階 | 位置づけ | 目安 |
|---|---|---|
| 必須演習 | 次回の内容に必要。授業後の自習を含めて必ず終える | 段階的ヒントがあり、最終段に解答がある |
| 標準演習 | その回の中心。100分と必要な自習で終えるのを目指す | ヒントはあるが、完成コードは出さない |
| 発展演習 | 先へ進みたい人向け。終わらなくても次回に困らない | 方向づけだけ。完成コードは出さない |

必須演習の解答は、ヒントの最後の段を開けば読める。
**ただし、まず自分で書いてから開く。** 開いてしまうと、
どこで詰まっていたかが分からなくなる。

標準演習と発展演習の完成コードは公開していない。
書けたかどうかは、完了条件（「実行して何が出れば終わりか」）で判断する。

::: note
発展演習は、作業量を増やすものではない。
問題の規模・制約・目的関数・検証方法のどれかを一段進めるように作ってある。
時間があるときに1つ選んで取り組めばよい。
:::

## 完了チェックの使い方

各回の末尾に「完了チェック」がある。
チェックボックスは表示だけで、状態は保存されない。
自分のメモに書き写すか、その場で口に出して確かめる。

チェック項目は「動いた」ではなく**「説明できる」**の形で書いてある。
これは意図的である。ソルバーが解を返したことと、
モデルが正しいことは別だからである。

::: check
1つの回を終えたと言えるのは、次の3つが揃ったときである。

- 必須演習の完了条件を満たした
- 得られた結果を、元の問題の言葉で説明できる
- 完了チェックの各項目に「はい」と答えられる
:::

## 実行環境

使う環境は3つで、**導入作業が要るのは Z3 だけ**である。

| 回 | 環境 | 準備 | 案内 |
|---|---|---|---|
| 第01〜02回 | 教材サイトの Prolog 実行ページ | 不要（ブラウザだけ） | [使い方](../references/setup-prolog.md) |
| 第03〜04回、第07〜10回 | MiniZinc Playground | 不要（ブラウザだけ） | [使い方](../references/setup-minizinc.md) |
| 第05〜06回 | Python + `z3-solver` | **必要**（版を固定して導入） | [使い方](../references/setup-z3.md) |

Z3 の導入は第05回の前に済ませておく。手順は事前に案内する。
**第05回の内容へ進む前に、Python から Z3 を呼び出せること**が完了条件である。

演習で編集するファイルは `workbook/` にまとめて配布する。
入手と展開のしかたは [演習ファイルの使い方](../../workbook/README.md)にある。

::: warning
ブラウザで動く実行環境は、書いた内容をブラウザの中にしか保存しない。
別の端末では続きから開けないし、履歴を消すと消える。
**残したいものは演習ファイルへ写して保存する。**
:::

## 困ったときの順序

つまずいたら、次の順に当たる。

1. その回のページの「よくある誤り」を見る。症状から原因を引ける形にしてある。
2. [よくあるエラーと対処](../references/errors.md)を見る。道具ごとのエラー文の読み方がある。
3. 早見表で書き方を確かめる（[Prolog](../references/prolog-cheatsheet.md) /
   [MiniZinc](../references/minizinc-cheatsheet.md) / [Z3Py](../references/z3py-cheatsheet.md)）。
4. 用語が分からなくなったら [用語集](../references/glossary.md)を引く。
   初出の回へのリンクが付いている。
5. **問題を小さくする。** 制約を1つずつコメントアウトして、
   どれを外すと動くかを見る。これが最も速い切り分けである。

## 自由課題（第11〜14回）

後半の4回は、自分で選んだ問題に取り組む。
第15回でその成果を発表する。

流れはおおよそ次のとおりである。

| 回 | やること |
|---|---|
| [第11回](../sessions/11-project-formulation.md) | 問題を選び、変数・定義域・制約・目的・入力データを決める |
| [第12回](../sessions/12-project-minimal-model.md) | 手作業で答えを確かめられる最小の例で、動くモデルを作る |
| [第13回](../sessions/13-project-extension.md) | 制約や目的関数を足し、規模を広げ、結果が正しいことを確かめる |
| [第14回](../sessions/14-project-completion.md) | 条件を変えて実験し、成果物一式と発表資料をまとめる |
| [第15回](../sessions/15-presentation.md) | 発表する |

題材は、授業で扱ったものの発展でも、まったく別のものでもよい。
道具は MiniZinc と Python+Z3 のどちらを選んでもよい。

**基礎回の演習が、そのまま自由課題の練習になっている。**
各回の末尾に「自由課題に向けて」という短いメモを置いてあるので、
気になった問題があればその都度書き留めておく。

詳しい案内は [自由課題の案内](../projects/README.md)にある。
テーマ例・成果物一式・評価の観点と、次のテンプレートがある。

## 質問・相談のしかた

少人数の科目なので、授業中はいつでも手を挙げてよい。
授業外の相談も受け付ける。

質問するときは、次の3つを一緒に伝えると早く進む。

1. **何をしようとしたか**（どの回のどの演習か）
2. **何をしたか**（書いたコードと、実行したクエリやコマンド）
3. **何が起きたか**（画面に出た文をそのまま。要約しない）

「動きません」だけでは切り分けられない。
エラー文は、たとえ読めなくてもそのまま写して見せる。

::: important
**答えを聞くのは最後でよい。**
「どこまでは意図どおり動いているか」を一緒に確かめるほうが、
次に同じ壁に当たったときに自分で抜けられる。
:::

## 評価について

成果物の提出と成果発表が必須要件である。
評価の観点は次のとおりである（[自由課題の案内](../projects/README.md#評価の観点)に同じ表がある）。

- 問題を変数・定義域・制約・目的へ分解できているか
- モデルやプログラムを他の人が再実行できるか
- 得られた解が制約を満たすことを確かめているか
- 実験結果を根拠に、モデルの特徴と限界を説明できているか
- 発表で、問題設定から結果までを一貫して説明できているか

**動くコードを書いたかどうかだけを見るのではない。**
書いたものが正しいと言える根拠を持っているかを見る。
