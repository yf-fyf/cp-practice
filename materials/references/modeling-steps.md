# 定式化の7手順

この科目では、どの題材も**同じ順序**で書き下す。
第03回で語彙を決めてから、[第10回](../sessions/10-roster-verification.md)と自由課題まで同じ順序を使う。
迷ったらこのページに戻ってくる。

## 7つの手順

| # | 手順 | 立てる問い |
|---|---|---|
| 1 | 対象と入力データ | 何が与えられていて、何は与えられていないか |
| 2 | 決定変数 | 解が決まったとき、何が決まっているのか |
| 3 | 定義域 | 各変数はどの範囲の値を取るか |
| 4 | ハード制約 | 破ったら解として認められない条件は何か |
| 5 | ソフト制約 | 破ってもよいが、なるべく避けたい条件は何か |
| 6 | 目的 | 何を最小化・最大化するのか。そもそも目的はあるのか |
| 7 | 検証 | 出てきた解が本当に条件を満たすと、どうやって確かめるか |

::: important
**手順5と6は無いこともある。** 「条件を満たす解が1つ欲しい」だけの問題では、
ソフト制約も目的も空でよい（第03〜06回・[第08回](../sessions/08-roster-hard.md)がそうである）。
「無い」と書くのも定式化の結果である。空欄のまま飛ばさない。
:::

## 1. 対象と入力データ

問題を解く前に分かっている値を書き出す。
これが**パラメータ**になる。

- 何が入力か（盤面の初期値、地区の隣接関係、職員の名簿、希望順位）
- 規模はどれくらいか（何行何列か、何人か、何日か）
- 入力はどこから来るのか（モデルに直接書くのか、データファイルに分けるのか）

::: {.term}
**パラメータ**とは、モデルを書く時点で値が決まっているものである。
ソルバーはこれを動かさない。
:::

::: warning
入力データと決定変数の区別が曖昧なまま書き始めると、
**決めてほしいものを先に決めてしまう**モデルになる。
「これは与えられているのか、決めてほしいのか」を1つずつ問う。
:::

## 2. 決定変数

「解が求まった」と言えるとき、**何が決まっているのか**を書き出す。
それが決定変数である。

| 題材 | 決定変数 |
|---|---|
| 数独 | 各マスに入る数字 |
| グラフ彩色 | 各地区に塗る色 |
| テーマ割当 | 各希望者に割り当てるテーマ |
| 勤務表 | 各職員の各日の勤務区分 |

同じ問題でも、変数の取り方は一通りではない。
グラフ彩色は「地区ごとに色を1つ」とも「地区と色の組ごとに真偽」とも書ける
（[グラフ彩色の3つの表現](graph-coloring.md)）。

::: {.discuss}
変数の取り方を変えると、**書かずに済む制約**が変わる。
どちらが読みやすいか、どちらが短く書けるかを比べてから決める。
:::

## 3. 定義域

各決定変数が取り得る値の範囲を書く。

- 数独のマス: 1〜4（または 1〜9）
- 地区の色: 赤・緑・青
- 勤務区分: 日勤・夜勤・休み

::: important
定義域を狭く正しく書くほど、**制約を1つ書かずに済む**。
「マスには 5 は入らない」を制約として書く必要はない。
定義域を 1〜4 にしておけばよい。
:::

## 4. ハード制約

破ったら解として認められない条件である。
**自然言語の文のまま**書き出してから、式に直す。

```{.text filename="まず日本語で書き出す"}
H1. どの行にも 1〜4 が1回ずつ現れる
H2. どの列にも 1〜4 が1回ずつ現れる
H3. どの 2×2 ブロックにも 1〜4 が1回ずつ現れる
H4. 初期値のマスは、その数字のまま動かさない
```

番号を振っておくと、後で「H3 を外すと解が出るか」と試せる。
モデルのコメントにも同じ番号を書いておく。

::: note
**表現がすでに保証している条件は書かない。**
「1つのマスに数字は1つだけ」は、マスを1つの決定変数にした時点で保証されている。
何が自動で保証され、何を明示的に書くかを意識する（[第08回](../sessions/08-roster-hard.md)の中心テーマである）。
:::

## 5. ソフト制約

破ってもよいが、なるべく避けたい条件である。
ハード制約と分けて書き、**破ったときのペナルティ**を決める。

```{.text filename="ソフト制約とペナルティ"}
S1. 夜勤は1人あたり3回まで  → 超えた回数 × 2 点
S2. 希望休はなるべく通す    → 通らなかった件数 × 1 点
```

::: warning
ハード制約に入れるかソフト制約に入れるかで、**解が出るかどうかが変わる**。
全部ハードにすると UNSAT になりやすい。
「絶対に破れないか」を1つずつ問い直す。
:::

重みの決め方に唯一の正解は無い。項ごとに値の範囲が違うと比較にならないので、
**桁を揃えてから**重みを付ける。

## 6. 目的

最小化または最大化する量を1つの式で書く。

| 型 | 例 |
|---|---|
| 目的なし | 条件を満たす解が1つあればよい（数独、グラフ彩色） |
| 最大化 | 希望順位の点数の合計（テーマ割当） |
| 最小化 | ソフト制約のペナルティの重み付き和（勤務表） |

::: {.discuss}
**「良い解」の定義は、目的関数の設計そのものである。**
合計を最大にすると、一部の人が極端に損をする解が選ばれることがある。
最も不満の大きい人の不満を最小にすると、合計は下がる。
どちらが良いかは問題の側の判断であって、ソルバーは決めてくれない。
:::

## 7. 検証

出てきた解が本当に条件を満たすかを、**モデルとは別の方法で**確かめる。

- 手で確かめられる小さな例を先に解く（答えが分かっている盤面など）
- モデルとは独立した検証スクリプトで、ハード制約を1つずつ点検する
- **わざと壊したデータ**を入れて、ちゃんと「違反あり」と言うかを確かめる
- 解が無いはずの入力で、本当に UNSAT になるかを確かめる

::: warning
モデル自身に「この解は正しいか」を聞いても意味が無い。
モデルが間違っていれば、間違った基準で「正しい」と答える。
**検証は必ずモデルの外側で行う**（[第10回](../sessions/10-roster-verification.md)）。
:::

## 書き出し用のひな形

新しい問題に取りかかるときは、これをコピーして埋める。
埋まらない欄があれば、そこがまだ決まっていないところである。

```{.text filename="定式化シート"}
■ 対象
   （何を決める問題か。1〜2文）

1. 入力データ（パラメータ）
   -
2. 決定変数
   -
3. 定義域
   -
4. ハード制約
   H1.
   H2.
5. ソフト制約とペナルティ
   S1.                     ペナルティ:
6. 目的
   （最小化 / 最大化 / なし）
7. 検証の方法
   - 手で確かめる小さな例:
   - 独立した検査:
   - 反例（違反しているはずのデータ）:
```

## よくあるつまずき

| つまずき | 直しかた |
|---|---|
| いきなりコードを書き始めて、何を決める問題か曖昧なまま進む | 1と2を日本語で書き終えるまでエディタを開かない |
| 入力データと決定変数が混ざる | 「与えられている／決めてほしい」で1つずつ仕分ける |
| 条件を全部ハード制約にして UNSAT になる | 4と5を分け直す。制約を1つずつ外して原因を特定する |
| 目的関数を作ってから「良い解」の意味を考える | 6の前に「何が良い解か」を1文で書く |
| 解が出た時点で終わりにする | 7を飛ばさない。壊したデータで検査が反応するかまで見る |
