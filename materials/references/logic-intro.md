# 論理の入門(1) 読み方

この科目は論理学の授業ではない。それでも、Prolog の規則も、MiniZinc の `forall` も、
Z3 の `Implies` も、同じ1つの骨組みの上に立っている。
このページは、その骨組みを**言葉の側から**一度だけ通して見るために置いてある。

::: note
このページは**番外の自習用**である。授業では扱わない。

読むなら**第05回に入る前に、上から一気に**読むとよい。

## 命題から述語へ {#from-propositions}

第05回では `use_app`（「`app` を入れる」）のように、
成り立つか成り立たないかが決まる文1つに、真偽変数1つを当てた。

この書き方は、対象が増えると行き詰まる。
第01回の4人の飲み物を同じやり方で表すと、
`aoi_drinks_cocoa`・`aoi_drinks_coffee`・… と変数が並ぶことになる。
数が増えるだけならまだよいが、**「誰が」「何を」が変数名の中に埋まって取り出せない**。
「同じ飲み物を飲む2人」のような、対象どうしの関係が書けなくなる。

第01回で書いたほうは、そこが違っていた。

```{.prolog filename="第01回の事実"}
drinks(aoi, cocoa).
```

「誰が」「何を」が、名前の中ではなく**引数**として外に出ている。

::: {.term}
[**述語**](glossary.md#predicate)は、第01回で見たとおり
「引数を受け取って、真か偽かが決まる関係の名前」である。
`drinks(aoi, cocoa)` の `drinks` が述語、`aoi` と `cocoa` が引数である。

真偽変数の代わりに、この述語と引数で書く論理を**述語論理**という。
第01回から書いてきたものは、はじめからこちら側に立っている。
:::

引数を外に出しておくと、その位置に**変数**を置ける。次の節がそれである。

## 変数と「すべて・ある」 {#quantifiers}

### 変数を入れると文が開く {#open-formulas}

`drinks(aoi, cocoa)` は真か偽かが決まる。知識ベースにあるので真である。

`drinks(X, cocoa)` はどうか。**これだけでは真偽が決まらない。**
`X` が誰なのかが決まっていないからである。

::: {.term}
**値の決まっていない変数**を含んでいて、そのままでは真偽が決まらない文を**開いた文**という。
`drinks(X, cocoa)` の `X` に `aoi` を入れれば真、`hikaru` を入れれば偽になる。

ここでいう「文」は日常語の意味である。厳密な言い分けは
[論理の入門(2)](logic-semantics.md#syntax)にある。
:::

開いた文を閉じる（真偽が決まる形にする）方法は2つある。

1. 変数に値を入れる。Prolog がクエリの答えを出すときにしているのがこれである
2. 「すべての `X` について」または「ある `X` が存在して」で覆う

2つめが次の節である。

### 「すべての X について」と「ある X が存在して」 {#forall-exists}

::: {.term}
- **全称量化**（$\forall$）… すべての対象について成り立つ、という覆い方
- **存在量化**（$\exists$）… 成り立つ対象が少なくとも1つある、という覆い方
- この2つをまとめて**量化子**と呼ぶ
:::

読み方だけ表にしておく。

| 記号 | 読み | 言い換え | この科目で出てきた形 |
|---|---|---|---|
| $\forall X.\ P(X)$ | すべての $X$ について $P(X)$ | どれを取っても成り立つ | [第03回](../sessions/03-minizinc-sudoku.md)の「すべての行について相異なり」 |
| $\exists X.\ P(X)$ | ある $X$ が存在して $P(X)$ | 少なくとも1つある | [第01回](../sessions/01-prolog-intro.md)のクエリ `drinks(X, cocoa)` |

::: important
**記号はここまでにする。**以降**このページでは** $\forall$ と $\exists$ を使わない。
このページで必要なのは「すべて」と「ある」の2つを**区別して読める**ことだけであり、
記号で書けることではない。第03回の note で「読めなくてよい」と書いたのと同じ立場である。

記号を使った**定義**のほうは[論理の入門(2)](logic-semantics.md)が引き受ける。
:::

Prolog のクエリは「ある」の側である。`drinks(X, cocoa)` と問い合わせるのは
「`drinks(X, cocoa)` が成り立つ `X` はあるか」と聞くことであり、
返ってきた `X = aoi.` は**その `X` が実際にあった証拠**である。
`false.` は「そのような `X` は1つも無い」という報告になる。

### 「すべて」と「ある」を重ねると順序が効く {#nested-quantifiers}

[第08回](../sessions/08-roster-hard.md)の資格の条件を材料にする。
4人・3日の勤務表で、リーダー資格を持つのは職員Aと職員Cの2人、
夜勤は毎日1名、そして「夜勤の翌日は休み」という休息制約がある。

資格の条件は、言葉にすると2通りに読める。

- **読み方A**: **すべての日について**、**ある**資格者がその日の夜勤にいる
- **読み方B**: **ある**資格者がいて、**すべての日について**その人が夜勤にいる

違うのは「ある資格者」を**いつ選ぶか**である。
A では日ごとに選び直してよい。1日目は職員A、2日目は職員C、でかまわない。
B では日より先に一人に決まり、その同じ人が3日とも夜勤に入る。
**「すべて」と「ある」を重ねたときは、順序を入れ替えると別の条件になる。**
B が成り立てば A も成り立つが、逆は成り立たない。

MiniZinc に写すと、順序がそのまま入れ子の順序として見える。
`exists` は[第04回](../sessions/04-sudoku-data-uniqueness.md)、
`where` で絞る書き方は第08回で使ったものである。

```{.minizinc filename="読み方A"}
constraint forall(d in DAYS)(
  exists(s in STAFF where leader[s])( roster[s, d] = night )
);
```

第08回が書いた `count(..., night) >= 1` は、これと同じ条件である。
「資格者の夜勤が1人以上いる」と「夜勤に入っている資格者がある」は同じことを言っている。

```{.minizinc filename="読み方B"}
constraint exists(s in STAFF where leader[s])(
  forall(d in DAYS)( roster[s, d] = night )
);
```

確かめてみる。第08回の完成モデルの資格の制約だけを差し替え、
`small.dzn`（4人・3日）で実行する。以下は既定のソルバー（Gecode）の実測である。

読み方Aは表が出る。

```solver
        1日 2日 3日
職員A   夜  休  夜
職員B   休  日  日
職員C   日  夜  休
職員D   日  日  日
日勤    2   2   2
夜勤    1   1   1
資格者  1   1   1
```

第08回の書き方で出るものと同じ表である。全部の解を出させると6通りで、これも第08回と一致する。

読み方Bに差し替えると、解が消える。

```solver
=====UNSATISFIABLE=====
```

同じ一人が3日とも夜勤に入らなければならないが、
休息制約「夜勤の翌日は休み」がそれを禁じている。
休息制約を外して実行し直すと解は出る（職員Aが3日とも夜勤に入る表になる）。

つまりこの `=====UNSATISFIABLE=====` は、**順序を入れ替えたせいで条件が強すぎた**
という報告である。[第05回](../sessions/05-sat-dependencies.md)に書いたとおり、
UNSAT は答えの一種であって、プログラムが壊れたという意味ではない。

**順序で意味が変わるのはなぜか**、その理由を定義から示したものが
[論理の入門(2) の「定義どおりに評価してみる」](logic-semantics.md#order)にある。
「すべて」と「ある」を式として書き、この勤務表の上で1行ずつ評価して真偽を出している。

3重以上の入れ子と、否定を混ぜた場合は扱わない（→[扱わないこと](#not-covered)）。

## 本科目の道具との対応 {#tools}

ここからが本題である。3つの道具で「すべて」と「ある」がどこに現れるかを見る。

### Prolog の規則は「すべての〜について、ならば」 {#prolog-rules}

第01回で書いた規則を持ってくる。

```{.prolog filename="第01回の規則"}
teammate(X, Y) :- club(X, C), club(Y, C).
```

これを言葉に戻すと、次のようになる。

> **すべての** `X`・`Y`・`C` について、
> `club(X, C)` かつ `club(Y, C)` **ならば** `teammate(X, Y)` である。

規則に書いた変数は、**書かなくても「すべての」で束ねられている**。
1行しか書いていないのに、誰について問い合わせても答えが返るのはこのためである。

確かめてみる。実行ページで第01回の知識ベース（4人分の `drinks` と `club`、
上の規則）を読み込み、クエリ欄に `teammate(kaede, Y)` と書いて「実行」を押す
（[事実と規則のサンプルを読み込んだ状態で実行ページを開く](../../tools/prolog/?example=facts)）。

```text
解 1: Y = aoi.
解 2: Y = kaede.
false.
```

`kaede` の teammate は**1行も書いていない**。それでも答えが出るのは、
あの1行の規則が `kaede` についても成り立っているからである。
`teammate(hikaru, Y)` に変えれば `解 1: Y = hikaru.` の1つだけになる。
テニス部が `hikaru` ひとりだからで、規則の側は何も変わっていない。

::: note
規則の変数が「すべて」、クエリの変数が「ある」である。同じ `X` という見た目でも、
**書く場所によって覆われ方が違う**。
「ならば」を Prolog だけ右から左に書くことについては、
[用語集の道具ごとの記法対応](glossary.md#道具ごとの記法対応)にまとめてある。
:::

### 単一化のもう一歩 {#unification-and-variables}

第02回では[単一化](glossary.md#unification)を
「等しくできるか調べて、できるなら結びつける」と書いて打ち切った。ここで一歩だけ進める。

規則の変数が「すべての」で束ねられているということは、処理系はその変数を
**どの対象に読み替えてもよい**ということである。
単一化は、**その読み替えを1つ選ぶ**操作である。
`teammate(kaede, Y)` を問い合わせたとき、処理系は規則の `X` を `kaede` に読み替え、
`C` と `Y` はまだ空のまま先へ進む。

代入と違うのは目的である。値を1つ決めることが目的ではなく、
**あり得る読み替えの中から、条件が成り立つものを見つける**ことが目的である。
だから成り立たなければ読み替えを取り消して別のものを試す。
これが第02回の[バックトラック](glossary.md#backtracking)である。

### MiniZinc の `forall` は「すべて」そのもの {#minizinc-forall}

[第03回](../sessions/03-minizinc-sudoku.md)で書いた行の制約を再掲する。

```{.minizinc filename="第03回の行の制約（再掲）"}
constraint forall(r in ROWS)( all_different([ x[r, c] | c in COLS ]) );
```

`forall(r in ROWS)` が「すべての行 `r` について」である。
同じ回の note に置いた数式と、語順まで同じ形をしている。

Prolog との違いは、**範囲がその場に書いてある**ことである。
`ROWS` は `1..4` と決まっているので、MiniZinc はこの1行を
「4本の制約を並べたもの」に展開できる。
逆にいえば、範囲を書かない「すべて」は MiniZinc では書けない。

### Z3 の `Implies` と、量化子を書かない理由 {#z3-implies}

第05〜06回では `forall` に当たるものを書かなかった。
「すべての依存の組について」は、Python の `for` 文で式を並べて表した。

```{.z3py filename="すべての依存の組について"}
from z3 import *

use = {name: Bool(f"use_{name}") for name in ["app", "gui", "net"]}
deps = [("app", "gui"), ("gui", "net")]

s = Solver()
s.add(use["app"])
for a, b in deps:                       # 「すべての依存の組について」
    s.add(Implies(use[a], use[b]))

print(s.assertions())
print(s.check())
```

```solver
[use_app,
 Implies(use_app, use_gui),
 Implies(use_gui, use_net)]
sat
```

`s` に入ったのは「すべての〜について」という1つの式ではなく、
**展開されたあとの3つの式**である。
組が有限で、しかも手元に列挙してあるのだから、これで足りている。

::: note
Z3 には量化子を書く `ForAll` / `Exists` もある。
「すべての整数 $n$ について」のように**対象が無限にある**ときには、
列挙できないのでこれが要る。
この科目で扱う問題は対象が有限で、数え上げられるものばかりなので使わない。
**名前だけ知っておけばよい。**
:::

### 「すべて・ある」の道具別対応 {#tool-table}

| 言いたいこと | Prolog（第01〜02回） | MiniZinc（第03〜04・07〜10回） | Z3Py（第05〜06回） |
|---|---|---|---|
| すべての … について | 規則の変数（書かずに束ねられている） | `forall(r in ROWS)( … )` | Python の `for` で式を並べる |
| ある … が存在して | クエリ（答えが出れば、それが存在の証拠） | `exists(s in STAFF)( … )`（制約の中で）／解が1つ出ること（問題全体で） | `Or(...)` に並べる（制約の中で）／`sat` と `model()`（問題全体で） |
| そのような … は無い | `false.` | `=====UNSATISFIABLE=====` | `unsat` |

::: note
この表は**「すべて・ある」の段**だけを並べたものである。
「かつ・または・でない・ならば」の段は
[用語集の道具ごとの記法対応](glossary.md#道具ごとの記法対応)にある。
2つの表は**段が違うだけで、見ている対象は同じ**である。

「ある … が存在して」の行だけ**2段に分かれる**。制約の中に書く「ある」（上の
[読み方A](#nested-quantifiers)の `exists`）と、問題全体として解があること（`sat`）は別の段である。
Prolog のクエリは、問い合わせが「ある」を書く場所でもあり、答えが返ることが存在の証拠でもあるので、
1つの欄で両方の段を兼ねている。
:::

  「この式からこの式が導ける」を人が示す手続きは、この科目の対象ではない
- **3重以上の入れ子、否定と量化子の組み合わせ** → 扱わない。
  2重までは[「すべて」と「ある」を重ねると順序が効く](#nested-quantifiers)にある

  [第05回](../sessions/05-sat-dependencies.md)と[SAT・SMT 概説](logic-sat-smt.md)にある。
