::: note

ソルバーに解かせる」ところまでである。CNF への変換や低水準の符号化は、
**もっと知りたい人向け**の補足として置いてある。

## 命題論理の記号

**命題変数**とは、真か偽のどちらかになる変数である。
「パッケージ `editor` を導入する」のように、成り立つ・成り立たないが決まる文に対応させる。

| 記号 | 読み | Z3Py | 意味 |
|---|---|---|---|
| $\neg p$ | 否定・でない | `Not(p)` | $p$ が偽のとき真 |
| $p \land q$ | 論理積・かつ | `And(p, q)` | 両方が真のとき真 |
| $p \lor q$ | 論理和・または | `Or(p, q)` | 少なくとも一方が真のとき真 |
| $p \to q$ | 含意・ならば | `Implies(p, q)` | $p$ が真で $q$ が偽のときだけ偽 |

否定・論理積・論理和は論理回路の NOT・AND・OR と同じである。
**含意だけは回路に対応するものが無い**ので、真理値表で確かめておく。

## 真理値表

変数の値の組み合わせをすべて並べ、式の値を書き出した表である。
変数が $n$ 個なら行は $2^n$ 行になる。

| $p$ | $q$ | $\neg p$ | $p \land q$ | $p \lor q$ | $p \to q$ |
|---|---|---|---|---|---|
| 偽 | 偽 | 真 | 偽 | 偽 | **真** |
| 偽 | 真 | 真 | 偽 | 真 | **真** |
| 真 | 偽 | 偽 | 偽 | 真 | **偽** |
| 真 | 真 | 偽 | 真 | 真 | **真** |

::: important
$p \to q$ は「$p$ が偽ならいつでも真」である。
「`editor` を入れるなら `parser` も入れる」という条件は、
**`editor` を入れない場合には何も要求しない**。ここが直感とずれやすい。
:::

含意は否定と論理和で書き直せる。この形は符号化のときに何度も使う。

$$p \to q \;\equiv\; \neg p \lor q$$

真理値表の右2列を見比べると、4行とも値が一致していることが確かめられる。

## 充足可能性・SAT・UNSAT

::: {.term}
- **充足可能**（satisfiable）: すべての式を同時に真にする値の割り当てが**存在する**
- **SAT**: 充足可能だと分かった状態。ソルバーは割り当ての例（モデル）を返す
- **UNSAT**: どう値を選んでも同時には満たせないと分かった状態
:::

UNSAT は**答えの一種**であって、モデルが壊れているという意味ではない。
「この条件では両立しない」ことが証明された、と読む。

たとえば $p \land \neg p$ は UNSAT である。
真理値表を書けば、どの行でも式が偽になることが分かる。

## CNF: ソルバーが受け取る形

**CNF**（連言標準形）とは、
「または」で結んだ塊（**節**）を「かつ」で並べただけの形である。

$$(\neg p \lor q) \land (\neg q \lor r) \land (p \lor r)$$

- 節: $\neg p \lor q$ のような「または」だけでできた部分
- リテラル: $p$ または $\neg p$ のような、変数か変数の否定

SAT ソルバーの入力はこの形と決まっている。
どんな論理式も CNF に書き直せるので、これで一般性を失わない。

```{.text filename="含意を CNF にする"}
editor → parser
  ≡ ¬editor ∨ parser        （節が1つ）

editor → (parser ∧ logger)
  ≡ (¬editor ∨ parser) ∧ (¬editor ∨ logger)     （節が2つ）
```

::: note
**Z3 を使うときに CNF へ手で直す必要はない。**
`Implies` や `And` をそのまま書けば、Z3 が内部で変換する。
ここで知っておきたいのは「最終的にはこの形になっている」ということだけである。
:::

## 代表的な Boolean 符号化

「選択肢のうちどれを選ぶか」を真偽変数で表すときの定型である。
$x_1, \dots, x_n$ を選択肢に対応する命題変数とする。

### 少なくとも一つ（at least one）

$$x_1 \lor x_2 \lor \dots \lor x_n$$

```{.z3py filename="少なくとも一つ"}
s.add(Or(xs))
```

### 高々一つ（at most one）

どの2つも同時には真にならない、と書く。節の数は組み合わせの数になる。

$$\bigwedge_{i < j} (\neg x_i \lor \neg x_j)$$

```{.z3py filename="高々一つ"}
for i in range(len(xs)):
    for j in range(i + 1, len(xs)):
        s.add(Or(Not(xs[i]), Not(xs[j])))
```

### ちょうど一つ（exactly one）

上の2つを並べるだけである。

```{.z3py filename="ちょうど一つ"}
s.add(Or(xs))                                   # 少なくとも一つ
for i in range(len(xs)):
    for j in range(i + 1, len(xs)):
        s.add(Or(Not(xs[i]), Not(xs[j])))       # 高々一つ
```

### 「両立しない」

2つが同時に成り立ってはいけない、という条件である。

$$\neg (x \land y) \;\equiv\; \neg x \lor \neg y$$

```{.z3py filename="両立しない"}
s.add(Or(Not(x), Not(y)))
```

グラフ彩色では、辺で結ばれた2地区が同じ色にならないことを
この形で書く（[グラフ彩色の3つの表現](graph-coloring.md)）。

### 「一方を選ぶなら他方も要る」

$$x \to y \;\equiv\; \neg x \lor y$$

```{.z3py filename="依存"}
s.add(Implies(x, y))
```

## SAT ソルバーの処理イメージ

内部の仕組みは科目の対象ではないが、
**総当たりではない**ことだけは知っておくと、結果の見え方が変わる。

1. まだ値が決まっていない変数を1つ選び、真か偽を仮に決める。
2. その決定から**必然的に決まる**変数を芋づる式に埋める
   （$\neg p \lor q$ があって $p$ を真にしたなら、$q$ は真に決まる）。
3. どこかの節がすべて偽になったら行き詰まりである。
   **なぜ行き詰まったか**を新しい節として覚え、決定をさかのぼってやり直す。
4. すべての変数が埋まれば SAT、行き詰まりの理由を積み上げて
   「どうやっても無理」と示せたら UNSAT である。

3 の「行き詰まりの理由を覚える」があるので、同じ失敗を繰り返さない。
変数が数万個あっても現実的な時間で解けることがあるのはこのためである。
一方で、**規模が少し増えただけで急に遅くなる問題もある**。
速さの予想は当たらないことがある、と思っておく。

## 全部は満たせないとき（MaxSAT）

SAT ソルバーが返すのは「全部の節を満たす割当てがあるか」だけである。
現実には、**全部は満たせないと分かっていて、なるべく多く満たしたい**ことがある。
勤務表の希望休がその例である（[第09回](../sessions/09-roster-soft.md)）。

このとき節を2種類に分ける。

- **必ず満たす節**（ハード節）… 破ったら答えとして認めない
- **なるべく満たす節**（ソフト節）… 破ってもよいが、破った数を数える

「ハード節をすべて満たし、破るソフト節の重みの合計を最小にする」問題を
**MaxSAT** と呼ぶ。重み付きの版は重み付き MaxSAT である。

[第09回](../sessions/09-roster-soft.md)で書く勤務表の重み付き和は、**これと同じ形**である。
ただし MiniZinc の `solve minimize` で書くので、
CNF に直したり MaxSAT ソルバーを呼んだりはしない。
**同じ考え方が別の書き方で現れている**、と見ておけばよい。

## SMT: 背景理論を足す

SAT は真偽値しか扱えない。「バージョン番号が 2 以上」のような条件を
真偽変数だけで書くと、変数の数が跳ね上がって読みにくくなる。

**SMT**（satisfiability modulo theories）は、
命題論理の骨組みに**背景理論**を組み合わせたものである。
背景理論とは「整数の大小」「実数の四則」のような、
値の世界ごとの決まりごとを担当する部品だと考えればよい。

```{.text filename="処理イメージ"}
  論理の骨組み            背景理論の担当
  ────────────            ──────────────
  (A ∨ B) ∧ ¬C     ←→     A: v_editor ≥ 2
                          B: v_editor = 0
                          C: v_parser > 5
```

1. 論理の骨組みだけを見て、$A$ を真、$B$ を偽、… と仮に決める。
2. その組み合わせが**整数の世界で成り立つか**を背景理論の担当が調べる。
3. 成り立たなければ「$A$ と $C$ は同時に真にできない」と骨組み側へ伝え、
   骨組み側がやり直す。

この往復をするので、`v_editor >= 2` のような式を**そのまま書ける**。
これが[第06回](../sessions/06-smt-versions.md)で整数変数を使う理由である。

## 型の選び方（Z3）

Z3 の変数にはいくつかの型がある。この科目で使うのは `Bool` と `Int` だけだが、
自由課題のために選び方の目安を挙げておく。

| 型 | 表せるもの | 選ぶ目安 | この科目 |
|---|---|---|---|
| `Bool` | 真・偽 | **入れる／入れない**、**選ぶ／選ばない**の2択。選択肢が少数で、順序に意味が無いとき | 第05回 |
| `Int` | 整数（上限・下限なし） | **大小や順序に意味がある**数。個数、番号、バージョン、時刻 | [第06回](../sessions/06-smt-versions.md) |
| `Real` | 実数 | 割合・重み・座標など、整数に丸めると意味が変わるもの | 使わない |
| `BitVec` | 決まった幅のビット列 | 機械語のレジスタ、桁あふれの再現、ビット演算そのものが対象のとき | 使わない |

判断に迷ったときの順序は次のとおりである。

1. **2択で表せるか**を先に考える。表せるなら `Bool` にする。
   ソルバーが最も得意な形であり、モデルも読みやすい。
2. 選択肢が多い、または**大小の比較を書きたい**なら `Int` にする。
   「ちょうど一つ」の節を大量に並べるより短く書ける。
3. 端数が意味を持つなら `Real` にする。
   ただし「解が存在するか」の判定が急に難しくなることがある。
4. `BitVec` は、ビット幅と桁あふれの挙動そのものを再現したいときだけ使う。

::: warning
同じ問題を `Bool` で書くか `Int` で書くかは**設計の判断**であり、
どちらか一方が常に正しいわけではない。
第05回と第06回で同じ依存関係の問題を両方の型で書くのは、この違いを体験するためである。
:::
