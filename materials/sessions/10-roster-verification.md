# 第10回 勤務表: 検証と性能評価

::: {.important}
**この回の最短ルート**（授業の100分で最低限これだけ終える）

1. **読む**: 「概念と構文」の *モデルの外側で確かめる* ・ *検査関数の形* ・ *正常例と反例* →「小さな実行例」
2. **やる**: 必須演習「資格の検査を書き、正常例と反例を自動判定する」（`verify_roster.py` の `TODO(1)`）
3. **確かめる**: 「完了チェック」の上から4項目
4. **「速さを測る」は1設定だけでよい**。60秒待つ実験は自習に回してよい

## この回の目標

この回を終えると、次のことができる。

- ソルバーが返した勤務表を、モデルとは別のプログラムで検査できる
- 正常例が合格し、反例が不合格になることを自動で判定できる
- 制約を1つ外したモデルの出力を検証器にかけ、どの検査が反応したかを言える
- 入力規模と実行時間の関係を測って記録し、正しさと速さを分けて評価できる

## 今回解く問題

第09回の最後に、こう書いた。

> 資格制約を書き忘れていたら、資格を無視した中での最適解が返る。
> `!=` を `=` と書き間違えていたら、逆の意味で最適化された表が返る。
> **どちらの場合も、ソルバーはエラーを出さない。**

ここまで3回、勤務表が正しいかどうかを**目で見て**確かめてきた。
4人・3日ならそれで足りる。8人・7日でもぎりぎり数えられる。
8人・14日では、もう無理である。

::: {.important}
**ソルバーは「書いたモデル」については完璧だが、「書きたかったモデル」については何も知らない。**

`=====UNSATISFIABLE=====` も出ないし、警告も出ない。
制約を1本書き忘れたモデルは、**その1本が無い世界の正解**を静かに返す。
:::

この回でやることは3つである。

1. モデルとは別に書いた Python のプログラムで、返ってきた表を検査する
2. わざと壊した表を食わせて、検査が**見つけられること**を確かめる
3. 7日を14日に増やして実行時間を測り、記録する

::: {.discuss}
「モデルが正しいかどうかを、モデル自身に確かめさせればよいのではないか」

- `constraint` をもう1本足して「この表は資格制約を満たす」と書いたら、何が起きるか。
- 検算を同じ人が同じ方法でやり直すことに、どれだけの意味があるか。
- テストと本体を別の人が書く現場があるのはなぜか。
:::

## 変数・定義域・制約・目的へ分解

[定式化の7手順](../references/modeling-steps.md)の最後の1つが、この回の中身である。
表の中身は第08回・第09回から**何も変わらない**。

| 語 | この問題では |
|---|---|
| 変数 | 職員 `s` の `d` 日目の勤務（第08回と同じ） |
| 定義域 | 日勤・夜勤・休みの3つ（第08回と同じ） |
| 制約 | 必要人数・資格・休息（第08回と同じ） |
| 目的 | 希望休違反と勤務の偏りの重み付き和（第09回と同じ） |
| **検証** | **返ってきた表を、上の4行とは別に書いたプログラムで確かめる** |

書く場所が変わっただけに見えるが、**書く人と書く言語が変わる**ことが要点である。

## 概念と構文

### モデルの外側で確かめる

::: {.term}
[**独立した検証**](../references/glossary.md#independent_verification)とは、
モデルの外側で解の正しさを確かめることである。
:::

[第03回](03-minizinc-sudoku.md)・[第04回](04-sudoku-data-uniqueness.md)で
数独の盤面を `check_sudoku.py` にかけたときと同じ考え方である。
違うのは、今回は**検査する項目を自分で書く**ところである。

なぜ別のプログラムにするのか。理由は3つある。

| 理由 | 中身 |
|---|---|
| 同じ誤りを繰り返さない | MiniZinc で `!=` を `=` と書き間違えた人は、MiniZinc で書き直しても同じ間違いをする。**言語も書き方も変える**と、同じ誤りが2回起きにくい |
| 制約の書き忘れが見える | モデルに無い制約は、モデルの中では検査できない。外側からなら「資格の検査」を独立に足せる |
| 何度でも自動で回せる | データやモデルを直すたびに、目で数え直さなくてよい |

::: {.warning}
**検証器も人が書いたプログラムである。** 検証器のほうが間違っていることもある。
だから「正常例が合格すること」だけでは足りない。
**反例で不合格になること**まで確かめる。
:::

### 機械可読な出力

::: {.term}
[**機械可読な出力**](../references/glossary.md#machine_readable_output)とは、
別のプログラムが読める形で解を出すことである。
:::

第09回の配布モデルは、人が読む表のほかに `#` で始まる行を出していた。

```solver
        1日 2日 3日   勤務  夜勤
職員A   *休  夜 *休    1     1
職員B    日  日  日    3     0
職員C    夜 *休  夜    2     2
職員D    日  日  日    3     0
希望休違反 = 0   勤務日数の偏り = 2   夜勤回数の偏り = 2   目的関数 = 4
#size 4 3
#shift A ONO
#shift B DDD
#shift C NON
#shift D DDD
#value pref 0
#value unfair 2
#value night_unfair 2
#value penalty 4
```

上半分は人のため、下半分はプログラムのためである。

| 行 | 中身 |
|---|---|
| `#size <人数> <日数>` | 表の大きさ。読み込んだ行数と食い違えば、途中が欠けている |
| `#shift <名前> <D/N/O の並び>` | 1人ぶんの勤務。`D` が日勤、`N` が夜勤、`O` が休み |
| `#value <名前> <整数>` | モデルが計算したペナルティの各項 |

`#size` と `#shift` は、第09回の TODO が未記入でも出る。
`#value` の4行は TODO を埋めてコメントを外したあとだけ出る。
検証器は `#value` が**無くても動く**（ハード制約の3項目だけを検査する）。

::: {.warning}
**整形した表を読ませようとしない。**

`職員A   *休  夜 *休` を読むプログラムは、全角スペースの数や `*` の位置に
振り回される。**受け渡し専用の行を別に出すほうが、桁違いに楽である。**

自由課題で自分のモデルを書くときも、同じ手を使ってよい。
`output` に1行足すだけで、検証がずっと書きやすくなる。
:::

### 検査関数の形

配布する `verify_roster.py` は、素の Python だけでできている。
検査は「見つけた違反を日本語で並べたリストを返す関数」の形に揃えてある。

```{.python filename="verify_roster.py（必要人数の検査）"}
def check_coverage(rows: list[str], data: dict) -> list[str]:
    """必要人数: どの日も日勤・夜勤がちょうど決まった人数になっているか。"""
    bad = []
    for d in range(data["nd"]):
        col = [r[d] for r in rows]               # d 日目の列（全職員ぶん）
        if col.count(DAY) != data["need_day"][d]:
            bad.append(f"{d + 1}日目の日勤が {col.count(DAY)} 名（必要 {data['need_day'][d]} 名）")
        if col.count(NIGHT) != data["need_night"][d]:
            bad.append(f"{d + 1}日目の夜勤が {col.count(NIGHT)} 名（必要 {data['need_night'][d]} 名）")
    return bad
```

- `rows` は `#shift` の行から作った文字列の並び（`["ONO", "DDD", ...]`）である
- `data` は `.dzn` から拾った値（`need_day` や `leader`）である
- 返り値が**空のリスト**なら、その検査は通ったという意味である

**違反の件数ではなく、違反の説明を返す**ようにしてある。
「3件ありました」より「1日目の日勤が1名（必要2名）」のほうが直せる。

::: {.note}
`rows[s][d]` は職員 `s` の `d` 日目である。
MiniZinc の `roster[s, d]` とまったく同じ並びだが、
**Python の添字は 0 から始まる**。日付を表示するときに `d + 1` としているのはこのためである。
:::

### 正常例と反例

::: {.term}
[**正常例と反例**](../references/glossary.md#positive_and_negative_cases)とは、
通るはずの例と、違反を含んでいる例である。
:::

演習ファイルの `samples/` には、8本の出力が入っている。

| ファイル | 中身 | 期待 |
|---|---|---|
| `good-small.txt` | 4人・3日の最適解 | 合格 |
| `good-week.txt` | 8人・7日の最適解 | 合格 |
| `broken-coverage.txt` | 1日目の日勤が1名（必要2名） | 不合格 |
| `broken-qualification.txt` | 夜勤に入るのが資格を持たない職員だけ | 不合格 |
| `broken-rest.txt` | 夜勤の翌日が日勤 | 不合格 |
| `broken-value.txt` | 表は制約を満たすが `#value pref` の値が違う | 不合格 |
| `dropped-qualification.txt` | 資格制約を外したモデルの実際の出力 | 不合格 |
| `dropped-rest.txt` | 休息制約を外したモデルの実際の出力 | 不合格 |

`broken-` の4本は、**1種類の違反だけ**を含むように作ってある。
どの検査関数が反応したかが1対1で分かる。

## 小さな実行例

演習ファイルのディレクトリで、正常例を検査する。

```console
$ python3 verify_roster.py samples/good-small.txt small_pref.dzn
```

```solver
合格
 (未実装) 資格の検査（TODO(1)）
 (未実装) 希望休違反の数え上げ（TODO(2)）
```

`(未実装)` の2行は、**まだ書かれていない検査がある**という知らせである。
書き終えると出なくなる。

次に、壊した表を検査する。

```console
$ python3 verify_roster.py samples/broken-coverage.txt small_pref.dzn
```

```solver
不合格
 - 1日目の日勤が 1 名（必要 2 名）
 (未実装) 資格の検査（TODO(1)）
 (未実装) 希望休違反の数え上げ（TODO(2)）
```

**どこがどう悪いかを名指しする。** これが「合っている／間違っている」だけの
判定との違いである。

同梱の8本をまとめて判定することもできる。

```console
$ python3 verify_roster.py --samples
```

```solver
good-small.txt                   期待 合格 / 結果 合格  期待どおり
good-week.txt                    期待 合格 / 結果 合格  期待どおり
broken-coverage.txt              期待 不合格 / 結果 不合格  期待どおり
      - 1日目の日勤が 1 名（必要 2 名）
broken-qualification.txt         期待 不合格 / 結果 合格  ← 期待と違う
broken-rest.txt                  期待 不合格 / 結果 不合格  期待どおり
      - 職員A の 1日目が夜勤なのに翌日が休みでない
broken-value.txt                 期待 不合格 / 結果 合格  ← 期待と違う
dropped-qualification.txt        期待 不合格 / 結果 合格  ← 期待と違う
dropped-rest.txt                 期待 不合格 / 結果 不合格  期待どおり
      - 職員A の 1日目が夜勤なのに翌日が休みでない

まだ書かれていない検査: 資格の検査（TODO(1)）
まだ書かれていない検査: 希望休違反の数え上げ（TODO(2)）
期待と違う行がある。検査関数を見直すこと。
```

（違反の行は長いので、上では各ファイル1行だけを載せてある。
実際には見つかった違反が全部並ぶ。）

配ったままの状態では、**3行が「期待と違う」になる**。
資格の検査と希望休違反の数え上げが空だからである。
その2つを埋めるのが、この回の必須演習と標準演習である。

::: {.note}
`verify_roster.py` は**終了コード**も返す。合格なら `0`、不合格なら `1` である。
`--samples` は全部が期待どおりなら `0` を返す。
自由課題で「検証を自動で回す」と書くときの、いちばん単純な形である。
:::

## 予想してから試す

::: {.predict}
`samples/dropped-qualification.txt` は、第09回の配布モデルから
**資格制約の1本だけを消して**実行した結果である。

```{.minizinc filename="消した1本"}
constraint forall(d in DAYS)(
  count([ roster[s, d] | s in STAFF where leader[s] ], night) >= 1
);
```

この出力を、**資格の検査を書き終えた**検証器にかけると何が出ると思うか。

1. 何も出ない（合格する）
2. 資格の違反だけが出る
3. 資格・必要人数・休息の3種類とも出る

消したのは資格制約だけである。ほかの2本は残っている。
:::

答えは 2 である。資格の検査を書き終えると、次のように出る。

```solver
不合格
 - 4日目の夜勤に資格者がいない
 - 7日目の夜勤に資格者がいない
 (未実装) 希望休違反の数え上げ（TODO(2)）
```

必要人数と休息の行は1つも出ない。**残した制約はソルバーが守っているからである。**

::: {.important}
**消した制約と、反応した検査が1対1で対応している。**

これが検証器を持つことの効き目である。
「どこかがおかしい」ではなく「**資格の制約が効いていない**」まで分かる。

逆に言えば、**検査を書いていない条件については何も分からない**。
検証器が合格を返したことは、「書いた検査は通った」以上の意味を持たない。
:::

### 資格の検査を書き、正常例と反例を自動判定する


どの日も、夜勤に入る人のうち1人以上がリーダー資格を持っていなければならない。

**その3**: 次の表を埋める。

| 入力 | 組にする `.dzn` | 期待 | 結果 | 終了コード |
|---|---|---|---|---|
| `samples/good-small.txt` | `small_pref.dzn` | 合格 | | |
| `samples/broken-qualification.txt` | `small_pref.dzn` | 不合格 | | |
| `samples/dropped-qualification.txt` | **`week_pref.dzn`** | 不合格 | | |

`dropped-qualification.txt` だけ 8人・7日なので、渡す `.dzn` が違う。
**出力とデータは常に組で扱う。**

終了コードは、実行した直後に見られる。**見る書き方は端末によって違う。**

```console
$ python3 verify_roster.py samples/good-small.txt small_pref.dzn
$ echo $?
```

| 端末 | 直後に打つもの |
|---|---|
| macOS / Linux のシェル、Windows の Git Bash・WSL | `echo $?` |
| Windows のコマンドプロンプト（`cmd`） | `echo %ERRORLEVEL%` |
| Windows の PowerShell | `$LASTEXITCODE` |

PowerShell の `$?` は `True` / `False` を返すもので、**番号ではない**。
番号が要るときは `$LASTEXITCODE` を見る。

**完了条件**: 正常例が「合格」・終了コード `0`、
資格の反例が「不合格」・終了コード `1` になり、
不合格の行に**資格の違反だけ**が並ぶ。
そのうえで、「この検査がモデルと独立していると言えるのはなぜか」を1行で書ける。
:::

::: {.hint summary="ヒント1: どこを見るのか"}
`rows[s][d]` が職員 `s` の `d` 日目の勤務で、`"D"` `"N"` `"O"` のどれかである
（`NIGHT` という名前が `"N"` として定義してある）。

職員 `s` が資格を持つかどうかは `data["leader"][s]` で分かる。`True` か `False` である。

`check_rest` が2重のループで全マスを回っているので、書き方はそこが参考になる。
:::

::: {.hint summary="ヒント2: 数えてから比べる"}
1日ぶんの処理はこうなる。

1. その日に**夜勤**で、かつ**資格を持つ**職員が何人いるかを数える
2. 0 人なら違反である

数え方は Python の内包表記でも `for` 文でもよい。

```{.python}
n = 0
for s, r in enumerate(rows):
    if r[d] == NIGHT and data["leader"][s]:
        n += 1
```

`enumerate(rows)` は「番号と中身」を同時に取り出す。
`s` が職員の番号（0 から）、`r` がその人の `"ONO"` のような文字列である。
:::

::: {.hint summary="ヒント3: 解答"}
```{.python filename="verify_roster.py（TODO(1)）"}
def check_qualification(rows: list[str], data: dict) -> list[str]:
    bad = []
    for d in range(data["nd"]):
        n = 0
        for s, r in enumerate(rows):
            if r[d] == NIGHT and data["leader"][s]:
                n += 1
        if n < 1:
            bad.append(f"{d + 1}日目の夜勤に資格者がいない")
    return bad
```

`return None` の行ごと差し替える。関数の型注釈の `| None` も消してよい。

内側の `for` 文4行は、次の1行に縮めても同じ動きをする（**縮めなくてよい**）。

```{.python}
        n = sum(1 for s, r in enumerate(rows) if r[d] == NIGHT and data["leader"][s])
```

`samples/broken-qualification.txt` では3日ぶんすべてが違反になる
（資格を持つのは職員Aと職員Cだが、夜勤に入っているのは職員Bと職員Dだけである）。
:::

## 標準演習

::: {.exercise level=standard}
### 希望休違反を数え直し、値の食い違いを見つける

`# TODO(2)` にあたる `count_pref` を書く。
モデルが `#value pref` として出してきた値を**信用せず**、こちら側で数え直して比べる。

**完了条件**: `python3 verify_roster.py --samples` が
「すべて期待どおりである。」を出し、終了コードが `0` になる。
そのうえで次の2つを説明できる。

- `samples/broken-value.txt` の表は3つのハード制約をすべて満たしている。
  それでも不合格になるのはなぜか。
- `pref` の食い違いを見つけたとき、疑うべきなのはモデルと検証器のどちらか。
  **どうやって決めるか。**
:::

::: {.hint summary="ヒント1: 何を数えるのか"}
第09回で MiniZinc に書いたのと同じことを、Python で書く。

```{.minizinc filename="第09回で書いた式"}
sum(s in STAFF, d in DAYS where want_off[s, d])( bool2int(roster[s, d] != off) )
```

- `data["want_off"][s][d]` が `True` なら、職員 `s` は `d` 日目に休みを希望している
- その日が `OFF` でなければ違反1件である
- 全職員・全日を見て、件数を返す
:::

::: {.hint summary="ヒント2: 書けたのに何も変わらないとき"}
`count_pref` は `int` を返す。`None` を返したままだと、
検証器は「まだ書かれていない」と判断して `pref` と `penalty` の
突き合わせを**飛ばす**。

`return` を書き忘れていないか、`print` で済ませていないかを確かめる。
:::

::: {.hint summary="ヒント3: broken-value.txt には何が起きているか"}
`broken-value.txt` は、第09回の「よくある誤り」に載っていた
**`bool2int` の中を `= off` と書いた**モデルの出力である。
「希望休の日に休んでいる数」を数えてしまっているので、
本当は3件ある違反を 0 件と報告する。

表そのものはハード制約を満たしている。
**壊れているのは表ではなく、モデルが計算した数のほうである。**
検証器は `pref` と、それを使う `penalty` の2つで食い違いを報告する。
:::

## 制約を1つずつ足す

::: {.term}
[**段階的テスト**](../references/glossary.md#incremental_testing)とは、
制約を1つずつ足しながら、その都度期待どおりかを確かめる進め方である。
:::

第08回では、制約を1本ずつ足しながらモデルを育てた。
検証器があると、**その各段階で何が起きたかを言葉で確かめられる**。

`roster_soft.mzn` のハード制約を上から順に有効にしていくと、
`week_pref.dzn` では次のようになった（`solve satisfy;` で実行した）。

| 有効な制約 | 検証器が出す違反の種類 |
|---|---|
| なし | 必要人数・資格 |
| 必要人数だけ | 資格・休息 |
| 必要人数＋資格 | 休息 |
| 3本とも | なし（合格） |

**期待どおりに減っていくこと**を1段階ずつ確かめる。
消したはずの違反がまだ出るなら、制約の書き方が意図と違っている。

::: {.note}
**1行目に注目する。制約が1本も無いのに、休息の違反が出ていない。**

制約が無いとソルバーは**全員が全日とも日勤**の表を返す（第08回で見たとおりである）。
夜勤が1つも無いので、「夜勤の翌日は休み」は自動的に満たされてしまう。

**検査が反応しないことは、条件が守られていることを意味しない。**
その条件が試されるような入力が来ていないだけかもしれない。
反例をわざわざ用意するのは、このためである。
:::

もう一方の向きも試せる。**制約を足しすぎると解が消える。**

```{.dzn filename="small_pref.dzn（1日目と2日目の必要人数を1名ずつ増やす）"}
need_day   = [  3,  3,  2 ];
```

```solver
=====UNSATISFIABLE=====
```

1日目は日勤3名と夜勤1名で職員4名を使い切る。
夜勤に入った人は2日目が休みなので、2日目に使えるのは3名しかない。
ところが2日目も4名要る。**この2つは同時に成り立たない。**

第08回の「予想してから試す」で見たのと同じ形である。
必要人数だけを見ても、休息制約だけを見ても矛盾は無い。
**組み合わさったときに解が消える。**

::: {.note}
**テストには2つの向きがある。**

| 向き | 確かめること |
|---|---|
| 通るはずの入力 | 解が返り、検証器が合格を出す |
| 通らないはずの入力 | `=====UNSATISFIABLE=====` になる |

片方だけでは足りない。制約が**弱すぎる**と前者しか見つからず、
**強すぎる**と後者しか見つからない。
:::

## 速さを測る

ここまでは**正しさ**の話だった。ここからは**速さ**の話である。

::: {.term}
[**正しさと速さの分離**](../references/glossary.md#correctness_vs_speed)とは、
正しいかどうかと、速いかどうかを別々に評価することである。
:::

::: {.warning}
**順番を逆にしない。** まず正しいことを確かめ、そのあとで速さを見る。
速い間違ったモデルに価値は無い。
:::

### 実行のときに見られること

::: {.term}
[**ソルバー統計**](../references/glossary.md#solver_statistics)とは、
実行時間や探索の規模を示す数値である。
:::

Playground の出力欄からは、道具立てを増やさずに次が読める。

| 見るもの | 読み取れること |
|---|---|
| `----------` の本数 | 途中経過の解が何本出たか。多いほど改善を重ねている |
| `==========` が出たか | **最適だと確かめられたか**。出なければ「まだ良い解があるかもしれない」 |
| 実行を押してから止まるまでの時間 | かかった時間。手元の時計でよい |
| 統計の表示があれば `nodes` `failures` などの数値 | 探索した場合分けの数。**規模の目安**として比較に使う |

::: {.note}
統計の表示があるかどうか、どの数値が出るかは Playground の画面によって変わる。
**無くても困らない。** この回で記録するのは
「終わったか」「何秒か」「解が何本出たか」の3つで足りる。

時間が長くて待てないときは実行を止め、
**そこまでに出た最後の解**を使う。これも立派な結果である。
:::

### 7日と14日

::: {.note}
**授業内で実行するのは1設定でよい。** 下の表の3行を全部再現する必要はない。
`week14_pref.dzn` を1回実行し、**30秒ほどで止めて**、
そのときの最後の解を使えば、この節の要点は確かめられる。
60秒待つ実験と、待ち時間ごとの値の記録は自習に回してよい。
:::

演習ファイルの `week14_pref.dzn` は、`week_pref.dzn` を2週間に伸ばしたものである。
職員・資格・必要人数の決め方はまったく同じで、**日数だけが2倍**になっている。
変えたのが日数だけなので、時間の違いを規模のせいだと言い切れる。

第09回の標準演習と同じ3項の目的関数（`w_pref = 10` / `w_fair = 1` / `w_night = 1`）で
測ると、次のようになった。

| データ | 規模 | 既定のソルバー（Gecode） |
|---|---|---|
| `small_pref.dzn` | 4人・3日 | 0.2 秒で `==========` |
| `week_pref.dzn` | 8人・7日 | 0.3 秒で `==========` |
| `week14_pref.dzn` | 8人・14日 | **60 秒待っても `==========` が出ない** |

::: {.warning}
**数値は機種と混み具合で変わる。** 桁の目安として読む。
0.3 秒が 1 秒になっても話は変わらないが、
**0.3 秒が 60 秒以上になる**ところが今回の要点である。
:::

日数が2倍になっただけで、終わるものが終わらなくなった。
表のマスの数は 56 から 112 になっただけである。
**入力が2倍でも、探す組合せは2倍では済まない。**

14日で60秒待つと、途中経過の最後の解は目的関数 25 だった。
これは**正しい解**である。ハード制約をすべて満たしている（検証器にかければ合格する）。
ただし、**これより良い表が無いとは言えていない**。

::: {.hint summary="待ち時間ごとの最良値（自習用の記録）"}
| 待った時間 | そのときの最良の目的関数 |
|---|---|
| 10 秒 | 26 |
| 30 秒 | 25 |
| 60 秒 | 25 |

30秒を過ぎても値が動いていない。**動かないことは、最適である証拠にはならない。**
:::

::: {.discuss}
実際の職場で勤務表を作るとして、次のどちらを選ぶか。

- 60秒で出た「たぶん良い表」（最適かどうかは分からない）
- 何時間かかるか分からないが「確かに最適な表」

そもそも「最適」とは、**こちらが書いた目的関数の中での**最適でしかない。
証明のために何時間も待つことに、どれだけの意味があるか。
:::

### 速くする3つの手

止まらないときに打てる手は、大きく3つある。
どれも**同じ問いに速く答える**わけではないことに注意する。

| 手 | やること | 何が変わるか |
|---|---|---|
| 打ち切る | 時間を決めて止め、最後の解を使う | 問いは同じ。**最適かどうかが分からなくなる** |
| 目的を緩める | 目的関数の項を減らす、重みを変える | **問いが変わる**。返る表も変わる |
| モデルを書き換える | 同じ問いを別の書き方にする | 問いは同じ。うまくいけば速くなる |

2つ目を実際にやってみる。3項のうち偏りの2項を落とし、
希望休違反だけを最小にする。**モデルは1文字も触らず、`.dzn` の重みだけを変える。**

```{.dzn filename="week14_pref.dzn（重みだけ変える）"}
w_pref  = 10;
w_fair  = 0;      % 1 から 0 へ
w_night = 0;      % 1 から 0 へ
```

```solver
希望休違反 = 1   勤務日数の偏り = 5   夜勤回数の偏り = 6   目的関数 = 10
==========
```

**0.6 秒で `==========` が出た。** 60秒でも終わらなかったものが、1秒足らずで終わる。

ただし、返ってきた表を見る。勤務日数の偏りは 3 から 5 へ、
夜勤回数の偏りは 3 から 6 へ増えている。

::: {.warning}
**速くなったのではない。答えている問いを易しくしたのである。**

偏りを目的から外したので、ソルバーは偏りをまったく気にしなくなった。
「速くなりました」とだけ報告するのは、事実の半分しか言っていない。

性能を報告するときは、**何を測ったか**と**何をあきらめたか**を必ず並べて書く。
:::

3つ目の「モデルを書き換える」は発展演習に置いた。
たとえば、まず希望休違反だけを最小にして最小値を求め、
その値を `constraint pref = 1;` で固定してから偏りを最小にする、という二段階に分けると、
14日でも `==========` まで到達できる（第09回の発展演習Aで書いた辞書式最適化と同じ形である）。

## 発展演習

::: {.exercise level=advanced}
### いずれか1つを選ぶ

**A. 打ち切り時間と最良値の関係を測る**（`week14_pref.dzn` で行う）

3項の目的関数のまま、10秒・30秒・60秒・（待てるなら）3分で止め、
そのときの最後の解の目的関数の値を記録する。

確かめたいこと。

- 値はどこで頭打ちになるか。時間を10倍にすると値は10分の1に近づくか。
- 途中で止めた解は、検証器にかけると合格するか。
- 「あと1分待つ価値があるか」を、どの数字を見て判断するか。

**B. 二段階に分けて最適まで到達する**（`week14_pref.dzn` で行う）

1. `w_fair = 0` `w_night = 0` で `pref` の最小値を求める（速い）。
2. その値を `constraint pref = <求めた値>;` としてモデルに足し、
   `solve minimize w_fair * unfair + w_night * night_unfair;` に差し替える。

確かめたいこと。

- `==========` は出るか。出るまでに何秒かかるか。
- 得られた目的関数の値は、Aで60秒待って得た値より良いか。
- この二段階は、3項の重み付き和と**同じ問い**に答えているか。
  違うとしたら、どういうデータで答えが分かれるか。

**C. 探索を絞る制約を足すと速くなるか**（`week14_pref.dzn` で行う）

「偏りは3以下のはずだ」と当たりを付けて、ハード制約として足してみる。

```{.minizinc filename="書きかけ"}
constraint unfair <= 3;
constraint night_unfair <= 3;
```

確かめたいこと。

- 予想どおり速くなるか。**手元で試したときは、60秒で解が1本も出なくなった。**
- なぜそうなるのか。上限を足したことで、ソルバーは何をしなければならなくなったか。
- 上限を 4 や 5 に緩めるとどうなるか。
- この制約を足したモデルの答えは、足す前と同じだと言えるか。

**D. 検査をもう1つ足す**（検証器を書き換える）

第08回の発展演習Bで書いた「5日以上続けて働かない」を、検証器の側に足す。
`check_run(rows, names, data)` を新しく書き、`verify` から呼ぶ。

確かめたいこと。

- `samples/good-week.txt` はこの検査を通るか。通らないとしたら、それは違反か。
- **モデルに書いていない条件を検証器で検査すると、何が起きるか。**
  検証器が「不合格」と言ったとき、直すのはモデルか、検査か、それとも仕様か。
:::

## よくある誤り

| 症状 | 原因 | 直し方 |
|---|---|---|
| `#size の行が無い` | 出力の一部しかコピーしていない | 出力欄を全部選んでコピーし直す。`#` の行は下のほうにある |
| `#size (4, 3) と #shift の行数・長さが合わない` | 途中経過の解と最適解が混ざった状態で貼り、行が欠けた | 出力全体をそのまま保存する。検証器は最後の解だけを見る |
| 正常例が「不合格」になる | 違う `.dzn` を指定した（重みや希望休が違う） | 出力を作ったときと同じ `.dzn` を渡す |
| 反例なのに「合格」になる | 対応する検査関数がまだ空である | `まだ書かれていない検査:` の行を読む |
| 資格の検査が全部の日で反応する | 資格の判定に `data["leader"][d]` と書いた（日の番号で引いている） | 資格は職員の性質なので `data["leader"][s]` である |
| 資格の検査が1日も反応しない | `r[d] == NIGHT` を `r[d] == "夜"` などと書いた | `#shift` の行は `D` / `N` / `O` である。表の全角文字ではない |
| `pref` の食い違いが報告されない | `count_pref` が `None` を返したままである | `return` で件数を返す |
| `検査できない: 出力の大きさ（…）とデータファイル（…）が合わない` | 出力と `.dzn` の組が違う（7日の出力に14日の `.dzn` を渡した、など） | 出力を作ったときと同じ `.dzn` を渡す |
| 14日のデータで `==========` が出ない | 打ち切られていないだけで、異常ではない | 本文の「速くする3つの手」を読む |

::: {.warning}
**検証器が「合格」を返しても、モデルが正しいとは限らない。**

分かるのは「**書いた検査は通った**」ということだけである。
検査を書いていない条件については、何も言っていない。

第09回の最後に書いた「最適値が出た」と「モデルが正しい」の関係と、
まったく同じ構図がもう一段外側にもある。
:::

## 扱わないこと

- **テストフレームワーク**（`pytest` など） → この科目では扱わない。
  素の Python で足りる。自由課題で使いたければ使ってよいが、
  **再現手順を README に書く**こと
- **ソルバーの内部アルゴリズム**（伝播・探索戦略・学習節） → この科目の対象外。
  統計の数値は「比較のための目安」として使うに留める
- **探索アノテーション・ソルバーの切り替えによる高速化** → この科目では扱わない
  （[MiniZinc 実行環境の使い方](../references/setup-minizinc.md)）。
  ただし自由課題で行き詰まったら、別のソルバーを試すのは正当な手である
- **統計値の詳しい解釈** → 数値の意味を細かく追うより、
  **同じ条件で2つを比べる**ことを優先する
- **モデルの自動的な検証**（充足可能性を使ったモデル間の同値性検査） → この科目では扱わない
- **形式化から検証までの工程を自分の問題で回すこと** →
  [第11回](11-project-formulation.md)から[第14回](14-project-completion.md)の自由課題。
  この回で最後の1手順が揃った
