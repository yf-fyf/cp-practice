# 第14回 自由課題: 評価と成果物の完成

## この回の目標

この回を終えると、次のことができる。

- 条件または規模を変えた実験を行い、結果を表として示せる
- 結果を根拠に、モデルの特徴と限界を説明できる
- 成果物一式を、第三者が再現できる形にまとめられる
- 発表資料の初版を作り、持ち時間内で通せる

## 今回やること

::: important
**この回の初めに、仕様を凍結する。**

凍結できるのは、次の3つが揃ったときである。

1. 企画書のハード制約が、すべてモデルに入っている
2. モデルとは独立した検査が、ハード制約1本について書けている
3. その検査に引っかかる反例が1つあり、「不合格」と出ることを確かめてある

**凍結するのは「新しい要求」と「任意の機能」である。**
企画書で合意済みのハード制約を入れることと、
重大な不具合（違反する解が出る、検査が通らない）を直すことは、この回でも行ってよい。
凍結後に足さないのは、企画書に無い制約・新しい目的関数・出力の飾りである。

まだ足したい制約があっても、企画書に無いものは足さない。
足すと、そこまでに取った実験結果が全部使えなくなる。
入れきれなかったものは「今後の課題」として発表で述べる。
足りないと分かっていることを述べるのは、減点ではない。
:::

3つが揃っていない場合は、実験より先に**そこを埋める**。
順序と時間の目安は下の「凍結条件が揃っていないとき」にある。

| 時間 | 活動 |
|---|---|
| 5分 | 凍結条件の3つを確かめ、仕様を凍結する。今の版をコピーして残す |
| 30分 | 実験する（条件を変える／規模を変える）。結果を実験記録へ書く |
| 15分 | 結果を1枚の表にまとめ、モデルの限界を3行で書く |
| 25分 | 成果物一式を整える（[成果物チェックリスト](../projects/deliverables-checklist.md)） |
| 20分 | 発表資料の初版を作る（[発表資料の構成ガイド](../projects/presentation-guide.md)） |
| 5分 | 発表練習会の日程を確認する |

### 凍結条件が揃っていないとき

第13回の最低ラインに届いていなくても、この回で成果物一式は完成できる。
**上から順に、届いたところで実験へ移る。**足りない分は「今後の課題」に書く。

| 順序 | やること | 目安 |
|---|---|---|
| 1 | ハード制約1本の独立した検査を書き、反例で「不合格」を出す（第13回の最低ライン） | 25分 |
| 2 | 企画書のハード制約で未実装のものを、1本ずつ足して実行する | 20分 |
| 3 | 実験を**1通りだけ**行う（規模を1段変える、が最も速い） | 15分 |
| 4 | 成果物一式を整え、発表資料の初版を作る | 40分 |

::: warning
**実験を増やすより、検証を1本持つほうを優先する。**

実験の表が3行あってもモデルが正しいとは言えないが、
独立した検査と反例が1組あれば「この条件については確かめた」と言える。
[評価の観点](../projects/README.md#評価の観点)でも、両者は別の項目である。
:::

### 実験する

実験とは、**2つ以上を比べること**である。1回動かして終わりではない。
比べ方は3通りある。1つ以上を選ぶ。

| 比べ方 | 例 | 分かること |
|---|---|---|
| **条件を変える** | 目的関数の重みを変える。制約を1本外す | 「良い解」の意味が何で決まっているか |
| **規模を変える** | 入力を2倍にする。要素数を段階的に増やす | 規模と実行時間の関係。どこで解けなくなるか |
| **表現を変える** | 同じ条件を別の書き方で表す | 記述の見やすさと速さの関係 |

規模を変えるときは、**変える軸を1つに絞る**。
第10回で7日と14日を比べたときに職員数を変えなかったのと同じ理由である。
2つ動かすと、差がどちらのせいか言えなくなる。

結果の表には、少なくとも次を入れる。

| 入力 | 設定 | 結果 | 実行時間 | 最適だと確かめたか |
|---|---|---|---|---|
| 何のデータか | 重み・制約の有無 | 目的関数の値、または解の有無 | 測った値 | 確かめた／打ち切った |

::: warning
**「最適だと確かめた」と「そこまでで一番良かった」を混ぜない。**

打ち切った結果を最適値として書くと、比較そのものが崩れる。
MiniZinc なら `==========` が出たかどうかで区別できる。
出ていないなら「打ち切り時点の最良解」と書く。
:::

### 限界を言葉にする

実験結果から、次の3つを書く。**それぞれ1〜2行でよい。**

1. **このモデルが扱えること。**どの規模まで、どの条件までなら解が出るか。
2. **扱えないこと。**規模の上限、表現しきれなかった条件、打ち切りが起きる設定。
3. **省略した条件。**現実にはあるが、モデルに入れなかったもの。なぜ入れなかったか。

3つ目を書けることが、この科目の到達点の1つである。
モデルは現実の一部を切り取ったものであり、
**何を切り落としたかを言えるかどうか**が、モデルを理解しているかの目安になる。

### 発表資料の初版を作る

構成は [発表資料の構成ガイド](../projects/presentation-guide.md)にある。
初版の時点では、体裁より**通しで話せること**を優先する。

発表は**10分**、質疑は**4分**を目安とする（第15回の時間割は下記の支援物にある）。
初版ができたら、一度声に出して時間を測る。
たいてい長すぎるので、削る場所を決めておく。

::: note
**発表練習会**は授業日程とは別に行う。第14回と第15回の間が基本候補である。
日時と参加方法は授業中に案内する。

- 持ち時間に収まるかを測る
- 「コードを読んでいない人」に通じるかを確かめる
:::

## 扱わないこと

- **企画書に無い制約・新しい機能の追加** → 凍結する。今後の課題として発表で述べる
  （企画書で合意済みのハード制約の実装と、重大な不具合の修正はこの回でも行う）
- **速くするためのモデルの作り直し** → この科目では扱わない。
  遅いことは結果として報告すればよい。第10回で見たとおり、
  速くなった理由が「問いを易しくした」ことである場合もある
- **統計値の詳しい解釈** → 数値の意味を細かく追うより、
  **同じ条件で2つを比べる**ことを優先する
