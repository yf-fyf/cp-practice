## この回の目標

この回を終えると、次のことができる。

- 職員×日の2次元の決定変数を宣言し、各マスにシフトを1つ割り当てるモデルを書ける

## 今回解く問題

架空の職場で、**職員の勤務表**を作る。

日は1日目から順に並んでいて、職員1人につき1日1つの勤務が決まる。
勤務は3種類しかない。

| シフト | 意味 |
|---|---|
| 日勤 | 昼間の勤務 |
| 夜勤 | 夜間の勤務 |
| 休み | その日は勤務しない |

::: {.note}
この形の問題は、一般に**ナーススケジューリング**（nurse scheduling / nurse rostering）
として知られている。制約プログラミングで繰り返し取り上げられる定番の題材である。
この教材が扱うのは、そのうち**いちばん単純な形**にあたる。
:::

::: {.warning}
**この回で使う職場・職員・勤務規則はすべて架空である。**
実在する医療機関や施設の勤務規則ではなく、
制約プログラミングの教材として単純化して作ったものである。
実際の勤務表には、法令・労使協定・個々の事情が関わる。
:::

必ず守らなければならない条件（**[ハード制約](../references/glossary.md#hard_constraint)**）は3つとする。

1. **必要人数**: どの日も、日勤に決まった人数、夜勤に決まった人数が入る
2. **資格**: どの日も、夜勤に入る人のうち1人以上がリーダー資格を持つ
3. **休息**: 夜勤に入った翌日は休みにする

::: {.note}
[**ハード制約**](../references/glossary.md#hard_constraint)は
[第07回](07-theme-assignment.md)で導入した語である。
「なるべく守る」ではなく「必ず守る」条件を指す。
第07回はハード制約が定員1本だけだった。**この回は3本を同時に書く。**

これに対して「なるべく守りたいが破ってもよい」条件（希望休など）は
[第09回](09-roster-soft.md)で扱う。
:::

::: {.discuss}
上の3つのほかに、勤務表で「必ず守るべき」ことは何が思いつくだろうか。

- 連続して何日まで働いてよいか
- 1週間の勤務日数に下限や上限はあるか
- 「この人とこの人は同じ日に入れたい」はハード制約か

書き出したものを1つずつ見て、**破ったら勤務表として無効になるもの**と、
**破っても勤務表ではあるが、なるべく避けたいもの**に分けてみる。
この分け方が、第08回と第09回の分かれ目そのものである。
:::

## 変数・定義域・制約・目的へ分解

第03回で決めた語彙を当てる。

| 語 | この問題では |
|---|---|
| 変数 | 職員 `s` の `d` 日目の勤務（職員の数 × 日数だけある） |
| 定義域 | 日勤・夜勤・休みの3つ |
| 制約 | 必要人数・資格・休息 |
| 目的 | **この回では無し**（条件を満たす表が1つ見つかればよい） |

第07回で埋まった「目的」の欄が、この回では空に戻る。
まず**条件を満たす表**を作れるようにしてから、第09回で「良い表」に進む。

前の回までと比べると、変数の並び方が変わっている。

| 回 | 決定変数の形 | 添字 | 値 |
|---|---|---|---|
| 第03回・第04回 | `array[ROWS, COLS] of var 1..9` | 行・列 | 数字 |
| 第07回 | `array[STUDENTS] of var THEMES` | 人 | テーマ |
| 第08回 | `array[STAFF, DAYS] of var SHIFTS` | 人・日 | シフト |

第07回の1次元に、**日という軸が1本増えただけ**である。

## 概念と構文

### シフトを `enum` で表す

::: {.term}
[**列挙型**](../references/glossary.md#enum_type)とは、
取り得る値のそれぞれに名前を付けた型である。
`1` `2` `3` と番号で覚える代わりに、`day` `night` `off` と書ける。
:::

```{.minizinc filename="シフトの種類"}
enum SHIFTS = { day, night, off };

array[SHIFTS] of string: mark = ["日", "夜", "休"];    % 表示用の1文字
```

`mark` は `SHIFTS` の宣言と**同じ並び**にする。
`day` が1番目なので `mark[day]` が `"日"` になる。

数字ではなく名前を使う利点は2つある。

- 読める。`roster[s, d] = night` は「その日は夜勤」と読める
- 書き間違いをソルバーが見つける。`nigth` と打てば「そんな名前は無い」と言われる

### 職員×日の決定変数

::: {.term}
[**シフトの表現**](../references/glossary.md#shift_representation)とは、
勤務表の各マスに勤務区分を1つ入れる表し方である。
:::

```{.minizinc filename="決定変数"}
set of int: STAFF = 1..ns;
set of int: DAYS  = 1..nd;

array[STAFF, DAYS] of var SHIFTS: roster;     % roster[s, d] = 職員 s の d 日目
```

第03回の数独が `array[ROWS, COLS] of var 1..9` だったのと同じ形である。
**添字が「行・列」から「職員・日」に変わり、値が数字からシフトに変わっただけ**である。

::: {.important}
**「1人1日1シフト」は制約として書かない。**

職員 `s` の `d` 日目にマスが1つあり、そのマスは値を1つしか取れない。
だから「日勤と夜勤の両方に入る」ことも「どの勤務にも入らない」ことも、
この書き方では起こりようがない。

第03回の「1マスに数字は1つ」、第07回の「1人につき1テーマ」と同じことである。
:::

::: {.term}
[**表現が保証する性質**](../references/glossary.md#representation_guarantees)とは、
変数の取り方そのものが自動的に満たす条件のことである。

**保証される性質は制約として書かない。**
モデルを読むときは「何が自動で保証され、何を自分で書いたか」を毎回見分ける。
:::

見分け方は単純である。**その条件を破った状態を、変数に値を入れて表せるか**を考える。
表せないなら表現が保証している。表せるなら書かないと守られない。

| 条件 | 破った状態を表せるか | 扱い |
|---|---|---|
| 1人1日1シフト | 表せない（マスの値は1つ） | 表現が保証する |
| 各日の日勤が2名 | 表せる（3名でも0名でも書ける） | 制約に書く |
| 夜勤の翌日は休み | 表せる（翌日に日勤と書ける） | 制約に書く |

### 列を取り出して数える

「その日の日勤の人数」は、表の**列**を1本取り出して数えたものである。

```{.minizinc filename="d 日目の列"}
[ roster[s, d] | s in STAFF ]                 % d 日目の全職員のシフトが並ぶ
```

第03回で使った配列内包表記そのままである。並んだら数える。

```{.minizinc filename="数える"}
count([ roster[s, d] | s in STAFF ], day)     % その列に day がいくつあるか
```

::: {.term}
[**必要人数制約**](../references/glossary.md#coverage_constraint)とは、
各日・各シフトに必要な人数を満たす条件である。
第07回の定員制約は上限だったが、必要人数は**ちょうどその人数**を求めることが多い。
:::

資格を持つ人だけを数えたいときは、内包表記に `where` を足して絞る。

```{.minizinc filename="資格者だけ"}
count([ roster[s, d] | s in STAFF where leader[s] ], night)
```

::: {.term}
[**資格制約**](../references/glossary.md#qualification_constraint)とは、
資格を持つ人を必ず配置する条件である。
:::

`where` の条件 `leader[s]` はパラメータなので、
「まずリーダー資格を持つ人だけを集めて、その中で夜勤の人数を数える」と読める。

この条件は「**すべての日について**、**ある**資格者がその日の夜勤にいる」の順序で読む。
順序を入れ替えると別の条件になる（[論理の入門(1)](../references/logic-intro.md#nested-quantifiers)）。

### 隣り合う日を見る

::: {.term}
[**隣接する添字**](../references/glossary.md#adjacent_index)とは、
`roster[s, d]` と `roster[s, d + 1]` のように隣り合う位置を同時に参照する書き方である。
:::

```{.minizinc filename="夜勤の翌日は休み"}
constraint forall(s in STAFF, d in 1..nd - 1)(
  roster[s, d] = night -> roster[s, d + 1] = off
);
```

::: {.term}
[**休息制約**](../references/glossary.md#rest_constraint)とは、
連続する日のあいだに置く条件である。「夜勤の翌日は休み」がその例である。
:::

::: {.warning}
**`d` の動く範囲は `1..nd - 1` である。**

最終日には翌日が無い。`d in DAYS` と書くと `roster[s, nd + 1]` を触ろうとして
`index out of bounds` で落ちる。
隣を見る制約を書くときは、**範囲を1つ内側に刻む**のが定石である。
:::

`->` は「ならば」で、第03回から使っている。
「夜勤でないなら何も言わない」ので、休みや日勤の翌日は自由である。

書き方の一覧は [MiniZinc 早見表](../references/minizinc-cheatsheet.md)にある。
この回で新しく使うのは `enum` と、隣の添字の参照だけである。

## 小さな実行例

3人・2日という、手で確かめられる大きさで動かす。
日勤1名・夜勤1名が毎日必要で、職員Aと職員Cがリーダー資格を持つ。

```{.minizinc filename="mini.mzn"}
int: ns = 3;
int: nd = 2;

set of int: STAFF = 1..ns;
set of int: DAYS  = 1..nd;

enum SHIFTS = { day, night, off };
array[SHIFTS] of string: mark = ["日", "夜", "休"];

array[STAFF] of string: sname = ["A", "B", "C"];
array[STAFF] of bool: leader  = [true, false, true];
array[DAYS]  of int: need_day   = [1, 1];
array[DAYS]  of int: need_night = [1, 1];

array[STAFF, DAYS] of var SHIFTS: roster;

constraint forall(d in DAYS)(                          % 必要人数
  count([ roster[s, d] | s in STAFF ], day) = need_day[d]
);
constraint forall(d in DAYS)(
  count([ roster[s, d] | s in STAFF ], night) = need_night[d]
);
constraint forall(d in DAYS)(                          % 資格
  count([ roster[s, d] | s in STAFF where leader[s] ], night) >= 1
);
constraint forall(s in STAFF, d in 1..nd - 1)(         % 休息
  roster[s, d] = night -> roster[s, d + 1] = off
);

solve satisfy;

% このあとに output（表の整形）が続く。配布ファイルに書いてある。
```

`output` は結果を人が読める表に整える部分で、**書けなくてよい**。
演習ファイルの `roster.mzn` に書き込んであるので、演習で触ることはない。

::: {.hint summary="output の中身を見る（読まなくてよい）"}
```{.minizinc filename="mini.mzn（output の部分）"}
output
  [ "        " ++ concat([ show(d) ++ "日 " | d in DAYS ]) ++ "\n" ]
  ++ [ "職員" ++ sname[s] ++ "   "
       ++ concat([ mark[fix(roster[s, d])] ++ "  " | d in DAYS ]) ++ "\n"
     | s in STAFF ]
  ++ [ "日勤    "
       ++ concat([ show(count([ roster[s, d] | s in STAFF ], day)) ++ "   " | d in DAYS ])
       ++ "\n" ]
  ++ [ "夜勤    "
       ++ concat([ show(count([ roster[s, d] | s in STAFF ], night)) ++ "   " | d in DAYS ])
       ++ "\n" ]
  ++ [ "資格者  "
       ++ concat([ show(count([ roster[s, d] | s in STAFF where leader[s] ], night)) ++ "   "
                 | d in DAYS ])
       ++ "\n" ];
```

`concat` は文字列を並べてつなぐ関数、`fix` は決定変数の値を取り出す関数である。
名前だけ知っていれば足りる。
:::

既定のソルバー（Gecode）で実行すると、次の表が出る。

```solver
        1日 2日
職員A   夜  休
職員B   休  日
職員C   日  夜
日勤    1   1
夜勤    1   1
資格者  1   1
```

3つの制約が全部きいていることを、表の上で確かめられる。

- **必要人数**: 下2行が `need_day` `need_night` と一致している（列で見る）
- **資格**: 1日目の夜勤は職員A、2日目は職員C。どちらもリーダー資格者である（列で見る）
- **休息**: 職員Aは1日目が夜勤なので2日目が休み（行で見る）

::: {.note}
この規模では条件を満たす表は全部で4通りある。
**どれが出るかはソルバー次第**である。
第04回で数独の複数解を見たときと同じで、
`solve satisfy;` は「そのうち1つ」を返しているにすぎない。
:::

## 予想してから試す

::: {.predict}
`mini.mzn` の `need_day` を `[2, 2]`（日勤2名）に変えて実行する。何が出ると思うか。

1. 全員が毎日働く表が出る（2名 + 1名 = 3名で人数はちょうど足りる）
2. `=====UNSATISFIABLE=====` が出る
3. エラーになって止まる

3人で「日勤2名・夜勤1名」なら、人数の合計はぴったり足りている。
それでも解が出ないとしたら、**どの制約が邪魔をしているか**まで書き出してから実行する。
:::

```solver
=====UNSATISFIABLE=====
```

人数は足りているのに解が無い。原因は**休息制約**である。

1日目に夜勤へ入った人は2日目が休みになる。
ところが2日目も3人全員が必要なので、休んでいる人がいてはいけない。
この2つは同時に成り立たない。

休息制約の3行を消して実行し直すと、今度は表が出る。

```solver
        1日 2日
職員A   夜  夜
職員B   日  日
職員C   日  日
日勤    2   2
夜勤    1   1
資格者  1   1
```

職員Aが2日続けて夜勤に入っている。
必要人数と資格だけを見れば正しい表だが、**勤務表としては受け入れがたい**。
休息制約は、まさにこれを止めるために書いたものである。

::: {.note}
**充足不能になる理由は、1つの制約だけを見ても分からないことがある。**

必要人数だけを見れば足りている。休息制約だけを見ても矛盾は無い。
**組み合わさったときに初めて解が消える。**

`=====UNSATISFIABLE=====` が出たときは、
制約を1つずつ外して「どれを外すと解が出るか」を調べる。
外して解が出た制約が、少なくとも矛盾の一方の側にいる。
:::

::: {.check}
ここまでで、次を確認しておく。

- `enum` で宣言した値を制約の中で使える
- 表の1列を内包表記で取り出して `count` で数えられる
- 隣の日を見る制約で、`d` の範囲を1つ内側に刻む理由を説明できる
- `=====UNSATISFIABLE=====` が出たときに、制約を外して原因を絞る手順を言える
:::

## 必須演習

::: {.exercise level=required}
### 必要人数の制約を書く

`workbook/sessions/08-roster-hard/roster.mzn` を Playground で開き、
データに `small.dzn`（4人・3日・日勤2名・夜勤1名）を使って
`% TODO(1)` の必要人数制約を2本書く。

**完了条件**: 実行して勤務表が1つ表示され、出力の `日勤` `夜勤` の行が
`small.dzn` の `need_day` `need_night` と一致している。
さらに、**「1人1日1シフト」を制約として1行も書いていないのに守られている理由**を
説明できる。

TODO を埋める前に一度実行してみるとよい。
制約が1つも無い状態では、**全員が3日とも日勤の表**が返り、
出力の `日勤` の行は `4 4 4`、`夜勤` の行は `0 0 0` になる。
第03回・第05回・第07回とまったく同じで、**制約を書いた分だけが守られる**。
:::

::: {.hint summary="ヒント1: 何を数えるのか"}
必要人数は「日ごと」の条件である。
まず1日を固定して、その日に日勤へ入っている人数を数える。

表のうち「その日の列」は、内包表記で取り出せる。

```{.minizinc}
[ roster[s, d] | s in STAFF ]
```

日を全部について回すのは `forall` である。
:::

::: {.hint summary="ヒント2: 数え方と比較の向き"}
数えるのは `count(配列, 値)` である。上の内包表記をそのまま第1引数に置く。

比較は `<=` ではなく `=` にする。
第07回の定員は上限だったが、必要人数は**ちょうどその人数**である。
多すぎても勤務表として成り立たない（人手が余っていても、
その人は休みにするか別の勤務に入れるべきである）。

日勤と夜勤で `constraint` を2本書く。
:::

::: {.hint summary="ヒント3: 解答"}
```{.minizinc filename="roster.mzn（TODO(1)）"}
constraint forall(d in DAYS)(
  count([ roster[s, d] | s in STAFF ], day) = need_day[d]
);
constraint forall(d in DAYS)(
  count([ roster[s, d] | s in STAFF ], night) = need_night[d]
);
```

既定のソルバーでは、次のような表が返る。

```solver
        1日 2日 3日
職員A   休  休  休
職員B   夜  夜  夜
職員C   日  日  日
職員D   日  日  日
日勤    2   2   2
夜勤    1   1   1
資格者  0   0   0
```

`日勤` `夜勤` の行は合っている。**必要人数制約は正しく書けている。**

一方で、職員Bが3日続けて夜勤に入り、職員Aは3日とも休みである。
`資格者` の行は3日とも `0` で、リーダー資格を持たない職員Bが
毎晩ひとりで夜勤に入っていることが分かる。

**書いていない条件は守られない。** 次はこれを直す。
:::

## 標準演習

::: {.exercise level=standard}
### 資格と休息を足し、8人・7日へ広げる

`roster.mzn` の `% TODO(2)`（資格）と `% TODO(3)`（休息）を埋める。
`small.dzn` で動かして表が変わることを確かめてから、
**モデルを1文字も変えずに** `week.dzn`（8人・7日）へ差し替える。

**完了条件**: 次の表が埋まっていて、3つのハード制約それぞれについて
「出力のどこを見れば確かめられるか」を言える。

| データ | 表が出たか | `資格者` の行 | 夜勤の翌日が休みか |
|---|---|---|---|
| `small.dzn` | | | |
| `week.dzn` | | | |

確かめどころは3つある。

- `small.dzn` で、必要人数だけのときと表がどう変わったか。
  職員Bの3連続夜勤はどうなったか。
- `week.dzn` の表で、**いちばん多く働いている人**と
  **いちばん休んでいる人**は何日ずつか。
  この表は「条件を満たしている」が、それでよいのか。
- `week.dzn` の `need_day` を全部 `3` にする（6日目・7日目も3名にする）と、
  どうなるか。
:::

::: {.hint summary="ヒント1: 資格制約（TODO(2)）"}
「その日の夜勤に入った人のうち、リーダー資格を持つ人が1人以上」である。

数えるのは必要人数と同じだが、数える相手が
**リーダー資格を持つ人だけ**に絞られている。
内包表記に `where` を足すと絞れる。

```{.minizinc}
[ roster[s, d] | s in STAFF where leader[s] ]
```

比較は `= 1` ではなく `>= 1` にする。2人とも資格者でもかまわない。
:::

::: {.hint summary="ヒント2: 休息制約（TODO(3)）"}
「夜勤ならば翌日は休み」である。`->` をそのまま使う。

```{.minizinc}
roster[s, d] = night -> roster[s, d + 1] = off
```

これを全職員・全日について回す。ただし**最終日には翌日が無い**ので、
`d` の範囲を `DAYS` ではなく `1..nd - 1` にする。

`forall` は `forall(s in STAFF, d in 1..nd - 1)( ... )` のように
2つの添字をカンマで並べて書ける（第03回の数独と同じ）。
:::

::: {.hint summary="ヒント3: データを差し替える"}
第04回・第07回と同じである。**モデルは触らない。**
Playground でデータファイルのタブを増やし、実行時に `week.dzn` を選ぶ。
画面の操作が見つからないときは、`week.dzn` の中身をモデルの末尾に
貼り足しても同じことができる（そのときは `small.dzn` の分を消す）。

`ns` `nd` `sname` `leader` `need_day` `need_night` を
**モデル側で値なしに宣言**してあるので、データを替えるだけで規模が変わる。
:::

### 条件を満たす表は「良い表」ではない

`week.dzn` を既定のソルバーで解くと、たとえば次の表が返る。

```solver
        1日 2日 3日 4日 5日 6日 7日
職員A   休  夜  休  夜  休  夜  休
職員B   夜  休  夜  休  夜  休  休
職員C   日  休  日  休  日  休  休
職員D   夜  休  夜  休  夜  休  夜
職員E   休  夜  休  夜  休  休  夜
職員F   休  日  休  日  休  日  日
職員G   日  日  日  日  日  夜  休
職員H   日  日  日  日  日  日  日
日勤    3   3   3   3   3   2   2
夜勤    2   2   2   2   2   2   2
資格者  1   1   1   1   1   1   1
```

3つのハード制約はすべて満たされている。**この表は正しい。**

それでも、この表を配られたら文句が出るはずである。

| 職員 | 勤務日数 | 夜勤の回数 |
|---|---|---|
| H | 7日 | 0回 |
| G | 6日 | 1回 |
| D | 4日 | 4回 |
| C | 3日 | 0回 |

職員Hは7日間ずっと働き、職員A・B・C・Eは3日しか働いていない。
職員Dは夜勤を4回引き受け、職員C・F・Hは1回も入っていない。

::: {.important}
**ソルバーは「条件を満たす表」を1つ返しただけである。**

偏りを避けよとは、こちらが一言も言っていない。
第07回で `solve satisfy;` が返した割当てが「良い割当てとは限らなかった」のと
同じことが、ここでも起きている。

**この偏りを直すのが第09回である。**
:::

## 発展演習

::: {.exercise level=advanced}
### いずれか1つを選ぶ

いずれも `week.dzn`（8人・7日）で試す。
`small.dzn`（4人・3日）は小さすぎて、足すとすぐ充足不能になる。

**A. 勤務日数に下限と上限を付ける**

「1週間に3日以上5日以下」という条件を足す。
1人ぶんの勤務日数は「休みでない日の数」である。

```{.minizinc filename="書きかけ"}
int: min_work = 3;
int: max_work = 5;

constraint forall(s in STAFF)(
  let { var int: w = sum(d in DAYS)( bool2int(roster[s, d] != off) ) } in
  min_work <= w /\ w <= max_work
);
```

`let { ... } in ...` は、その場だけの名前を付ける書き方である。
`w` を2回書きたいので置いている。

確かめたいこと。

- 上の表で7日働いていた職員Hは何日になったか。
- `min_work` を `5` に上げると何が起きるか。
  必要な勤務のマスは全部で何個あり、8人で分けるとどうなるか。

**B. 連勤の上限**

「5日以上続けて働かない」＝「どの5日間を取っても、その中に休みが1日はある」。

```{.minizinc filename="書きかけ"}
int: max_run = 4;

constraint forall(s in STAFF, d in 1..nd - max_run)(
  exists(k in 0..max_run)( roster[s, d + k] = off )
);
```

`exists` は第04回で使った。`d` の範囲がなぜ `1..nd - max_run` なのかを、
`nd = 7` `max_run = 4` に当てはめて確かめる。

**C. 夜勤の間隔をあける**

休息制約は「夜勤の翌日は休み」までしか言っていない。
翌々日にまた夜勤へ入ることは止めていない。
「夜勤と次の夜勤のあいだを2日以上あける」を足す。

```{.minizinc filename="書きかけ"}
constraint forall(s in STAFF, d in 1..nd - 2)( ? );
```

上の表の職員Aと職員Dが、この条件でどう変わるかを見る。

**D. 同じ問題を真偽値で書き直す**

シフトの表現を変える。`array[STAFF, DAYS, SHIFTS] of var bool: x` とし、
`x[s, d, k]` を「職員 s が d 日目にシフト k へ入るか」とする。

このとき**「1人1日1シフト」は表現が保証してくれない**ので、
制約として書かなければならない。

```{.minizinc filename="書きかけ"}
constraint forall(s in STAFF, d in DAYS)(
  sum(k in SHIFTS)( bool2int(x[s, d, k]) ) = 1
);
```

確かめたいこと。

- 決定変数の個数は、元のモデルと比べて何倍になったか。
- 必要人数・資格・休息の3つは、この表現ではどう書くか。
- どちらの表現が読みやすいか。**書く量が少ないほうが常に良いと言えるか。**

::: {.note}
同じ問題を違う表現で書く比較は、
[グラフ彩色の3つの表現](../references/graph-coloring.md)でも扱っている。
第05回の Boolean 符号化と同じ考え方である。
:::
:::

## よくある誤り

| 症状 | 原因 | 直し方 |
|---|---|---|
| 全員が全日とも日勤の表が出る | 制約を1つも書いていない | `TODO(1)` を埋める |
| `index out of bounds` で落ちる | 隣の日を見る制約で `d in DAYS` と書いた | `d in 1..nd - 1` に刻む |
| `type error: no function or predicate with this signature` | `count` の第2引数に `SHIFTS` の要素以外を渡した | `day` / `night` / `off` のどれかにする |
| `undefined identifier: nigth` | `enum` の値の綴り間違い | 綴りを直す。**この誤りを見つけてくれるのが `enum` の利点である** |
| `資格者` の行が `0` のまま | `TODO(2)` を書いていない、または `where` を付け忘れた | `where leader[s]` で絞る |
| 夜勤の翌日に日勤が入っている | `TODO(3)` を書いていない | `->` の右辺を `= off` にする |
| `=====UNSATISFIABLE=====` になる | 必要人数の合計が人数を超えている、または休息制約と噛み合っていない | 制約を1つずつ外して、どれを外すと解が出るかを見る |
| `output` で `roster[s, d]` を添字に使うと型エラー | 決定変数のまま `mark` の添字にした | `mark[fix(roster[s, d])]` にする |
| データを替えたのに結果が変わらない | データファイルが選ばれていない | 実行時のデータの選択を確かめる。貼り足す方式なら古い方を消す |

::: {.warning}
**表が出たことは、モデルが正しいという意味ではない。**

資格制約を書き忘れていても、ソルバーは「その条件を無視した表」を返す。
返ってきた表を、**出力の `日勤` `夜勤` `資格者` の3行で必ず確かめる**。
第03回からずっと同じである。

そして、この目視の確認そのものを自動化するのが[第10回](10-roster-verification.md)である。
:::

## 扱わないこと

- **希望休・公平性などのソフト制約** → [第09回](09-roster-soft.md)。
  この回のハード制約は「破ったら勤務表として無効」なものだけである
- **モデルとは独立した検証・性能評価** → [第10回](10-roster-verification.md)
- **`cumulative` などスケジューリング向けの大域制約** →
  この科目では扱わない。名前だけ知っておけばよい。
  この規模なら `count` と `forall` で足りる
- **実際の勤務規則・労働法制** → この科目の範囲外。
  ここで使う規則はすべて教材用に単純化した架空のものである
- **勤務希望の集め方や運用** → この科目の範囲外
- **探索アノテーションによる高速化** →
  [MiniZinc 実行環境の使い方](../references/setup-minizinc.md)の「扱わないこと」

## 次回への接続

この回で作った表は、3つのハード制約をすべて満たしている。**正しい表である。**
それでも、7日連続で働く人と3日しか働かない人が同居していた。

第09回では、この表に次の2つを足す。

- **希望休**: 「この日は休みたい」という申し出。かなえたいが、必ずかなうとは限らない
- **公平性**: 勤務日数や夜勤の回数の偏りを、数で表して小さくする

どちらも「破ったら無効」ではない。**なるべく満たしたい条件**である。
第07回で希望順位を得点に直したのと同じように、
**破った回数を数えて目的関数に入れる**。

::: {.note}
**自由課題に向けて**: 自分が考えている問題について、
「破ったら成り立たない条件」を箇条書きで並べてみる。
並べたあとで、その中に**本当は破ってもよいもの**が混ざっていないか見直す。
全部をハード制約にすると、たいてい `=====UNSATISFIABLE=====` になる。
:::
