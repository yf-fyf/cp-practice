## 今回解く問題

`pip install` や `apt install` で1つ頼んだだけなのに、
知らない名前がいくつも一緒に入ってきた経験や、
「その版とは一緒に入れられない」と断られた経験はないだろうか。

ソフトウェアを入れるとき、そのソフトだけが入ることはめったにない。
「A を入れるなら B も要る」「C と D は同時には入れられない」といった条件が付いてくる。
条件をすべて満たす**入れ方の組合せ**を見つけるのが、パッケージ管理ソフトの仕事である。

この回で扱うのは、次の架空の5つのパッケージである。

| パッケージ | 役割 |
|---|---|
| `app` | アプリ本体 |
| `gui` | 画面を描く部品 |
| `net` | 通信をする部品 |
| `db` | 新しいデータ保存の仕組み |
| `legacy` | 古いデータ保存の仕組み |

条件は次のとおりである。

1. `app` は必ず入れる（**必須**）
2. `app` を入れるなら `gui` も入れる（**依存**）
3. `gui` を入れるなら `net` も入れる（**依存**）
4. `app` を入れるなら、`db` か `legacy` の少なくとも一方を入れる（**択一**）
5. `db` と `legacy` は同時には入れられない（**競合**）

問いは「この5つの条件をすべて満たす入れ方はあるか。あるならどれか」である。

::: {.discuss}
実行する前に、紙の上で1つ答えを作ってみる。
5つの条件を上から順に読んでいけば、手でも見つけられる。
答えは**1通りしか無い**だろうか。
:::

## 変数・定義域・制約・目的へ分解

第03回で決めた語彙をそのまま当てる。

| 語 | この問題では |
|---|---|
| 変数 | 各パッケージを「入れるか、入れないか」 |
| 定義域 | 真か偽（2通り） |
| 制約 | 必須・依存・択一・競合の5つの条件 |
| 目的 | なし（条件を満たすものが1つ見つかればよい） |

数独では、1つの変数が 1〜9 のどれかを取った。
ここでは1つの変数が**真か偽**しか取らない。
定義域が2つしか無いこの形を特別に扱うのが、この回の題材である。

::: {.term}
[**命題変数**](../references/glossary.md#propositional_variable)とは、
真か偽のどちらかになる変数である。
「`app` を入れる」のように、**成り立つか成り立たないかが決まる文**に1つずつ対応させる。

この科目では `use_app` のように名前を付ける。
`use_app` が真なら「`app` を入れる」、偽なら「入れない」と読む。
:::

このように、選択肢を真偽変数の組で表すことを
[**Boolean 符号化**](../references/glossary.md#boolean_encoding)という。

## 理論概説

### 論理回路から論理式へ

論理回路で使った AND・OR・NOT は、そのまま論理式の記号に置き換わる。
**新しく覚えるのは「ならば」だけ**である。

![論理回路のNOT・AND・OR記号と、論理式の否定・論理積・論理和、および Z3Py の Not・And・Or の対応を1行ずつ並べた表。右端に、回路に対応する記号が無い含意（ならば、p→q、Implies）を分けて置いてある。](figures/logic-gates-formulas.svg)

::: {.term}
[**論理演算**](../references/glossary.md#logical_connectives)は次の4つである。

| 記号 | 読み | Z3Py | 真になるとき |
|---|---|---|---|
| $\neg p$ | $p$ でない | `Not(p)` | $p$ が偽のとき |
| $p \land q$ | $p$ かつ $q$ | `And(p, q)` | 両方が真のとき |
| $p \lor q$ | $p$ または $q$ | `Or(p, q)` | 少なくとも一方が真のとき |
| $p \to q$ | $p$ ならば $q$ | `Implies(p, q)` | 下の真理値表を見る |
:::

「または」は日常語と少しずれる。$p \lor q$ は
**両方が真のときも真**である（どちらか一方だけ、という意味ではない）。

### 「ならば」を真理値表で確かめる

[**真理値表**](../references/glossary.md#truth_table)は、
変数の値の組み合わせをすべて並べて式の値を書き出した表である。
変数が2つなら4行になる。

| $p$ | $q$ | $\neg p$ | $p \land q$ | $p \lor q$ | $p \to q$ |
|---|---|---|---|---|---|
| 偽 | 偽 | 真 | 偽 | 偽 | **真** |
| 偽 | 真 | 真 | 偽 | 真 | **真** |
| 真 | 偽 | 偽 | 偽 | 真 | **偽** |
| 真 | 真 | 偽 | 真 | 真 | **真** |

$p \to q$ が偽になるのは、**$p$ が真なのに $q$ が偽**の1行だけである。

::: {.important}
$p \to q$ は「$p$ が偽ならいつでも真」である。
「`app` を入れるなら `gui` も入れる」という条件は、
**`app` を入れない場合には何も要求していない**。

ここが直感とずれやすい。「`app` を入れないなら `gui` も入れてはいけない」とは
**言っていない**。約束を破ったことになるのは、`app` を入れたのに `gui` を入れなかったときだけである。
:::

含意は否定と論理和で書き直せる。$p$ が偽の行と、$q$ が真の行で真になる、と読む。

$$p \to q \;\equiv\; \neg p \lor q$$

$\equiv$ は「**どの行でも値が同じ**」という記号である（「同値」と読む）。
真理値表の右2列を見比べると、4行とも値が一致していることが確かめられる。

### 充足可能性・SAT・UNSAT

::: {.term}
- [**充足可能**](../references/glossary.md#satisfiability): 与えたすべての式を
  同時に真にする値の割り当てが**存在する**こと
- **SAT**: 充足可能だと分かった状態。ソルバーは割り当ての例を返す
- [**UNSAT**](../references/glossary.md#unsat): どう値を選んでも同時には満たせない、
  と分かった状態
:::

たとえば $p \land \neg p$ は UNSAT である。
真理値表を書けば、どちらの行でも式が偽になることが分かる。

::: {.important}
**UNSAT は答えの一種である。**プログラムが壊れたという意味ではない。
「この条件は両立しない」ことが確かめられた、と読む。
第03回の `=====UNSATISFIABLE=====` とまったく同じ立場である。
:::

### 名前だけ知っておく2つ

理論概説はここまでである。この先には、名前だけ知っておけばよいものが2つある。
**どちらも必須演習にも標準演習にも出てこない。**

::: {.term}
- [**CNF**](../references/glossary.md#cnf)（連言標準形）: SAT ソルバーが受け取る形。
  「または」で結んだ塊（**CNF の節**）を「かつ」で並べただけの形である。
  第01回に出てきた「Prolog の節」（ピリオドで終わる1行のまとまり）とは**別のもの**で、
  名前が同じだけである
  **この科目では CNF へ手で直さない。**`Implies` や `And` をそのまま書けば、
  Z3 が内部で変換する
- [**ちょうど一つ**](../references/glossary.md#exactly_one): 選択肢のうち1つだけを選ぶ条件。
  「少なくとも一つ」と「高々一つ」を並べて書く。
  グラフ彩色を真偽変数で書くときに要る（発展演習 B）
:::

どちらも自習用の説明が
[SAT・SMT 概説](../references/logic-sat-smt.md)にある。
必要になってから読めばよい。

## 概念と構文

Z3 のプログラムは、どれも同じ4段構えになる。

```{.z3py filename="骨格"}
from z3 import *

# 1. 変数を作る
p, q = Bools("p q")

# 2. ソルバーに制約を足す
s = Solver()
s.add(Or(p, q))
s.add(Not(p))

# 3. 解けるかどうかを調べる
if s.check() == sat:
    # 4. 割り当てを読む
    m = s.model()
    print("p =", is_true(m[p]), " q =", is_true(m[q]))
else:
    print("条件を同時に満たす割り当ては無い")
```

```solver
p = False  q = True
```

使う API の一覧は [Z3Py 早見表](../references/z3py-cheatsheet.md)にある。
この回で使うのは `Bool` / `Bools` / `Not` / `And` / `Or` / `Implies` /
`Solver` / `add` / `check` / `model` / `is_true` だけである。

::: {.warning}
**`if s.check():` と書いてはいけない。**
`check()` が返すのは `sat` / `unsat` / `unknown` という値であって、真偽値ではない。
Python はこれをすべて「真」と見なすので、`unsat` でも分岐に入ってしまう。
そのまま `model()` を呼ぶと `Z3Exception: model is not available` になる。
**必ず `== sat` で比べる。**
:::

::: {.warning}
Python の `and` / `or` / `not` は Z3 の式には使えない。
`s.add(p and q)` は例外になる。`And(p, q)` と書く。
一方、比較演算子（`==` `!=`）は Z3 の式を返すのでそのまま使える。
:::

### 変数をまとめて作る

パッケージが5つあるので、変数を1つずつ手で書くより、辞書に入れて名前で引くほうが楽である。

```{.z3py filename="辞書で持つ"}
PACKAGES = ["app", "gui", "net", "db", "legacy"]

use = {name: Bool(f"use_{name}") for name in PACKAGES}
```

`use["app"]` が「`app` を入れる」という命題変数になる。

### 自然言語から論理式へ

条件の言い回しと論理式の対応を、この題材で並べておく。
**この対応表がこの回の中心**である。

| 日本語の条件 | 論理式 | Z3Py |
|---|---|---|
| A を必ず入れる | $a$ | `s.add(use["a"])` |
| A を入れるなら B も入れる | $a \to b$ | `s.add(Implies(use["a"], use["b"]))` |
| A を入れるなら B か C の一方は入れる | $a \to (b \lor c)$ | `s.add(Implies(use["a"], Or(use["b"], use["c"])))` |
| B と C は同時に入れられない | $\neg b \lor \neg c$ | `s.add(Or(Not(use["b"]), Not(use["c"])))` |
| A を入れてはいけない | $\neg a$ | `s.add(Not(use["a"]))` |

::: {.note}
「同時に入れられない」は $\neg(b \land c)$ とも書ける。
$\neg(b \land c) \equiv \neg b \lor \neg c$ なので、どちらでも同じである
（真理値表を4行書けば確かめられる）。
:::

## 小さな実行例

パッケージに入る前に、変数3つの小さな式で SAT と UNSAT を見ておく。

$$(r \lor p) \land (r \lor q) \land (\neg p \lor \neg q)$$

「$r$ か $p$」「$r$ か $q$」「$p$ と $q$ の両方ではない」の3つを同時に満たす割り当てはあるか。

```{.z3py filename="小さな例"}
from z3 import *

p, q, r = Bools("p q r")

s = Solver()
s.add(Or(r, p))
s.add(Or(r, q))
s.add(Or(Not(p), Not(q)))

print(s.check())
print(s.model())
```

```solver
sat
[r = True, q = False, p = False]
```

$r$ を真にすれば最初の2つが満たされ、$p$ と $q$ はどちらも偽にできる。
3つ目の条件も満たされている。

::: {.note}
表示される順序（`r` が先か `p` が先か）は決まっていない。
**中身が合っていれば問題ない。**
また、返ってくる割り当ては**1つの例**であって、唯一の答えとは限らない。
第04回の数独と同じで、「他にもあるか」は聞かないと分からない。
:::

## 予想してから試す

::: {.predict}
上の3つの条件に、4つ目として $\neg r$（$r$ は偽）を足す。何が起きると思うか。

1. さっきと同じ割り当てが出る
2. $r$ が偽である別の割り当てが出る
3. `unsat` が出る
4. エラーになって止まる

選んだ理由も一緒に書き出してから実行する。
**$r$ を偽にしたとき、最初の2つの条件は $p$ と $q$ に何を要求するか**を考えるとよい。
:::

```{.z3py filename="条件を1つ足す"}
s.add(Not(r))
print(s.check())
```

```solver
unsat
```

$r$ が偽なら、$r \lor p$ を満たすには $p$ が真でなければならない。
同じく $q$ も真でなければならない。
ところが3つ目の条件が「$p$ と $q$ の両方ではない」と言っている。
**どう値を選んでも両立しない。**これが UNSAT である。

::: {.check}
ここまでで、次を確認しておく。

- 3つの条件では `sat` が出て、$\neg r$ を足すと `unsat` になった
- `unsat` はエラーメッセージではないと説明できる
- `unsat` のときに `model()` を呼んではいけない理由を説明できる
:::

s.add(Or(Not(use["db"]), Not(use["legacy"])))   # どちらか一方は「入れない」

```console
$ python3 deps.py
```

埋める前に一度実行してみるとよい。制約を1つも足していない状態で何が返るかは、
それ自体が「制約を書いた分だけが守られる」ことの確認になる。

::: {.hint summary="ヒント1: 必須と依存の書き方"}
「`app` は必ず入れる」は、`use["app"]` という命題そのものが成り立つ、という意味である。
論理演算は要らない。そのまま `add` に渡す。

「`app` を入れるなら `gui` も入れる」は $a \to g$ である。
`Implies(条件, 結論)` の順に書く。**向きを逆にすると別の条件になる**ので注意する。
:::

::: {.hint summary="ヒント2: 択一と競合の書き方"}
「`db` か `legacy` の少なくとも一方」は $d \lor l$ である。
ただし、これは `app` を入れるときだけの要求なので、$a \to (d \lor l)$ となる。

「同時には入れられない」は「両方が真になることは無い」である。
$\neg d \lor \neg l$ と書けば、どちらか一方が偽であることを要求できる。
:::

::: {.hint summary="ヒント3: 解答"}
```{.z3py filename="deps.py（TODO(1)〜TODO(4)）"}
# TODO(1) app は必ず入れる
s.add(use["app"])

# TODO(2) 依存関係
s.add(Implies(use["app"], use["gui"]))
s.add(Implies(use["gui"], use["net"]))

# TODO(3) app を入れるなら db か legacy の少なくとも一方
s.add(Implies(use["app"], Or(use["db"], use["legacy"])))

# TODO(4) db と legacy は同時に入れられない
s.add(Or(Not(use["db"]), Not(use["legacy"])))
```

実行すると `sat` になり、`app` `gui` `net` と、
`db` か `legacy` のどちらか一方が入る組合せが返る。
どちらが返るかは決まっていない。**両方とも正しい答え**である。
:::

## 標準演習

::: {.exercise level=standard}
### 条件を足して、解を変え、`unsat` にする

`deps.py` に条件を足していく。次の2段階を自分で作る。

1. **解が変わる条件を1つ足す。** `sat` のままだが、返ってくる入れ方が変わる。
2. **さらに1つ足して `unsat` にする。** どう入れても条件を満たせない状態にする。

足す条件は自分で決める。たとえば「`db` は使えなくなった」「`net` と `legacy` は競合する」
「`legacy` は必ず入れる」など、**言葉で言える条件**にすること。

**完了条件**: 次の表が埋まっていて、それぞれの結果になる理由を
**論理式をたどって**説明できる。

| 段階 | 足した条件（日本語） | 論理式 | `check()` の結果 | 入れ方 |
|---|---|---|---|---|
| 0 | （必須演習のまま） | — | `sat` | |
| 1 | | | `sat` | |
| 2 | | | `unsat` | |

説明では「ソルバーがそう言ったから」で止めない。
**どの条件とどの条件が両立しないのか**を名指しする。

考えどころは3つある。

- 段階1で入れ方が変わったのはなぜか。変わった部分はどの条件に押されたのか。
- 段階2で両立しなくなったのは、どの条件の組み合わせか。1つ外せば `sat` に戻るか。
- 条件を足したのに結果が何も変わらないことがある。それはなぜか。
:::

::: {.hint summary="ヒント1: 解が変わる条件を作る"}
必須演習の答えでは `db` と `legacy` のどちらが入ってもよかった。
片方を禁止すれば、もう片方が入るしかなくなる。
`sat` のまま、入れ方だけが変わる。
:::

::: {.hint summary="ヒント2: 両立しない形を作る"}
`unsat` にするには、**逃げ道をすべて塞ぐ**必要がある。

- `app` は必須なので、`gui` と `net` は必ず入る（依存の連鎖）。
- `app` を入れる以上、`db` か `legacy` のどちらかは必ず入る。

したがって「`db` も `legacy` も入れられない」状態を作れば `unsat` になる。
片方を直接禁止し、もう片方を**必ず入るもの**と競合させればよい。
:::

::: {.hint summary="ヒント3: 結果が変わらないとき"}
足した条件が、すでに他の条件から**導かれている**場合、結果は何も変わらない。
たとえば `app` が必須で `app → gui` があるなら、
「`gui` は必ず入れる」を足しても新しい情報にならない。

これは失敗ではない。**制約が冗長かどうかを見分ける練習**になる。
:::

## 発展演習

::: {.exercise level=advanced}
### いずれか1つを選ぶ

**A. 「ちょうど一つ」を符号化する**

保存方式の選択肢を `db`・`legacy`・`cloud` の3つに増やし、
**ちょうど一つだけ**を選ぶ条件を書く。
「少なくとも一つ」と「高々一つ」を分けて書き、
選択肢が $n$ 個になったときに**CNF の節**（「または」で結んだ塊）がいくつ要るかを数える。
書き方は [SAT・SMT 概説](../references/logic-sat-smt.md)の「代表的な Boolean 符号化」にある。

さらに、`cloud` を選ぶなら `net` が要る、といった条件を足して、
選択肢どうしの依存がどう効くかを見る。

**B. グラフ彩色を Boolean 変数で書く**

第02回（Prolog）・第03回（MiniZinc）で解いた5地区の3彩色を、
真偽変数だけで書き直す。「地区 $d$ を色 $c$ で塗る」を1つの変数にする。

書けたら [グラフ彩色の3つの表現](../references/graph-coloring.md)と見比べる。
**先に自分で書いてから開くこと。** 見どころは次の点である。

- Prolog と MiniZinc では書かずに済んだ「1地区に1色」を、
  ここでは自分で書かなければならない。なぜか。
- 「ちょうど一つ」は「少なくとも一つ」と「高々一つ」の2つでできている。
  **片方ずつ外して**実行し、返ってきた割り当てを読む。
  外したほうによって、壊れ方が違う。
- 色を2色に減らすと `unsat` になることを確かめる。
:::

## よくある誤り

| 症状 | 原因 | 直し方 |
|---|---|---|
| `NameError: name 'Bool' is not defined` | `from z3 import *` を書いていない | ファイルの先頭に書く。`import z3` だけでは足りない |
| `unsat` なのに割り当てが表示される | `if s.check():` と書いている | `if s.check() == sat:` に直す |
| `Z3Exception: model is not available` | `unsat` なのに `model()` を呼んだ | `== sat` の中でだけ `model()` を呼ぶ |
| `Symbolic expressions cannot be cast to concrete Boolean values.` | Python の `and` / `or` / `not` を使った | `And` / `Or` / `Not` に直す |
| 何を足しても `sat` のまま変わらない | 足した条件が他の条件から導かれている | 標準演習のヒント3を見る |
| `Implies` の向きが逆で、入れ方がおかしい | 「A ならば B」の A と B を取り違えた | 日本語の「〜なら」の前が第1引数である |
| `m[use["app"]]` が `None` になる | その変数が制約に一度も出てこない | 変数を制約に入れ忘れていないか確かめる |

::: {.warning}
**`sat` が出たことは、モデルが正しいという意味ではない。**
条件を1つ書き忘れていても、ソルバーはその条件を無視した「答え」を平気で返す。
第03回・第04回の数独とまったく同じである。
返ってきた入れ方を、**元の日本語の条件と1つずつ突き合わせる**。
:::

## 次回への接続

この回では、パッケージを「入れる／入れない」の2択で表した。
現実には**版**がある。「`net` の 2 以上 4 以下」のような条件は、
真偽変数だけで表そうとすると変数が一気に増える。

第06回では、命題論理の骨組みに**整数**を足した **SMT** に進む。
`v_net >= 2` のような式をそのまま書けるようになる。
同じ依存関係の問題を Boolean で書いた場合と整数で書いた場合で比べ、
**どちらで書くかは設計の判断である**ことを確かめる。

::: {.note}
**自由課題に向けて**: 自分が考えている問題の中に、
「入れる／入れない」「使う／使わない」「選ぶ／選ばない」で言える部分があるか探す。
あるなら、その部分は Boolean 符号化に向いている。
:::
