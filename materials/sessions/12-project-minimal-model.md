# 第12回 自由課題: 最小実行モデル

## この回の目標

この回を終えると、次のことができる。

- 最小インスタンスで動くモデルまたはプログラムを示せる
- 出た解が手作業の答えと合っていることを確かめられる
- モデルと入力データを分けて持てる
- 第三者が同じ結果を再現できる手順を書ける

## 今回やること

企画書に書いた**最小インスタンス**を動かす。
この回の終わりに欲しいのは、正しくて大きいモデルではなく、
**小さくて動いて、答えが合っていると言えるもの**である。

| 時間 | 活動 |
|---|---|
| 10分 | 企画書の最小インスタンスを**確定する**（下の5点）。紙の上で答えを1つ作る |
| 15分 | 変数と定義域だけを書いて実行する（制約はまだ書かない） |
| 40分 | 制約を1本ずつ足す。1本足すたびに実行する |
| 20分 | 紙の答えと出力を突き合わせる。合わなければ制約を疑う |
| 15分 | 暫定 README を書く（[README テンプレート](../projects/readme-template.md)） |

### 最初の10分: 最小インスタンスを確定する

第11回の宿題は「最小インスタンスの入力を**数値まで**書き下す」だった。
この10分は、その数値が**そのまま `.dzn` やデータ辞書に書ける形になっているか**を見る時間である。
**ここが決まらないまま先へ進むと、100分が数値決めで終わる。**

次の5つが埋まっていれば確定である。上から順に確かめる。

| # | 確かめること | 例（勤務表を題材にした場合） |
|---|---|---|
| 1 | 要素の**個数**が全部決まっているか | 職員4人、3日 |
| 2 | 要素の**名前**が全部書いてあるか | 職員A・B・C・D、1日目・2日目・3日目 |
| 3 | 各要素に付く**値**が全部書いてあるか | 各日の必要人数、資格の有無 |
| 4 | 紙の上で**答えを1つ**作れたか | 4×3 の表を1枚、手で埋めた |
| 5 | **解が無い入力**も1つ作れたか | 必要人数の合計を人数より多くした版 |

::: {.warning}
**数値がまだ決まっていない人は、この10分で決めきる。**

決めるときの基準は「良い題材か」ではなく、**紙で答えが作れる大きさか**である。
迷ったら小さくする。第12回のあいだは、小さすぎて困ることは無い。

目安は次のとおりである。これより大きくしない。

- 割り当てる対象は**5個以下**（人・科目・地区など）
- 割り当て先は**4個以下**（テーマ・色・時間帯など）
- 日や回の軸があるなら**3以下**
- ハード制約は**3本以下**（残りは第13回で足す）

この大きさに落とせない題材は、題材のほうを見直す。第11回に戻ってよい。
:::

4 と 5 は、あとの突き合わせと第13回の検証にそのまま使う。
**紙に書いた答えは捨てずに残しておく。**

### 制約は1本ずつ足す

第10回で扱った [段階的テスト](../references/glossary.md#incremental_testing)を、
自分の問題に当てる。

1. **変数と定義域だけ**を宣言して実行する。ここで何か出れば、骨組みは通っている。
2. 制約を**1本**足して実行する。解が減ったか、形が変わったかを見る。
3. 期待どおりでなければ、**足した1本**を疑う。ほかを疑わない。
4. 2〜3を繰り返す。

::: important
**動く状態を保ったまま進む。**

一度に全部書いてから実行すると、落ちたときに疑うところが多すぎる。
1本ずつなら、直前に足した1本しか容疑者がいない。
第08回で勤務表の制約を足していった順序が、そのまま手本になる。
:::

### 紙の答えと突き合わせる

最小インスタンスの意味は、**答えを人間が知っていること**にある。

- 出た解が、紙で作った答えと一致するか。しなくてもよいが、**両方とも仕様を満たしているか**
- 解が出ないはずの入力で、本当に解が出ないか
- 解が1つしかないはずの入力で、2つ目が出ないか

これは第04回でやった [既知例による検証](../references/glossary.md#known_example_validation)と同じ手である。

### 動かないときの縮小手順

止まったら、次の順に問題を小さくする。**上から順に試す。**

| 順序 | やること | 分かること |
|---|---|---|
| 1 | 直前に足した制約をコメントアウトする | その1本が原因か |
| 2 | 制約をすべて外し、変数と定義域だけにする | 宣言そのものが通るか |
| 3 | データを減らす（人数・日数・要素数を最小まで） | 規模の問題か、記述の問題か |
| 4 | 変数を減らす（多次元を1次元に、複数の配列を1本に） | 添字の対応が合っているか |
| 5 | 期待する解を制約として固定し、`UNSAT` になるか見る | どの制約が期待解を弾いているか |

5 は特に効く。「出るはずの答え」を制約として書き足して `UNSAT` になれば、
**その答えを弾いている制約がどこかにある**と分かる。1本ずつ外せば犯人が出る。

エラー文の読み方は [よくあるエラーと対処](../references/errors.md)にある。

::: warning
**モデルを縮小したら、縮小した版を残しておく。**

動いた最小版を消して大きい版だけを持つと、
壊れたときに戻る先が無くなる。ファイル名を分けて両方置く。
:::

### 暫定 README を書く

この回の時点で README に書けるのは4つである。完成させなくてよい。

1. 実行環境（道具と版）
2. 実行手順（そのまま打てば動く形で）
3. 入力（どのファイルが何のデータか）
4. 出力（何が出れば成功か）

**自分以外の人が同じ結果を出せるか**が基準である。
書いてみると、暗黙に決めていたことが必ず1つ2つ見つかる。
