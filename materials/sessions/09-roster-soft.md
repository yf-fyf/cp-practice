## この回の目標

この回を終えると、次のことができる。

- ハード制約とソフト制約を区別し、どちらに入れるべきかを条件ごとに判断できる
- ソフト制約の違反を `bool2int` の和で数え、目的関数に入れられる
- 勤務の偏りを1つの数で表し、公平性を目的関数の一項として書ける
- 重みを変えると選ばれる勤務表が変わることを、実行結果を指して説明できる

## 今回解く問題

第08回で作った表は、3つのハード制約をすべて満たしていた。それでも問題があった。

- 7日間ずっと働く人がいた
- 夜勤を4回引き受ける人と、1回も入らない人がいた

そして、第08回では**そもそも扱っていなかった条件**がある。**希望休**である。

各職員は「この日は休みたい」という申し出を出す。かなえたいが、
必要人数を割ってまでかなえるわけにはいかない。

::: {.term}
[**ソフト制約**](../references/glossary.md#soft_constraint)とは、
破ってもよいが、なるべく避けたい条件である。

[ハード制約](../references/glossary.md#hard_constraint)は「破ったら解ではない」。
ソフト制約は「破っても解ではあるが、その解は少し悪い」。
:::

同じ条件でも、どちらに入れるかは**こちらが決めること**である。

| 条件 | この教材での扱い | もし逆にしたら |
|---|---|---|
| 各日の必要人数 | ハード | 人手が足りない日ができる |
| 夜勤の翌日は休み | ハード | 連続夜勤が起きうる |
| 希望休 | ソフト | 希望が集中した日に人がいなくなり、たいてい充足不能になる |
| 勤務の偏りを小さく | ソフト | 「完全に均等」を要求すると、割り切れないだけで充足不能になる |

::: {.important}
**全部をハード制約にすると `=====UNSATISFIABLE=====` になる。**

「守れたら嬉しい」条件までハード制約にすると、解は簡単に消える。
そして UNSAT は「どれをあきらめればよいか」を何も教えてくれない。

ソフト制約にしておけば、ソルバーは
**どれを、いくつ、あきらめたか**を数字で返してくれる。
:::

::: {.discuss}
希望休が同じ日に集中したとする。5人が同じ日に休みを希望し、
その日は4人が勤務しなければならない。

- 誰の希望をあきらめるかを、モデルはどうやって決めるのか。
- 「違反の合計が最小」でよいのか。
  1人が3回我慢するのと、3人が1回ずつ我慢するのは同じ扱いでよいか。
- 前の月に我慢した人を優先したいとしたら、モデルのどこに入れるか。
:::

## 変数・定義域・制約・目的へ分解

第08回で空だった「目的」の欄が埋まる。**変数と制約は第08回のままである。**

| 語 | この問題では |
|---|---|
| 変数 | 職員 `s` の `d` 日目の勤務（第08回と同じ） |
| 定義域 | 日勤・夜勤・休みの3つ（第08回と同じ） |
| 制約 | 必要人数・資格・休息（第08回と同じ。**ハード制約**） |
| 目的 | 希望休違反と勤務の偏りを、重みを付けて足した値を最小にする |

第07回で希望順位を得点に直したのと同じことを、**逆向き**にやる。
第07回は「良さ」を足して最大にした。この回は「悪さ」を足して最小にする。

| | 第07回 | 第09回 |
|---|---|---|
| 数えるもの | 希望順位の得点 | ソフト制約の違反 |
| 向き | `solve maximize` | `solve minimize` |
| 良い解 | 値が大きい | 値が小さい |

## 概念と構文

### 違反を数える

::: {.term}
[**違反ペナルティ**](../references/glossary.md#penalty)とは、
ソフト制約を破ったときに加える値である。
「破った回数」をそのまま数えるのが、いちばん単純な形である。
:::

希望休のデータは、日ごと・人ごとの真偽値で持つ。

```{.minizinc filename="希望休のデータ"}
array[STAFF, DAYS] of bool: want_off;      % true = その日は休みたい
```

違反は「希望休を出した日なのに、休みになっていない」ことである。

```{.minizinc filename="希望休違反の件数"}
var int: pref =
  sum(s in STAFF, d in DAYS where want_off[s, d])( bool2int(roster[s, d] != off) );
```

読み方は3段階である。

1. `where want_off[s, d]` … 希望休を出したマスだけに絞る
2. `bool2int(roster[s, d] != off)` … そのマスが休みでなければ 1、休みなら 0
3. `sum(...)` … 全部足す

::: {.note}
**ここで `count` は使えない。**

`count(配列, 値)` は「ちょうどこの値がいくつあるか」しか数えられない。
今回数えたいのは「`off` **ではない**マス」なので、
[集計](../references/glossary.md#aggregation_sum_count)の
もう一方の書き方（`sum` + `bool2int`）を使う。

`bool2int(条件)` は、条件が成り立てば 1、成り立たなければ 0 になる。
第07回では「もう1つの数え方がある」と名前だけ挙げた書き方である。
**自分で書くのはこの回が初めてになる。**
:::

### 偏りを1つの数にする

::: {.term}
[**公平性の数値化**](../references/glossary.md#fairness_metric)とは、
偏りの大きさを式で表したものである。
:::

「公平」はそのままでは式にならない。**何の偏りを見るか**を決める必要がある。

```{.minizinc filename="勤務日数と、その偏り"}
array[STAFF] of var 0..nd: works =
  [ sum(d in DAYS)( bool2int(roster[s, d] != off) ) | s in STAFF ];

var int: unfair = max(works) - min(works);       % いちばん多い人 - いちばん少ない人
```

`max(配列)` と `min(配列)` は、配列の中の最大・最小を返す。
第07回の `max(s in STUDENTS)( ... )` と同じ道具である。

同じ形で、夜勤の回数の偏りも書ける。

```{.minizinc filename="夜勤の回数と、その偏り"}
array[STAFF] of var 0..nd: nights =
  [ count([ roster[s, d] | d in DAYS ], night) | s in STAFF ];

var int: night_unfair = max(nights) - min(nights);
```

::: {.note}
**「偏り」の定義はこれ1つではない。**

- 最大と最小の差（この教材で使う）
- 目標値からのずれの合計
- いちばん多い人の値そのもの（第07回の「最大不満」と同じ形）

どれも「公平」と呼べる。**選び方によって選ばれる解が変わる。**
公平性を数値化するというのは、**どの意味の公平を採るかを決めること**である。
:::

### 重みを付けて足す

::: {.term}
[**重み付き和**](../references/glossary.md#weighted_sum)とは、
複数のペナルティ項に重みを掛けて足した目的関数である。
:::

```{.minizinc filename="目的関数"}
int: w_pref = 10;                                % 希望休違反1件あたり
int: w_fair = 1;                                 % 勤務日数の偏り1あたり

var int: penalty = w_pref * pref + w_fair * unfair;

solve minimize penalty;
```

重みは「1件の違反が、偏り1つぶんの何倍の重さか」を表す。
`w_pref = 10` は「希望休を1件あきらめるくらいなら、偏りが10増えてもよい」と
宣言したのと同じである。

::: {.warning}
**重みに正解は無い。決めるのはこちらである。**

ソルバーは重みが妥当かどうかを判断しない。書いたとおりに最小化する。
第07回で `minimize` と書けば望まない方向にも最適化したのと同じである。
:::

書き方の一覧は [MiniZinc 早見表](../references/minizinc-cheatsheet.md)にある。
この回で新しく使う構文は無い。**既に知っている道具の組み合わせ方**が中身である。

## 小さな実行例

第08回の4人・3日のデータに、希望休を足す。
職員Aが1日目と3日目、職員Cが2日目に休みを希望している。

```{.minizinc filename="mini9.mzn"}
int: ns = 4;
int: nd = 3;

set of int: STAFF = 1..ns;
set of int: DAYS  = 1..nd;

enum SHIFTS = { day, night, off };
array[SHIFTS] of string: mark = ["日", "夜", "休"];

array[STAFF] of string: sname = ["A", "B", "C", "D"];
array[STAFF] of bool: leader  = [true, false, true, false];
array[DAYS]  of int: need_day   = [2, 2, 2];
array[DAYS]  of int: need_night = [1, 1, 1];

array[STAFF, DAYS] of bool: want_off =            % 希望休
  [| true,  false, true      % 職員A: 1日目と3日目
   | false, false, false     % 職員B
   | false, true,  false     % 職員C: 2日目
   | false, false, false |]; % 職員D

int: w_pref = 10;                                 % 希望休違反1件あたり
int: w_fair = 1;                                  % 勤務日数の偏り1あたり

array[STAFF, DAYS] of var SHIFTS: roster;

constraint forall(d in DAYS)( count([ roster[s, d] | s in STAFF ], day)   = need_day[d] );
constraint forall(d in DAYS)( count([ roster[s, d] | s in STAFF ], night) = need_night[d] );
constraint forall(d in DAYS)( count([ roster[s, d] | s in STAFF where leader[s] ], night) >= 1 );
constraint forall(s in STAFF, d in 1..nd - 1)( roster[s, d] = night -> roster[s, d + 1] = off );

var int: pref =
  sum(s in STAFF, d in DAYS where want_off[s, d])( bool2int(roster[s, d] != off) );

array[STAFF] of var 0..nd: works =
  [ sum(d in DAYS)( bool2int(roster[s, d] != off) ) | s in STAFF ];

var int: unfair = max(works) - min(works);

var int: penalty = w_pref * pref + w_fair * unfair;

solve minimize penalty;

% このあとに output（表の整形）が続く。配布ファイルに書いてある。
```

`output` は結果を人が読める表に整える部分で、**書けなくてよい**。
演習ファイルの `roster_soft.mzn` に書き込んである。

読むときに要るのは1点だけである。**`*` は希望休の印**で、
`*` の付いたマスが「休」でなければ違反だから、目で数え直せる。

::: {.hint summary="output の中身を見る（読まなくてよい）"}
```{.minizinc filename="mini9.mzn（output の部分）"}
output
  [ "        " ++ concat([ show(d) ++ "日 " | d in DAYS ]) ++ "  勤務\n" ]
  ++ [ "職員" ++ sname[s] ++ "   "
       ++ concat([ (if want_off[s, d] then "*" else " " endif)
                   ++ mark[fix(roster[s, d])] ++ " " | d in DAYS ])
       ++ "   " ++ show(works[s]) ++ "\n"
     | s in STAFF ]
  ++ [ "希望休違反 = " ++ show(pref) ++ "   勤務日数の偏り = " ++ show(unfair)
       ++ "   目的関数 = " ++ show(penalty) ++ "\n" ];
```

`if ... then ... else ... endif` は式の形の条件分岐である。
ここでは `*` を出すか空白を出すかを選んでいるだけである。
:::

既定のソルバー（Gecode）で実行すると、解が2本出る。

```solver
        1日 2日 3日   勤務
職員A   *夜  休 *夜    2
職員B    休  日  日    2
職員C    日 *夜  休    2
職員D    日  日  日    3
希望休違反 = 3   勤務日数の偏り = 1   目的関数 = 31
----------
        1日 2日 3日   勤務
職員A   *休  夜 *休    1
職員B    日  日  日    3
職員C    夜 *休  夜    2
職員D    日  日  日    3
希望休違反 = 0   勤務日数の偏り = 2   目的関数 = 2
==========
```

1本目は途中経過で、3件の希望休がすべて破られている（`*` の3マスが全部勤務）。
2本目が最適解で、**希望休は3件とも通った**。`==========` が最適の印である。

その代わり、職員Aは3日のうち1日しか働かず、職員Bと職員Dは3日とも働いている。
勤務日数の偏りは 1 から 2 に増えた。**希望をかなえた分のしわ寄せである。**

## 予想してから試す

::: {.predict}
`mini9.mzn` の重みを入れ替えて実行する。

```{.minizinc}
int: w_pref = 1;                                  % 10 から 1 へ
int: w_fair = 10;                                 % 1 から 10 へ
```

何が出ると思うか。

1. さっきと同じ表が出る（目的関数の値だけが変わる）
2. 希望休違反が増える代わりに、勤務日数の偏りが小さい表が出る
3. `=====UNSATISFIABLE=====` が出る

**ハード制約は1つも変えていない**ことに注意する。
選べる表の集まりは、さっきとまったく同じである。
:::

```solver
        1日 2日 3日   勤務
職員A   *日  夜 *休    2
職員B    休  日  日    2
職員C    夜 *休  夜    2
職員D    日  日  日    3
希望休違反 = 1   勤務日数の偏り = 1   目的関数 = 11
==========
```

（途中経過の解は省いてある。最後の1本だけを載せた。）

違う表が返った。職員Aの1日目の希望休をあきらめる代わりに、
勤務日数は2日・2日・2日・3日と揃っている。

| 設定 | 希望休違反 | 勤務日数の偏り |
|---|---|---|
| 希望重視（`w_pref = 10` / `w_fair = 1`） | **0** | 2 |
| 公平重視（`w_pref = 1` / `w_fair = 10`） | 1 | **1** |

::: {.important}
**同じ問題・同じハード制約でも、重みが違えば別の表が「最適」になる。**

どちらの表も、3つのハード制約をすべて満たしている。
どちらが正しいかをソルバーは知らない。
**「良い勤務表とは何か」を決めているのは、重みを書いた人である。**
:::

ここまでで、次を確認しておく。

- `sum` + `bool2int` で「条件を満たすマスの個数」を数えられる
- `where` で数える範囲を絞れる
- `max(works) - min(works)` が何を表すか説明できる
- 重みを変えると最適解が変わることを、実行結果2本を指して説明できる
:::

**自分で決める1点**: 表の3行目は**自分で決めた重み**である。
既定の2組を試す**前に**、自分なら `w_pref` と `w_fair` をいくつにするかを決めて書き込む。

| 設定 | `w_pref` | `w_fair` | 希望休違反 | 勤務日数の偏り | 目的関数 |
|---|---|---|---|---|---|
| 希望重視 | 10 | 1 | | | |
| 公平重視 | 1 | 10 | | | |
| **自分の設定** | | | | | |

**完了条件**: 2つの設定で**違う勤務表**が返ることを確かめ、
なぜ違うのかを目的関数の値の比較で説明できる。
また、出力の `*` が付いたマスを見て、違反件数を目で数え直せる。
そのうえで、自分の設定が既定の2組の**どちらと同じ表を選んだか**を述べ、
その理由を「どちらの項を重く見たか」で1行で書く。

出力のコメントを外すのを忘れないこと（`希望休違反 = ...` の行が出るようになる）。
:::

::: {.hint summary="ヒント1: 何を数えるのか（TODO(1)）"}
数えたいのは「希望休を出した日なのに、休みになっていないマスの数」である。

まず、数える範囲を希望休のマスだけに絞る。

```{.minizinc}
sum(s in STAFF, d in DAYS where want_off[s, d])( ? )
```

`?` のところは、そのマスが違反なら 1、違反でなければ 0 になる式である。
違反とは「休みではない」ことなので、`roster[s, d] != off` が成り立つときである。

真偽値を 0 か 1 にするのは `bool2int` である。
:::

::: {.hint summary="ヒント2: 偏りの書き方（TODO(2)）"}
`works` は配布モデルの中で**すでに定義してある**。
`works[s]` が職員 `s` の勤務日数である。

偏りは「いちばん多い人」と「いちばん少ない人」の差である。
配列をそのまま `max` と `min` に渡せる。

```{.minizinc}
var int: unfair = ? - ?;
```

`penalty` の行と `solve` の行のコメントも外す。
`solve` は `satisfy` の行を消して `minimize penalty;` の行を残す。
:::

::: {.hint summary="ヒント3: 解答"}
```{.minizinc filename="roster_soft.mzn（TODO(1)(2)）"}
var int: pref =
  sum(s in STAFF, d in DAYS where want_off[s, d])( bool2int(roster[s, d] != off) );

var int: unfair = max(works) - min(works);
```

`small_pref.dzn` での結果は次のとおりである。

| 設定 | `w_pref` | `w_fair` | 希望休違反 | 勤務日数の偏り | 目的関数 |
|---|---|---|---|---|---|
| 希望重視 | 10 | 1 | 0 | 2 | 2 |
| 公平重視 | 1 | 10 | 1 | 1 | 11 |

希望重視では職員Aが1日しか働かない表が、
公平重視では職員Aの希望休を1件あきらめる表が返る。
:::

## 候補を全部並べる

`small_pref.dzn` は小さいので、**ハード制約を満たす勤務表を全部数えられる**。
`small_pref.dzn` の冒頭のコメントにあるとおり6通りしかない
（`D` が日勤、`N` が夜勤、`O` が休みである）。
下の表は、その6通りを実際に並べたものである。

| 候補 | 職員A | 職員B | 職員C | 職員D | 勤務日数 | 偏り | 希望休違反 | 希望重視の値 | 公平重視の値 |
|---|---|---|---|---|---|---|---|---|---|
| #1 | `DNO` | `DDD` | `NON` | `ODD` | 2 3 2 2 | 1 | 1 | 11 | **11** |
| #2 | `DNO` | `ODD` | `NON` | `DDD` | 2 2 2 3 | 1 | 1 | 11 | **11** |
| #3 | `NON` | `DDD` | `DNO` | `ODD` | 2 3 2 2 | 1 | 3 | 31 | 13 |
| #4 | `NON` | `DDD` | `ONO` | `DDD` | 2 3 1 3 | 2 | 3 | 32 | 23 |
| #5 | `NON` | `ODD` | `DNO` | `DDD` | 2 2 2 3 | 1 | 3 | 31 | 13 |
| #6 | `ONO` | `DDD` | `NON` | `DDD` | 1 3 2 3 | 2 | 0 | **2** | 20 |

- 希望重視の値 = `10 × 希望休違反 + 偏り` … 最小は **#6 の 2**
- 公平重視の値 = `希望休違反 + 10 × 偏り` … 最小は **#1 と #2 の 11**

ソルバーがやっているのは、この表のいちばん小さい行を選ぶことである。
**重みを変えるというのは、この表の右2列の作り方を変えること**である。

::: {.note}
公平重視では **#1 と #2 が同点**である。どちらが表示されるかはソルバー次第である。

この2つは、職員Bと職員Dの勤務が入れ替わっているだけで、
勤務日数の並びは（順番を無視すれば）まったく同じである。
**偏りという指標は「誰が」を見ていない。**
「Bさんは先週も多かった」といった事情を入れたいなら、
それは別の項として書かなければならない。
:::

::: {.discuss}
6通りしかないなら、目的関数など書かずに全部並べて選べばよいのではないか。

- 8人・7日ではハード制約を満たす表が何通りあるか、見当がつくか。
- 全部並べられないとき、「いちばん良いもの」をどうやって見つけるか。
- 目的関数を書くというのは、**選び方をソルバーに委ねるための言語**である。
:::

## 標準演習

::: {.exercise level=standard}
### 3つの項を比較できるようにして組み合わせる

データを `week_pref.dzn`（8人・7日）に差し替える。
`% TODO(3)` に夜勤回数の偏り `night_unfair` を書き、
目的関数を3項にする。

```{.minizinc filename="3項の目的関数"}
var int: penalty = w_pref * pref + w_fair * unfair + w_night * night_unfair;
```

**完了条件**: 次の表が埋まっていて、
「重みを付ける前に各項の範囲を調べるのはなぜか」を説明できる。

| 設定 | `w_pref` | `w_fair` | `w_night` | 希望休違反 | 勤務日数の偏り | 夜勤回数の偏り |
|---|---|---|---|---|---|---|
| 希望だけ | 1 | 0 | 0 | | | |
| 希望＋勤務日数 | 10 | 1 | 0 | | | |
| 3項 | 10 | 1 | 1 | | | |

進め方は3段階である。

1. **各項の範囲を調べる**。`w_pref = 1` `w_fair = 0` `w_night = 0` として
   希望休違反だけを最小にし、そのときの3つの値を記録する。
   同じように `w_fair` だけ、`w_night` だけを 1 にした場合も見る。
2. 3つの項の**大きさの桁が揃っているか**を確かめる。
   桁が違う項をそのまま足すと、重みが意味を持たなくなる。
3. 3項を足した設定を実行し、1段階目の結果と比べる。
:::

::: {.hint summary="ヒント1: 夜勤回数の偏り（TODO(3)）"}
`nights` は配布モデルの中ですでに定義してある。
勤務日数の偏りとまったく同じ形で書ける。

```{.minizinc}
var int: night_unfair = ? - ?;
```

`w_night` は `.dzn` の中にある。標準演習では `0` から `1` に変える。
:::

::: {.hint summary="ヒント2: 範囲の調べ方"}
「範囲」とは、その項が取りうる最小値と最大値のことである。
最小値は、その項だけを最小にしたときの値で分かる。

- 希望休違反: `w_pref = 1` `w_fair = 0` `w_night = 0` で実行する
- 勤務日数の偏り: `w_pref = 0` `w_fair = 1` `w_night = 0` で実行する

最大値は、データから手で見積もれる。
希望休違反の最大は `want_off` に `true` が入っているマスの数である。
偏りの最大は、日数を超えることはない。
:::

::: {.hint summary="ヒント3: 桁が違う項を足すとどうなるか"}
::: {.term}
[**正規化**](../references/glossary.md#normalization)とは、
値の範囲が違う項を、比較できるようにそろえることである。
:::

`week_pref.dzn` では、希望休違反は 0 から十数まで動くのに対し、
偏りは 0 から数までしか動かない。
重みを全部 `1` にすると、**動く幅の大きい項が勝手に優先される**。

そろえ方は2通りある。

- 各項を最大値で割る（0〜1にそろえる）。MiniZinc は整数どうしの割り算を切り捨てるので、
  この規模では**先に定数倍してから割る**必要がある
- 動く幅の比を見て、重みのほうで打ち消す（この教材ではこちらを使う）

`w_pref = 10` としているのは、後者の考え方である。
:::

### 副次の項は何をしているか

`week_pref.dzn` を3つの設定で解くと、次の結果になる。

| 設定 | 希望休違反 | 勤務日数の偏り | 夜勤回数の偏り |
|---|---|---|---|
| 希望だけ（1 / 0 / 0） | **0** | 3 | 3 |
| 希望＋勤務日数（10 / 1 / 0） | **0** | **2** | 3 または 4 |
| 3項（10 / 1 / 1） | **0** | **2** | **2** |

**希望休違反はどの設定でも 0 のままである。**
このデータでは、希望休をすべてかなえる表が存在する。

重みを掛けていない項（上の表の「3 または 4」）は、
**ソルバーによって値が違う**。目的関数が何も言っていない量は、
どうなっても構わないからである。第07回の発展演習Aで見たのと同じことである。

ところが「希望だけ」の設定では、希望休違反が 0 になる表なら
**どれでも同じ点数**なので、ソルバーは偏りの大きいものを返すこともある。
`w_fair` と `w_night` を足すと、
**同点の中でいちばん偏りの小さいものが選ばれる**ようになった。

::: {.note}
**副次の項は、同点の解の中から選ぶ役割をしている。**

`w_pref = 10` は「希望休違反1件は、偏り10ぶんより重い」という宣言である。
このデータでは偏りが 10 を超えないので、
**希望休違反は必ず優先される**。そのうえで偏りが小さいものが選ばれる。

各項の範囲を先に調べておくのは、この「必ず優先される」を
重みの大きさで保証するためである。
:::

::: {.warning}
**逆向きの設定（公平を主にする）は、この規模では最適だと確かめきれない。**

`w_pref = 1` `w_fair = 10` にして `week_pref.dzn` を解くと、
勤務日数の偏りが 1 の表はすぐ見つかるが、
**`==========` が出ないまま探索が続く**（Gecode でも Chuffed でも同じである）。
偏りを最小にしたうえで希望休違反も最小だと**証明する**のが難しいためである。

途中経過の解は正しい解である。ただし、**最適だと確かめられてはいない**。
第07回で見た `----------` と `==========` の違いがここで効いてくる。
どこまで待てばよいかは[第10回](10-roster-verification.md)で扱う。
:::

## 発展演習

::: {.exercise level=advanced}
### いずれか1つを選ぶ

**A. 辞書式最適化と重み付き和を比べる**（`small_pref.dzn` で行う）

::: {.term}
[**辞書式最適化**](../references/glossary.md#lexicographic_optimization)とは、
優先順位の高い目的から順に最適化し、
その値を固定してから次の目的を最適化する進め方である。
:::

「まず勤務日数の偏りを最小にし、**その中で**希望休違反を最小にする」を
`small_pref.dzn` で試す。

MiniZinc の `solve` に書ける目的は1つだけなので、
**優先したい項に、もう一方が絶対に逆転できない重み**を掛ける。

```{.minizinc filename="書きかけ"}
var int: lex = ? * unfair + pref;
solve minimize lex;
```

`?` に入れるべき数は、`pref` が取りうる最大値から決まる。
`small_pref.dzn` では `want_off` に `true` が3マスあるので、`pref` は3を超えない。

確かめたいこと。

- 「候補を全部並べる」の表のどの行が選ばれるか。重み付き和のときと同じか。
- 重み `w_pref = 1` `w_fair = 10` は、辞書式になっているか。
  なっていないとしたら、どのデータで差が出るか。
- 第07回の発展演習Bで書いた式と、形はどう違うか。

**B. 最適解を全部出す**（`small_pref.dzn` で行う）

`small_pref.dzn` の公平重視の設定では、同点の解が2つあった。
両方を表示させる。目的関数の値を固定してから `solve satisfy;` に戻す方法がある。

```{.minizinc filename="書きかけ"}
constraint penalty = 11;
solve satisfy;
```

Playground の「すべての解」を有効にして実行する
（[MiniZinc 実行環境の使い方](../references/setup-minizinc.md)）。
第04回で数独の複数解を数えたときと同じ手である。

確かめたいこと。

- 同点の解は何通りあるか。上の6行の表と合っているか。
- 同点の解が複数あると分かったとき、現場ではどう選ぶか。
  **それはモデルの外側の判断か、モデルに書ける条件か。**

**C. 「多すぎる分」だけを数える**（`week_pref.dzn` で行う）

偏りの代わりに、**上限を超えた分**をペナルティにする。
「夜勤は2回まで。それを超えた回数だけ数える」という書き方である。

```{.minizinc filename="書きかけ"}
int: night_cap = 2;

var int: over_night = sum(s in STAFF)(
  if nights[s] > night_cap then nights[s] - night_cap else 0 endif
);
```

`if 条件 then A else B endif` は**式**である。`endif` を忘れない。

確かめたいこと。

- `max - min` と `over_night` で、選ばれる表はどう違うか。
- `night_cap` を 3 にすると、ペナルティはどうなるか。
- **上限を超えた分を数える**のと、**上限をハード制約にする**のは何が違うか。
  どちらが `=====UNSATISFIABLE=====` になりにくいか。

**D. 連勤をソフト制約にする**（`week_pref.dzn` で行う）

第08回の発展演習Bでは「5日以上続けて働かない」をハード制約として書いた。
これをソフト制約にする。
「連続5日勤務になっている箇所の数」を数えて、ペナルティに足す。

確かめたいこと。

- ハード制約にしたときと、ソフト制約にしたときで結果はどう違うか。
- この条件は、どちらにすべきものだと思うか。**理由を1行で書く。**
:::

## よくある誤り

| 症状 | 原因 | 直し方 |
|---|---|---|
| `undefined identifier: pref` | 出力のコメントだけ外して `TODO(1)` を書いていない | 先に `pref` を定義する |
| 希望休違反がいつも 0 になる | `bool2int` の中を `= off` にした（休みの数を数えている） | `!= off` にする |
| 希望休違反が希望を出していない日でも増える | `where want_off[s, d]` を書き忘れた | `sum` の内包表記に `where` を足す |
| `unfair` がいつも 0 になる | `max(works) - max(works)` のように書いた | 片方を `min` にする |
| 重みを変えても結果が変わらない | `.dzn` を差し替えていない、または `solve` が `satisfy` のまま | `solve minimize penalty;` になっているか確かめる |
| 解が何本も出て、どれが答えか分からない | 最適化では途中経過が表示される | 最後の1本を読む。`==========` が最適の印である |
| `==========` が出ずに止まらない | 最適だと確かめるのに時間がかかる設定である | 途中経過の解は正しい。標準演習の警告を読む |
| 3項にしたら希望休違反が増えた | 重みの大きさが釣り合っていない | 各項の範囲を調べ直し、`w_pref` を大きくする |

::: {.warning}
**目的関数の値が小さいことは、勤務表として妥当だという意味ではない。**

重みの付け方を間違えていれば、ソルバーは**間違った基準で**最適化する。
その結果は、間違った基準の中では最適である。
返ってきた表を必ず目で見て、`*` の付いたマスと勤務日数の欄を確かめる。

そして、この確認そのものを別のプログラムにやらせるのが[第10回](10-roster-verification.md)である。
:::

## 次回への接続

この回で得た表は、目的関数の値がいちばん小さい表である。
ただし、それは**書いた制約と書いた目的関数の中でいちばん**という意味でしかない。

- 資格制約を書き忘れていたら、資格を無視した中での最適解が返る
- `!=` を `=` と書き間違えていたら、逆の意味で最適化された表が返る
- どちらの場合も、ソルバーはエラーを出さない

[第10回](10-roster-verification.md)では、**モデルとは別のプログラム**で表を検査する。
配布モデルの `output` に `#size` `#shift` で始まる行が入っているのは、
そのためである。あの行は人ではなく**プログラムが読むため**に出している。

第10回でやることは3つである。

1. Python の検証器で、出力された表がハード制約を満たすか独立に確かめる
2. わざと違反を含む表を食わせて、検証器が見つけられることを確かめる
3. 7日を14日に増やして、実行時間がどう変わるかを測る

::: {.note}
**自由課題に向けて**: 自分の問題のソフト制約を2つ挙げ、
それぞれに仮の重みを付けてみる。
そのあと「この2つの重みの比は、何と何を天秤にかけているか」を1行で書く。
**書けないなら、その重みはまだ決まっていない。**
:::
