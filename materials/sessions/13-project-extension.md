# 第13回 自由課題: 制約追加、最適化、検証

## この回の目標

この回を終えると、次のことができる。

- 最小モデルに制約または目的関数を足し、標準規模の入力で実行できる
- 足した制約が意図どおり働いていることを、反例を使って示せる
- モデルとは独立した方法で、出た解が仕様を満たすことを確かめられる
- 検証の結果を、後から読める形で記録できる

## 今回やること

::: {.important}
**この回の最低ライン**

この回でやることは多い。全部に手が届かなくてよい。
**次の2つが済んでいれば、この回は達成である。**

1. **ハード制約1本を、モデルの外から独立に検査するコード（または手順）がある**
2. **その検査に引っかかる反例を1つ作り、実際に「不合格」と出ることを確かめた**

**この2つを先に片づける。**下の時間表でも最初の40分に置いてある。
制約を足すのは、そのあとである。

**目的関数は任意である。**「条件を満たす解が1つ欲しいだけ」の問題なら、
ソフト制約も目的関数も足さなくてよい。
その分の時間は、制約を足すか規模を上げるか、検証を厚くするかに使う。

規模拡大が途中で止まっても、実験記録に「どこまで解けたか」を書けば結果である
（[第10回](10-roster-verification.md)で扱ったとおり、正しさと速さは別に評価する）。
:::

第12回で動いた最小モデルを育てる回である。育て方は2方向ある。

| 方向 | 中身 |
|---|---|
| **広げる** | 制約を足す。ソフト制約と目的関数を足す。入力規模を上げる |
| **確かめる** | 足したものが働いていることを、正常例と反例で示す |

**この2つは交互に行う。**まとめて広げてからまとめて確かめるのではない。
そして**「確かめる」から始める。**最低ラインが最後に回ると、
遅れた人ほど手が届かなくなるからである。

| 時間 | 活動 |
|---|---|
| 10分 | 検査するハード制約を1本選び、反例に使う入力を決める |
| 30分 | **最低ライン**: その1本の独立した検査を書き、反例で「不合格」が出ることを確かめる |
| 20分 | 残りの制約を1本ずつ足し、そのたびに最小インスタンスで実行する |
| 20分 | ソフト制約と目的関数を足す。目的が無い問題は規模拡大に充てる |
| 20分 | 標準規模の入力で実行する。時間がかかるようなら規模を戻す。実験記録に書く |

### 制約を足す

第08回から第09回への進み方が手本になる。

1. **ハード制約を全部そろえる。**まず「解として認めてよいか」を決めきる。
2. **次にソフト制約を足す。**破ってよいが避けたい条件を、
   [違反ペナルティ](../references/glossary.md#penalty)として数える。
3. **最後に目的関数を1本立てる。**複数の項があるなら
   [重み付き和](../references/glossary.md#weighted_sum)にする。
   項ごとに値の範囲が違うときは、比較できるように揃える（第09回の正規化）。

::: warning
**目的関数を足すと、急に終わらなくなることがある。**

第10回で見たとおりである。`==========`（最適だと確かめた印）が
出ないまま止まらないなら、次のどれかを行う。

- 入力規模を1段戻す
- 目的関数の項を減らす（重みを `0` にするだけでよい）
- 打ち切って、そこまでの最良解を使う（**最適とは書かない**）

どれを選んでも、**選んだことを実験記録に書く**。
「速くなった」のではなく「問いを易しくした」場合があるからである。
:::

### 確かめる

**この回はここから始める**（時間表の最初の40分）。
第10回で扱った検証を、自分の問題に当てる。
道具は変わっても、見るところは同じである。

| 見るところ | 具体的に |
|---|---|
| **正常例** | 答えが分かっている入力で、期待どおりの解が出るか |
| **反例** | 解が無いはずの入力で、本当に「解なし」になるか |
| **制約の効き** | 制約を1本外したとき、外した条件に違反する解を**探しに行くと見つかるか** |
| **独立した検査** | モデルの外側（Python など）で、出た解を条件と照らせるか |

3つ目が最も見落としやすい。
**書いたつもりの制約が実は何も縛っていない**ことは珍しくない。

::: warning
**外して結果が変わらなかった、では判定できない。**

ソルバーが返すのは条件を満たす解の1つであって、解の全体ではない。
制約を外しても**たまたま同じ解を返す**ことがある。
これだけで「働いていない」と決めつけない。
:::

**確かめ方**は、制約 `H` に違反する解を**能動的に探す**ことである。

1. `H` をコメントアウトする。
2. **`H` の否定**を一時的な制約として足す（「`H` を破った解を出せ」と頼む）。
   否定が書きにくいなら、`H` が禁じているはずの値を**出力に固定**するか、
   違反の件数を数えて `solve maximize` で最大化してもよい。
3. 違反する解が**出た** → `H` は効いている。`H` を戻すと、その解が消えることも確かめる。
4. `=====UNSATISFIABLE=====` になった → `H` は**他の制約から導かれている**（冗長である）か、
   探し方が足りていない。**この時点では未作動と断定しない。**

4 は失敗ではない。すでに導かれている条件を書くのは誤りではなく、
[第05回](05-sat-dependencies.md#標準演習)のヒント3で扱ったとおり、
**結果が変わらないこと自体が「冗長かどうか」の情報**である。
冗長だと分かったら、企画書に「この条件は他から導かれる」と1行書いておく。

::: important
**独立した検査は、モデルを見ずに仕様から書く。**

モデルを見ながら検査を書くと、モデルと同じ間違いを写してしまう。
企画書の制約一覧を見ながら、1条件につき1つの検査関数を書く。

MiniZinc を使っているなら、解を機械可読な行として出力し
（第09回の `#shift` のような形）、Python で読んで検査する。
Z3 を使っているなら、`model` から値を取り出して同じ Python の関数へ渡す。
どちらも `workbook/projects/verify.py` の雛形が骨格を持っている。
:::

### 記録する

確かめたことは、その場で [実験記録](../projects/verification-checklist.md)へ書く。
後からまとめて書き起こすことはできない。何を試したか忘れるからである。

1行に「入力・設定・結果・確認方法」を書く。
第14回の実験は、この表をそのまま伸ばしたものになる。

## 扱わないこと

- **企画書に無い制約・新しい機能の追加** → 第14回の初めで凍結する。
  企画書に無いものは「今後の課題」に回す
  （**企画書で合意済みのハード制約**は、この回で入れきれなくても第14回で足してよい）
- **発表資料の作成** → 第14回
- **ソルバーの内部アルゴリズム・探索アノテーション** → この科目では扱わない。
  行き詰まったら別のソルバーを試すのは正当な手である
  （[MiniZinc 実行環境の使い方](../references/setup-minizinc.md)）
- **モデルの自動的な検証**（モデル間の同値性検査） → この科目では扱わない

## 次回への接続

第14回は、複数の条件・複数の規模で実験し、結果とモデルの限界を言葉にする。
成果物一式を第三者が再現できる形に整え、発表資料の初版を作る。

次回までに、**比べたい条件を2つ以上決めておく**。
「重みを変える」「規模を変える」「制約を1本外す」のいずれでもよい。
比べる相手が無いと、実験は1回の実行で終わってしまう。
