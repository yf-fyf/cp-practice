## この回の目標

この回を終えると、次のことができる。

- 必ず満たすハード制約と、良さを測る目的関数を区別できる

### MiniZinc の復習（冒頭5分）

MiniZinc に触るのは第04回以来、2週間ぶりである。
**新しい構文に入る前に、次の骨格を1本読み返す。**これだけ思い出せば足りる。

```{.minizinc filename="第04回までに書いたモデルの骨格"}
include "globals.mzn";          % 大域制約を使うときに要る

int: n;                         % パラメータ（.dzn から値をもらう）
set of int: ROWS = 1..n;        % 添字集合

array[ROWS, ROWS] of var 1..n: x;   % 決定変数（var が付く）

constraint forall(r in ROWS)( all_different([ x[r, c] | c in ROWS ]) );

solve satisfy;                  % 解き方の指定

output [ show(x) ];             % 表示（書けなくてよい）
```

| 見るところ | 思い出すこと |
|---|---|
| `int: n;` に `var` が無い | **パラメータ**。すでに決まっている値。`.dzn` から受け取る |
| `var 1..n` の `var` | **決定変数**。ソルバーに決めてもらうもの。`1..n` が定義域 |
| `[ x[r, c] \| c in ROWS ]` | **内包表記**。「`c` を動かして作った列」を1つの配列にする |
| `forall(...)` | 中の条件を、動かす範囲すべてについて要求する |
| `solve satisfy;` | 「条件を満たす解を1つ」。この回で `solve maximize` に変わる |

**この回で新しいのは最後の1行だけ**である。`solve satisfy;` が
`solve maximize <式>;` になると、ソルバーは「条件を満たす解」ではなく
「条件を満たすもののうち、その式がいちばん大きい解」を探す。

構文の一覧は [MiniZinc 早見表](../references/minizinc-cheatsheet.md)にある。

## 今回解く問題

ここまでの5回は、どれも「条件を満たすものを1つ見つける」問題だった。
数独の解は条件を満たせばそれで完成であり、
パッケージの入れ方も、条件さえ満たせばどれでもよかった。

この回で扱うのは違う。**条件を満たす答えがたくさんあり、その中に良し悪しがある**問題である。

架空の設定として、何人かを研究テーマへ割り当てる。
各テーマには定員があり、各人はテーマを希望順に並べている。
（この科目のために作ったデータであり、実在の希望調査ではない。）

必ず守ることは次の2つである。

1. 全員をちょうど1つのテーマへ割り当てる
2. どのテーマにも、定員を超える人数を割り当てない

::: {.term}
[**ハード制約**](../references/glossary.md#hard_constraint)とは、
**破ったら解として認められない**条件である。
上の2つは、どんなに希望がかなっていても、破っていれば答えではない。

これに対して「なるべく守りたいが、破ってもよい」条件もある。
**ソフト制約**といい、[第09回](09-roster-soft.md)で扱う。
この回で扱うのはハード制約だけである。
:::

これだけなら答えは山ほどある。そこで「どれが良い割当てか」を決める尺度が要る。
希望順位を点数に直して、次のように測る。

| 割り当てられたテーマ | 得点 |
|---|---|
| 第1希望 | 3点 |
| 第2希望 | 2点 |
| 第3希望 | 1点 |
| 第4希望 | 0点 |

問いは2つある。

- **合計点をいちばん大きくする割当ては何か。**
- **いちばん低い点になった人を、なるべく引き上げる割当ては何か。**

この2つは同じ答えになるとは限らない。そこがこの回の中心である。

::: {.discuss}
6人を3つのテーマ（定員2）へ割り当てるとする。
4人が同じテーマを第1希望にしていたら、何が起きるか。
「全員が納得する割当て」は必ずあると言えるだろうか。
:::

## 変数・定義域・制約・目的へ分解

第03回で決めた語彙を当てる。**この回で初めて「目的」の欄が埋まる。**

| 語 | この問題では |
|---|---|
| 変数 | 各人について「どのテーマへ割り当てるか」 |
| 定義域 | テーマの番号（`1..nt`） |
| 制約 | 定員（1つのテーマに `cap` 人まで） |
| 目的 | 合計点を最大にする（または、いちばん悪い順位を最小にする） |

::: {.term}
[**最適化**](../references/glossary.md#optimization)とは、
制約を満たす解のうち、[**目的関数**](../references/glossary.md#objective_function)の値が
最も良いものを探すことである。

目的関数は「良さ」を1つの数で表した式であり、**「良い解」の定義そのもの**である。
:::

::: {.important}
**「全員をちょうど1つのテーマへ」は、制約として書かない。**

1人につき変数を1つ用意し、その値をテーマ番号にする。
変数は値を1つしか取れないので、「2つのテーマに入る」ことも
「どこにも入らない」ことも、この書き方では起こりようがない。

第03回の数独で、1マスに数字が1つしか入らなかったのと同じである。
**表現の選び方が、制約を1つ減らしている。**
:::

### 実行可能解と最適解

::: {.term}
- [**実行可能解**](../references/glossary.md#feasible_solution): すべてのハード制約を満たす解。
  良し悪しは問わない
- [**最適解**](../references/glossary.md#optimal_solution): 実行可能解のうち、
  目的関数の値が最も良いもの。**複数あることもある**
:::

`solve satisfy;` が返すのは実行可能解の1つである。
その中で目的関数の値が良いか悪いかは、ソルバーの知ったことではない。
良いものが欲しいなら、**何が良いのかを式で伝える**必要がある。

## 概念と構文

### 割当てを表す決定変数

```{.minizinc filename="割当変数"}
set of int: STUDENTS = 1..ns;
set of int: THEMES   = 1..nt;

array[STUDENTS] of var THEMES: assign;      % assign[s] = s に割り当てるテーマ
```

第03回の数独は `array[ROWS, COLS] of var 1..n` という2次元だった。
今回は1次元で、**添字が人、値がテーマ**である。

### 定員をどう数えるか

::: {.term}
[**定員制約**](../references/glossary.md#capacity_constraint)とは、
1つの選択肢に割り当てられる個数の上限を定める条件である。
:::

「テーマ `t` に割り当てられた人数」を数える必要がある。
[**集計**](../references/glossary.md#aggregation_sum_count)は `count` で書く。

```{.minizinc filename="数える"}
count(assign, t)                                   % 配列 assign の中の t の個数
```

「数える」という意図がそのまま名前になっている。この回で使うのはこれだけである。

::: {.note}
数え方はもう1つある。`sum(s in STUDENTS)( bool2int(assign[s] = t) )` と書くと、
「条件が成り立つ個数」を足し算として書ける
（`bool2int(条件)` は成り立てば 1、成り立たなければ 0）。
数えた値をそのまま重み付き和へ入れられるので、
[第09回](09-roster-soft.md)のペナルティではこちらを使う。
**この回では `count` だけでよい。**書き方は
[MiniZinc 早見表](../references/minizinc-cheatsheet.md)の「集計と数え上げ」にある。
:::

### 得点表は配布モデルに書いてある

希望順位のデータ `rank[s, t]`（「s は t を第何希望にしたか」）は、
そのままでは足し算できない。第1希望が `1`、第4希望が `4` で、
**良いほど小さい数**になっているからである。そこで先に得点へ直しておく。

この変換は `assign.mzn` に**すでに書いてある**。読むだけでよい。

```{.minizinc filename="assign.mzn（配布済み）"}
array[STUDENTS, THEMES] of int: score =
  array2d(STUDENTS, THEMES, [ point[rank[s, t]] | s in STUDENTS, t in THEMES ]);
```

`point[1]` が第1希望の得点、`point[2]` が第2希望の得点なので、
`point[rank[s, t]]` が「s を t に割り当てたときの得点」になる。
`array2d` は、内包表記で作った1次元の並びを2次元の表に畳むためのものである。

::: {.note}
**この回で自分で書くのは、定員制約と合計と `solve maximize` の3か所だけ**である。
表を作る手間は配布モデルが引き受けてある。この回の中心は
「目的を式で伝えると答えが変わる」ことであって、表作りではない。
:::

### 決定変数を添字に使う

```{.minizinc filename="合計満足度"}
var int: total = sum(s in STUDENTS)( score[s, assign[s]] );
```

`score` はパラメータの配列だが、**添字の `assign[s]` は決定変数**である。
MiniZinc はこれを許す。「割り当て先が決まれば得点も決まる」という関係を、
そのまま書ける。

### 目的を伝える

```{.minizinc filename="solve の3つの形"}
solve satisfy;                  % 条件を満たすものを1つ
solve maximize total;           % total がいちばん大きいもの
solve minimize penalty;         % penalty がいちばん小さいもの
```

::: {.important}
**最適化では、途中経過の解が次々と表示される。**

ソルバーは「まず1つ見つけて、それより良いものを探し、また見つけたら表示する」
という進み方をする。出力欄に何本も解が並ぶのはそのためである。

- **最後に出た解が最適解**である
- 末尾の `==========` が「もう良いものは無いと確かめた」という印である

`==========` が出ずに止まった場合、その解は最適だと**確かめられていない**
（[MiniZinc 実行環境の使い方](../references/setup-minizinc.md)の区切り記号の表）。
:::

書き方の一覧は [MiniZinc 早見表](../references/minizinc-cheatsheet.md)にある。
**この回で自分で書く新しい構文は `count` / `sum` / `solve maximize` の3つだけ**である
（`max` は発展演習 A で使う）。

## 小さな実行例

4人を2つのテーマ（定員2）へ割り当てる。
1番から3番はテーマAが第1希望、4番だけがテーマBを第1希望にしている。
得点は第1希望2点、第2希望1点とする。

```{.minizinc filename="mini.mzn"}
int: ns  = 4;
int: nt  = 2;
int: cap = 2;

set of int: STUDENTS = 1..ns;
set of int: THEMES   = 1..nt;
set of int: RANKS    = 1..nt;

array[THEMES] of string: tname = ["テーマA", "テーマB"];
array[RANKS]  of int: point = [2, 1];

array[STUDENTS, THEMES] of RANKS: rank =
  [| 1, 2      % 1番: A が第1希望
   | 1, 2      % 2番: A
   | 1, 2      % 3番: A
   | 2, 1 |];  % 4番: B

array[STUDENTS] of var THEMES: assign;

constraint forall(t in THEMES)( count(assign, t) <= cap );

array[STUDENTS, THEMES] of int: score =
  array2d(STUDENTS, THEMES, [ point[rank[s, t]] | s in STUDENTS, t in THEMES ]);

var int: total = sum(s in STUDENTS)( score[s, assign[s]] );

solve maximize total;

output [ show(s) ++ "番 -> " ++ tname[fix(assign[s])] ++ "\n" | s in STUDENTS ]
    ++ [ "合計満足度 = " ++ show(total) ++ "\n" ];
```

実行すると、解が2本出る。

```solver
1番 -> テーマB
2番 -> テーマB
3番 -> テーマA
4番 -> テーマA
合計満足度 = 5
----------
1番 -> テーマB
2番 -> テーマA
3番 -> テーマA
4番 -> テーマB
合計満足度 = 7
==========
```

1本目は**実行可能解**である。定員は守れているが、
4番がわざわざ第2希望のテーマAに入っていて、もったいない。
2本目が**最適解**で、`==========` が「これ以上は無い」という印である。

::: {.note}
`solve satisfy;` に戻して実行すると、1本目のような解が1つだけ出て終わる。
定員は守られているので、それも**正しい答え**である。
良いか悪いかを聞いていないだけである。
:::

## 予想してから試す

::: {.predict}
上のモデルの `solve maximize total;` を `solve minimize total;` に変えて実行する。
何が出ると思うか。

1. 同じ割当てが出る（合計7）
2. 合計がいちばん小さい割当てが出る
3. `=====UNSATISFIABLE=====` が出る
4. エラーになって止まる

選んだ理由も一緒に書き出してから実行する。
**目的関数は「良さ」の定義そのものである**ことを思い出すとよい。
:::

```solver
1番 -> テーマB
2番 -> テーマB
3番 -> テーマA
4番 -> テーマA
合計満足度 = 5
==========
```

合計がいちばん小さい割当てが返った。
ソルバーは「良い割当て」を知らない。**こちらが式で伝えた通りに動く。**
`minimize` と書けば、こちらが望まない方向にも同じ精度で最適化する。

::: {.check}
ここまでで、次を確認しておく。

- 実行可能解と最適解の違いを、上の2本の出力を指して説明できる
- `----------` と `==========` の違いを説明できる
- 目的関数を変えると答えが変わることを、実行結果で確かめた
:::

## 必須演習

::: {.exercise level=required}
### 全員を定員内で割り当てる

`workbook/sessions/07-theme-assignment/assign.mzn` を Playground で開き、

**完了条件**: 実行して割当てが1つ表示され、出力の「人数」の行で
どのテーマも定員以下になっている。
さらに、「全員がちょうど1つのテーマに入っている」ことが
**制約を1つも書かずに保証されている理由**を説明できる。

**自分で決める1点**: 書いた `<= cap` を `= cap`（ちょうど定員）に変えて、
もう一度実行する。`small.dzn` では**結果が変わらない**。
「なぜ変わらないのか」と「それでも `<= cap` と書くべきなのはなぜか」を、
それぞれ1行で書く。確かめ終わったら `<= cap` に戻す。

TODO を埋める前に一度実行してみるとよい。
定員制約が無い状態では、**全員が同じテーマに入った割当て**が返る。
第03回・第05回と同じで、**制約を書いた分だけが守られる**ことの確認になる。
:::

::: {.hint summary="ヒント1: 何を数えるのか"}
定員は「テーマごと」の条件である。
まずテーマを1つ固定して、そのテーマに入っている人数を数える。

`assign` はテーマ番号が並んだ配列なので、
「テーマ `t` に入っている人数」は「`assign` の中に `t` がいくつあるか」である。

テーマを全部について回すのは `forall` である。
:::

::: {.hint summary="ヒント2: 比較の向き"}
数えた人数と `cap` を比べる。比較は `<= cap` である。
`= cap`（ちょうど）にはしない。
このデータではたまたま同じ結果になるが、
「定員」は上限であって、埋めきる義務ではない。
:::

::: {.hint summary="ヒント3: 解答"}
```{.minizinc filename="assign.mzn（TODO(1)）"}
constraint forall(t in THEMES)( count(assign, t) <= cap );
```

`small.dzn` は6人・3テーマ・定員2 なので、どのテーマもちょうど2人で埋まる。
表示される割当ては実行可能解の1つであり、**良い割当てとは限らない**。
:::

## 標準演習

::: {.exercise level=standard}
### 合計満足度を最大にする

`assign.mzn` の `% TODO(2)` を埋め、
`solve satisfy;` を `solve maximize` に変える。
得点表 `score` は配布モデルに書いてあるので、**書くのは合計の1行と `solve` の1行**である。
`small.dzn` で動かしてから、**モデルを1文字も変えずに** `medium.dzn`
（12人・4テーマ・定員3）へ差し替える。

**完了条件**: 次の表が埋まっていて、`small.dzn` の最適解について
「なぜこれ以上上げられないか」を希望データと対応付けて説明できる。

| データ | 合計満足度の最適値 | 第1希望の人数 | いちばん悪い順位 |
|---|---|---|---|
| `small.dzn` | | | |
| `medium.dzn` | | | |

考えどころは3つある。

- `small.dzn` では、6人のうち何人が第1希望に入れたか。
  入れなかった人は、**どの条件に押されて**入れなかったのか。
- 出力に解が何本も並ぶ。最後の1本以外は何なのか。
- `medium.dzn` では、いちばん悪い順位が `small.dzn` より悪くなる。
  合計が最大なのに、それでよいのか。
:::

::: {.hint summary="ヒント1: score を読む"}
配布モデルの `score[s, t]` は「s を t に割り当てたときの**得点**」である
（順位ではない。第1希望なら `point[1]`）。

まず `small.dzn` の `rank` と `point` を見て、
`score[1, 1]` と `score[1, 2]` がそれぞれいくつになるかを手で計算してみる。
ここが分かれば、あとは足すだけである。
:::

::: {.hint summary="ヒント2: 合計の書き方と solve"}
合計は、全員について「割り当てられたテーマの得点」を足したものである。
割り当てられたテーマは `assign[s]` なので、その人の得点は `score[s, assign[s]]` である。

```{.minizinc}
var int: total = sum(s in STUDENTS)( ? );
```

`var int` と書くのは、`assign` が決定変数なので `total` の値も
解が決まるまで決まらないからである。

最後に `solve satisfy;` を `solve maximize total;` に変える。
:::

::: {.hint summary="ヒント3: データを差し替える"}
第04回と同じである。**モデルは触らない。**
Playground でデータファイルのタブを増やし、実行時に `medium.dzn` を選ぶ。
画面の操作が見つからないときは、`medium.dzn` の中身を
モデルの末尾に貼り足しても同じことができる
（そのときは `small.dzn` の分を消す）。

`ns` `nt` `cap` `point` `rank` `tname` を**モデル側で値なしに宣言**してあるので、
データを替えるだけで規模が変わる。
:::

## 二つの目的関数を比べる

`medium.dzn`（12人・4テーマ・定員3）で合計満足度を最大にすると、
合計は **32点**になる。順位の内訳は次のとおりである。

```solver
順位  第1希望: 10人  第2希望: 0人  第3希望: 2人  第4希望: 0人
合計満足度 = 32   最大不満 = 3
```

12人のうち10人が第1希望に入れた。**とても良い結果に見える。**
ところが、残った2人は第2希望も通らず、**第3希望**まで落ちている。

::: {.term}
[**合計の目的と最大の目的**](../references/glossary.md#total_vs_max_objective)は違う。

- **合計満足度**を最大にする ＝ 全体としての得の総量を大きくする（効率）
- **いちばん悪い順位**を最小にする ＝ 最も損をした1人を引き上げる（公平）

合計を最大にすると、**一部が極端に損をする解**が選ばれることがある。
1人が3点損しても、他の3人が1点ずつ得をすれば合計は変わらないからである。
:::

同じデータで「いちばん悪い順位」を最小にすると、結果はこうなる。

```solver
順位  第1希望: 6人  第2希望: 6人  第3希望: 0人  第4希望: 0人
合計満足度 = 30   最大不満 = 2
```

並べると違いがはっきりする。

| | 合計満足度を最大にする | いちばん悪い順位を最小にする |
|---|---|---|
| 合計満足度 | **32** | 30 |
| いちばん悪い順位 | 第3希望 | **第2希望** |
| 第1希望の人 | **10人** | 6人 |
| 第2希望の人 | 0人 | 6人 |
| 第3希望の人 | 2人 | **0人** |

合計を2点下げる代わりに、第3希望の2人が消えて全員が第2希望以内に収まった。
その代わり、第1希望に入れた人は10人から6人に減っている。

::: {.discuss}
**どちらが公平だろうか。**

- 「10人が第1希望に入れたのだから、そちらが良い」と言えるか。
- 「2人だけが割を食うのはおかしい」と言えるか。
- あなたがこの2人の片方だったら、どちらの割当てを受け入れるか。
  割り当てる側だったらどうか。

正解は無い。**目的関数を決めるというのは、この問いに答えを出すこと**である。
モデルの外側で決めなければならないことがある、という例でもある。
:::

::: {.note}
`small.dzn` では、この2つの目的が**同じ割当てを選ぶ**。
合計17点の最適解が、同時にいちばん悪い順位も最小にしている。
**目的関数が違えば必ず答えが違う、というわけではない。**
違いが出るかどうかはデータによる。
:::

## 発展演習

::: {.exercise level=advanced}
### いずれか1つを選ぶ

**A. いちばん悪い順位を最小にする**

上の比較表の右列を、自分のモデルで再現する。
「いちばん悪い順位」は、全員の順位のうち最大のものである。

```{.minizinc filename="書きかけ"}
var RANKS: worst = max(s in STUDENTS)( ? );
```

`max(i in S)( 式 )` は `sum` と同じ形で書ける。
書けたら `solve minimize worst;` にして実行する。

確かめたいこと。

- 得られた合計満足度は、標準演習の32点よりいくつ下がったか。
- **同じ結果になるとは限らない。**もう一度実行したり、
  ソルバーを替えたりすると合計が変わることがある。なぜか。
  （ヒント: `minimize worst` は合計について何も言っていない。）

**B. 辞書式最適化**

Aで見つけた問題を直す。
「まずいちばん悪い順位を最小にし、**その中で**合計満足度を最大にする」
という二段構えにしたい。

MiniZinc の `solve` に書ける目的は1つだけである。
2つの目的を1つの式にまとめるには、
**優先したい方に、もう一方が絶対に逆転できないほど大きな重みを掛ける**。

`total` が取り得る最大値を考えれば、掛けるべき重みの大きさが決まる。
式を1つ書いて実行し、合計が安定することを確かめる。

::: {.note}
これが[**辞書式最適化**](../references/glossary.md#lexicographic_optimization)の考え方である。
重みの設計そのものは[第09回](09-roster-soft.md)で扱う。
:::

**C. 特定の条件を持つ人を分散させる**

`medium.dzn` の1番から4番までが同じ分野の経験者だとする
（この演習のための架空の区分である）。
経験が1つのテーマに固まらないよう、
**1つのテーマに経験者は高々1人**という制約を足す。

確かめたいこと。

- 合計満足度は、制約を足す前と比べていくつ下がったか。
- **制約を足すと目的関数の値は良くならない**（同じか悪くなる）。
  なぜそう言い切れるか。
- この条件は、ハード制約として書くべきものか。
  それとも「なるべく分散」というソフト制約にすべきものか
  （ソフト制約の書き方は[第09回](09-roster-soft.md)で扱う。ここでは考えるだけでよい）。
:::

## よくある誤り

| 症状 | 原因 | 直し方 |
|---|---|---|
| 全員が同じテーマに入る | 定員制約を書いていない | `TODO(1)` を埋める |
| `=====UNSATISFIABLE=====` になる | 定員の合計が人数より少ない | `cap * nt >= ns` を確かめる |
| `type error: no function or predicate with this signature` | `count` に渡した配列と値の型が合っていない | `count(assign, t)` の `t` は `THEMES` の要素にする |
| `total` が順位の合計になっていて、`maximize` すると悪い割当てが出る | `score[s, assign[s]]` ではなく `rank[s, assign[s]]` を足している | 順位は「小さいほど良い」、得点は「大きいほど良い」。足すのは `score` のほうである |
| 解が何本も出て、どれが答えか分からない | 最適化では途中経過が表示される | 最後の1本を読む。`==========` が最適の印である |
| `==========` が出ない | 打ち切られた | この回の規模では起きない。起きたらモデルを疑う |
| `output` で `assign[s]` を添字に使うと型エラー | 決定変数のまま添字に使った | `output` の中では `fix(assign[s])` にする |
| `medium.dzn` に替えたのに結果が変わらない | データファイルが選ばれていない | 実行時のデータの選択を確かめる。貼り足す方式なら古い方を消す |

::: {.warning}
**最適解が出たことは、モデルが正しいという意味ではない。**
定員を書き忘れていても、ソルバーは「その条件を無視した中での最適解」を返す。
返ってきた割当てを、**出力の「人数」の行で必ず確かめる**。
第03回から第06回までとまったく同じである。
:::
