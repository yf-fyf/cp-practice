# 第08回　希望の上限と、最小化する指標

勤務できる人だけで人数を揃えた勤務表にも、休みの希望や日数の偏りという違いがある。希望違反と勤務日数の差を数にして比べ、重みで選ぶ方法から、「違反はここまで」と保証する条件の書き方へ進む。

## 目標 {.unnumbered}

この回では、必須条件を守る勤務表の中で何を改善するかを考える。表から評価値を読み取り、目的を変えた結果について、次の三つを説明できるようになろう。

- 勤務できない日と、勤務可能だが休みたい日を区別できる。
- 希望違反V・全員の日数差F・重み付きの評価値Jを計算できる。
- 違反上限を制約に置き、その範囲で日数差を最小化できる。

第06回の和と最小化、第07回の0/1勤務表を使う。[技能なしの基本モデル](../../../workbook/sessions/08-preferences/roster-basic.mzn)と[5人の入力](../../../workbook/sessions/08-preferences/practice.dzn)を再配布する。前の必修の完成は不要で、技能・周期の条件も使わない。最大・最小の記法はこの回で説明する。操作は[入力と結果の確認手引き](guides/preferences-check.md)で授業内に確認できる。

説明・実演に50分、[5. 演習](#演習)に45分、振り返りに5分を使う。必修1は15分、必修2は25分、残り5分は確認の目安である。通常演習の提出・宿題・完了報告はなく、教員の完了承認も待たない。発展は選んで取り組む。

## 問題

勤務の可否は、表が必ず守る条件である。一方、休みたいという希望は、必要な人数を揃えるためにかなわないこともある。まず二種類の入力を別々に読み、どちらが選択を禁止するかを確かめよう。

::: {.given label="条件と入力"}
5人A〜Eの4日間の勤務を決める。一人一日について勤務するかしないかを選び、各日ちょうど2人、一人の勤務は合計2日以下とする。勤務可能性が0の位置では勤務させない。

各欄は左から1・2・3・4日目の値。勤務可能性の1は勤務可能、休み希望の1は休みたいことを表す。希望の0は休みの希望なしであり、出勤の義務ではない。

| 人 | 勤務可能性（1〜4日） | 休み希望（1〜4日） |
|---|---|---|
| A | 1 1 0 1 | 0 0 0 0 |
| B | 1 0 1 1 | 0 0 0 0 |
| C | 0 1 1 1 | 0 0 0 0 |
| D | 1 1 1 0 | 0 0 0 0 |
| E | 1 1 1 1 | 1 1 1 1 |

休み希望のある位置で勤務した回数の合計をV、全員の勤務日数の最大と最小の差をFとする。非負の整数重みα・βを使い、J=αV+βFを最小にする。重みは(1,0)、(1,1)、(1,2)を別々に試す。
:::

Eは4日とも勤務可能なので、選ぶこと自体は禁止されていない。Eが1日勤務すると希望違反は1回になる。この区別を保つため、勤務可能性と休み希望を同じ表へ上書きしない。

## 定式化

勤務表の条件をそのまま残し、表に応じて決まる指標を追加する。指標の定義と、どの指標を小さくするかという指定を分けると、目的を切り替えたときの違いを説明しやすくなる。

### 必須条件と希望違反

$x_{p,d}\in\{0,1\}$を人pが日dに勤務するかどうかとする。勤務可能性を$a_{p,d}$、休み希望を$r_{p,d}$と置く。基本条件は、各日2人、勤務可能、一人2日以下の三種類である。

$$\sum_p x_{p,d}=2\quad(各日d),\qquad
x_{p,d}\le a_{p,d}\quad(各組p,d),\qquad
\sum_d x_{p,d}\le2\quad(各人p).$$

希望違反の合計は $V=\sum_{p,d}r_{p,d}x_{p,d}$ と定義する。希望が1かつ勤務が1の位置だけが1を加える。希望があるだけで違反にはならず、その日に実際に勤務した場合に数える。

例えばEが1日目と3日目に勤務すれば、Eの4日分は1×1+1×0+1×1+1×0=2となる。他の人には休み希望がないので、勤務してもこの入力のVは増えない。

### 全員の日数と最大・最小

各人の勤務日数を $L_p=\sum_d x_{p,d}$ とする。この値を全員分並べ、その中で最も大きい値を最大、最も小さい値を最小と呼ぶ。どちらも一人の行の中ではなく、全員の日数から選ぶ値である。

$$F=\max_p L_p-\min_p L_p.$$

日数が(2,2,2,2,0)なら最大2・最小0でF=2、(2,2,2,1,1)なら最大2・最小1でF=1となる。勤務0日の人も全員の一人なので、最小を取る前に除外しない。

ここで測るのは勤務日数の差である。各日の忙しさや担当内容の違いまでは測っていない。「公平」という言葉だけで指標を決めず、Fがどの差を数えているかを説明しよう。

### 重み付きの評価値

J=αV+βFを小さくする。αは希望違反1回、βは日数差1日の増加に付ける重みである。例えば(α,β)=(1,2)なら、Vが1減る改善より、Fが1減る改善に大きい点数を付ける。

重みを変えると、同じ勤務表のVとFは変わらなくてもJが変わる。片方の重みが0なら、その指標をJで比較しない。両方0では全表のJが0となるため、今回の入力では使わない。

重みは違反回数の上限そのものではない。「Vはk以下」という保証には、その条件を別に置く必要がある。[必修2](#演習)では、保証したい量と、その条件の中で小さくする量を選び分ける。

## 解説例

教員が基本勤務表を開き、希望入力、日数の集計、重み付きの最小化を順に確認する。集計値が表からどう決まるかを追い、重みを変える前後で、基本勤務条件が残っていることも見ていこう。

### 手順1　必須条件と希望

[weighted-demo.mzn](../../../workbook/sessions/08-preferences/weighted-demo.mzn)は[metrics-core.mzn](../../../workbook/sessions/08-preferences/metrics-core.mzn)を読み、その中から[roster-core.mzn](../../../workbook/sessions/08-preferences/roster-core.mzn)の基本条件を読む。共通部分には`solve`{.minizinc}を置かず、実行するモデルだけに置く。

```{.minizinc filename="metrics-core.mzn"}
include "roster-core.mzn";
array[PEOPLE, DAYS] of 0..1: request;
var int: violations = sum(p in PEOPLE, d in DAYS)(
    request[p,d]*work[p,d]
);
```

`request`は0/1の入力なので`var`{.minizinc}を付けない。`violations`は勤務表に応じて決まるVなので`var`{.minizinc}を付ける。[request-demo.dzn](../../../workbook/sessions/08-preferences/request-demo.dzn)には、5人の基本入力と、Eの4日分だけ1の希望をまとめてある。

### 手順2　全員の日数と日数差

まず人ごとに一行の勤務を足して`load[p]`{.minizinc}へ結び付ける。その配列全体を`max`と`min`へ渡せば、全員の日数の最大と最小が得られる。最小値の対象には勤務0日の人も含まれる。

```{.minizinc filename="metrics-core.mzn"}
array[PEOPLE] of var 0..n_days: load;
constraint forall(p in PEOPLE)(load[p] = sum(d in DAYS)(work[p,d]));
var int: spread = max(load) - min(load);
```

`load`の範囲0〜日数は安全な宣言であり、一人2日以下という基本条件も引き続き働く。`spread`がFに当たる。`max(load)`{.minizinc}は配列から最大値を取る式で、目的を大きくする`solve maximize`{.minizinc}とは役割が異なる。

### 手順3　重みと最小化

VとFの定義を共通部分に残し、実行するモデルで重みと目的を指定する。ここでは重みを定数入力として読み、勤務表に応じたJへ`objective`という名前を付けている。

```{.minizinc filename="weighted-demo.mzn"}
var int: objective = alpha*violations + beta*spread;
solve minimize objective;
```

[weights-10.dzn](../../../workbook/sessions/08-preferences/weights-10.dzn)、[weights-11.dzn](../../../workbook/sessions/08-preferences/weights-11.dzn)、[weights-12.dzn](../../../workbook/sessions/08-preferences/weights-12.dzn)を一つずつ選び、Gecodeで実行する。重みを二つ同時に読み込むと入力が重複する。

```sh
minizinc --solver gecode weighted-demo.mzn request-demo.dzn weights-12.dzn
```

出力には勤務表、`load`、V・F・Jが出る。表示順に依存せず、`load=`・`V=`・`F=`・`J=`の名前で対応を確かめる。最後の`==========`まで確認する。途中の候補や時間制限で止めた候補は、それよりよい解がないことまで確認済みとは限らない。

## 結果

次の二表は、いずれも勤務可能性、各日2人、一人2日以下を満たす。日ごとの担当者を読み、AからEまで各人が何日出ているかを数えると、希望と日数差の違いを比較できる。

| 表 | 1日目 | 2日目 | 3日目 | 4日目 | 日数A〜E | V | F |
|---|---|---|---|---|---|---:|---:|
| S0 | AB | AD | CD | BC | 2,2,2,2,0 | 0 | 2 |
| S1 | AB | AC | BD | CE | 2,2,2,1,1 | 1 | 1 |

S0はEが勤務しないのでV=0、最小の日数は0なのでF=2である。S1はEが4日目に勤務してV=1となるが、勤務0日の人はいなくなりF=1となる。希望を一つかなえないことと引き換えに、日数差が小さくなる。

| 重み(α,β) | S0のJ | S1のJ | 最適な指標対(V,F) |
|---|---:|---:|---|
| (1,0) | 0 | 1 | (0,2) |
| (1,1) | 2 | 2 | (0,2)と(1,1) |
| (1,2) | 4 | 3 | (1,1) |

重み1対1では二つの指標対が同点になる。S0とS1のどちらが出ても誤りではなく、同じ指標対を持つ別の勤務表が出る場合もある。表の完全一致ではなく、基本条件・VとFの再計算・Jの最適値を順に確認する。

この二表だけを比べることと、全勤務表の最適性を証明することは別である。実行では最適終了を確認し、手計算では表示された値の意味を確かめる。[確認手引き](guides/preferences-check.md)には入力ごとの希望・上限・目的をまとめてある。

## 演習

必修1では集計と重み付きの最小化を再現し、必修2では条件と目的の置き場所を変える。それぞれ別の出発ファイルを使うので、前の作業中の入力や目的が残っていないかを確認しよう。

### 必修1　希望の変更

Eの休み希望を1日分に減らした場合を扱う。勤務可能性を変えず、希望の表だけを変えることがポイントである。同じ重みで比べると、どの指標が改善できるかを調べられる。

#### 問題

::: {.given label="条件と入力"}
5人A〜Eの4日間の勤務を、勤務するなら1、休むなら0で決める。各日ちょうど2人、一人の勤務は合計2日以下。勤務可能性0の位置では勤務させない。各欄は左から1・2・3・4日目である。

| 人 | 勤務可能性（1〜4日） | 休み希望（1〜4日） |
|---|---|---|
| A | 1 1 0 1 | 0 0 0 0 |
| B | 1 0 1 1 | 0 0 0 0 |
| C | 0 1 1 1 | 0 0 0 0 |
| D | 1 1 1 0 | 0 0 0 0 |
| E | 1 1 1 1 | 0 0 0 1 |

Eは4日目だけ休みを希望し、他の人には希望がない。希望1の位置で勤務した回数の合計をV、勤務0日の人も含む全員の勤務日数の最大と最小の差をFとし、J=V+2Fを最小にする。希望0は出勤の義務ではなく、違反上限は追加しない。
:::

#### 作業

モデルの `work[p,d]`{.minizinc} は勤務の有無、`available[p,d]`{.minizinc} は勤務可能性、`request[p,d]`{.minizinc} は休み希望を表す。添字は `PEOPLE=1..5`{.minizinc} がA〜E、`DAYS=1..4`{.minizinc} が日1〜4である。`load[p]`{.minizinc} は人pの勤務日数、`violations` は希望違反の合計V、`spread` は日数差Fを表す。

[weighted-start.mzn](../../../workbook/sessions/08-preferences/weighted-start.mzn)と[roster-core.mzn](../../../workbook/sessions/08-preferences/roster-core.mzn)、[request-practice.dzn](../../../workbook/sessions/08-preferences/request-practice.dzn)、[weights-12.dzn](../../../workbook/sessions/08-preferences/weights-12.dzn)を使う。`roster-core.mzn` に基本勤務条件、出発ファイルに各人の日数・出力の足場が完成している。`request-practice.dzn` が上の表と人数・日数上限、`weights-12.dzn` が重み `alpha=1`{.minizinc}、`beta=2`{.minizinc} を持つ。自分で定義する `objective` がJに対応する。

1. **作業1：** `violations`と`spread`を定義する。希望位置と勤務の積を足し、日数差には全員の`load`を使う。
2. **作業2：** `objective`を重み付きの合計として定義し、最小化する`solve`{.minizinc}を一つ書く。入力を選んで実行する。
3. 表から日数・V・Fを手で求め、表示されたJまで照合する。

```{.minizinc filename="weighted-start.mzn"}
% TODO(作業1): 希望違反violationsと、全員の日数差spreadを定義する。
% TODO(作業2): 重み付きのobjectiveを定義し、最小化する。
```

出力は作業1・2で定義する名前を使うため、未記入では未定義のエラーになる。入力だけを変えて完成したことにはせず、何を足し、どの値を小さくするかを自分の式へ写そう。

#### 自己確認

最適値はJ=2、指標対は(V,F)=(0,1)である。例えば日ごとの担当者がAB／AE／CD／BCなら、日数は(2,2,2,1,1)。Eの勤務は2日目だけなので、4日目の休み希望を守れる。

別表でも基本条件と指標対が一致すればよい。総勤務は4日×2人=8で、5人へ同じ整数日数を割り当てられないためF=0にはできない。V≥0と合わせるとJ≥2であり、上の表がその値を達成している。

::: {.hint summary="ヒントを開く：二つの集計の対象"}
Vは人と日の全組について`request[p,d]*work[p,d]`{.minizinc}を足す。Fは`max(load)-min(load)`{.minizinc}とする。希望が変わるとVは変わり得るが、同じ勤務表のFは変わらない。
:::

### 必修2　違反の上限

運営者の二つの要求を読み、必ず守る条件と、よりよい表を選ぶ基準に分ける。どの量を制約へ置き、どの量を目的へ置くかを自分で決め、二つの入力で確かめよう。

#### 問題

::: {.given label="条件と入力"}
5人A〜Eの4日間の勤務を、勤務するなら1、休むなら0で決める。各日ちょうど2人、一人の勤務は合計2日以下。勤務可能性0の位置では勤務させない。各欄は左から1・2・3・4日目である。

| 人 | 勤務可能性（1〜4日） | 休み希望（1〜4日） |
|---|---|---|
| A | 1 1 0 1 | 0 0 0 0 |
| B | 1 0 1 1 | 0 0 0 0 |
| C | 0 1 1 1 | 0 0 0 0 |
| D | 1 1 1 0 | 0 0 0 0 |
| E | 1 1 1 1 | 1 1 1 1 |

Eは全4日休みを希望し、他の人には希望がない。運営者の要求は「休み希望に反する勤務は、合計で今回許されたk回を超えないこと」「その範囲で、最も勤務が多い人と少ない人の日数差を、できるだけ小さくすること」である。

k=0とk=1を別々に調べる。希望違反の合計をV、勤務0日の人も含む全員の勤務日数の最大と最小の差をFと呼ぶ。
:::

#### 作業

モデルの `work[p,d]`{.minizinc} は勤務の有無、`available[p,d]`{.minizinc} は勤務可能性、`request[p,d]`{.minizinc} は休み希望を表す。添字は `PEOPLE=1..5`{.minizinc} がA〜E、`DAYS=1..4`{.minizinc} が日1〜4である。`load[p]`{.minizinc} は人pの勤務日数、`violations` は希望違反の合計V、`spread` は日数差Fを表す。

[capped-start.mzn](../../../workbook/sessions/08-preferences/capped-start.mzn)、[metrics-core.mzn](../../../workbook/sessions/08-preferences/metrics-core.mzn)、[roster-core.mzn](../../../workbook/sessions/08-preferences/roster-core.mzn)を使う。V・各人の日数・Fの定義は完成している。上の表と人数・日数上限には [request-demo.dzn](../../../workbook/sessions/08-preferences/request-demo.dzn) を使う。

1. **作業1：** 二つの要求について「これを満たさない表は拒否する」「許された表同士で、こちらを比べる」のどちらかをメモし、対応する量と理由を書く。k回より少ない違反も許されるか考える。
2. **作業2：** メモに従って制約と`solve`{.minizinc}を記述する。重みを付けて足す方法で要求を必ず守れるかも検討する。
3. [cap-0.dzn](../../../workbook/sessions/08-preferences/cap-0.dzn)と[cap-1.dzn](../../../workbook/sessions/08-preferences/cap-1.dzn)を一つずつ使って実行する。二つの上限入力を同時に読み込まない。

```{.minizinc filename="capped-start.mzn"}
% TODO(作業1): 二つの要求を、必ず守る条件と比べる量に分けてメモする。
% TODO(作業2): メモに従って制約とsolveを書く。
```

出発ファイルには上限制約と目的をまだ入れていない。実行前に「Eの希望は全日」「今回のk」を入力から確認し、自分が書いた制約・目的のそれぞれが、どちらの要求を表すか説明する。

#### 自己確認

k=0では最小F=2、指標対は(0,2)。k=1では最小F=1、指標対は(1,1)になる。次の二表は基本勤務条件を満たすので、追加した上限と目的の違いに集中して確認できる。

| 表（1〜4日目の担当者） | 日数A〜E | V | F | k=0 | k=1 |
|---|---|---:|---:|---|---|
| AB／AD／CD／BC | 2,2,2,2,0 | 0 | 2 | 実行可能・最適 | 実行可能・最適でない |
| AB／AC／BD／CE | 2,2,2,1,1 | 1 | 1 | 上限違反 | 実行可能・最適 |

k=1は「違反を必ず1回起こす」ことではない。V=0の表も条件を満たすが、F=1の表があるので最適ではない。一方、k=0でV=1の表を通す実装は、最適性を比べる前に上限制約を確かめる必要がある。

::: {.hint summary="ヒントを開く：要求を二つに分ける"}
「k回を超えない」は拒否の基準、「その範囲で日数差を小さく」は比較の基準である。重み付きの和を小さくしても、超えてはいけない回数を直接指定したことにはならない。
:::

::: {.hint summary="ヒントを開く：制約と目的の式"}
拒否するのはVがkを超えた表なので`constraint violations <= k;`{.minizinc}と書く。その中で小さくするのはFなので`solve minimize spread;`{.minizinc}とする。`solve`はこの一つだけにする。
:::

::: {.hint summary="ヒントを開く：最適値の理由"}
総勤務8は5人へ均等に分けられないのでF≥1。さらにk=0ではEが0日、他の4人が各2日となりF=2。k=1では上の二つ目の表がF=1を達成する。
:::

同じ表でも希望入力が変わればVが変わり、同じVとFでも重みが変わればJが変わる。入力、集計、目的のどこを変えたのかをたどり、次の点を自分の言葉で説明してみよう。

- 勤務不可能と休み希望を同じ禁止条件にすると、どの選択を失うか。
- 最大・最小を取る前に勤務0日の人を除くと、Fの意味がどう変わるか。
- k=1でV=0・F=2の表は、なぜ実行可能だが最適ではないのか。

第09回は、既習の命題論理とPythonの基本から、真偽値の選択へ進む。今回のPython発展や検査器の完成には依存しない。今回はまず、[必修2](#演習)で制約と目的の役割を言い分けられるかを確認しよう。

## 参照 {.unnumbered}

入力の組や実行の区切りに迷ったら、[確認手引き](guides/preferences-check.md)の一覧へ戻る。本文中の記号と配布モデルの名前は次のように対応し、同じ表から順に計算できる。

| 記号・名前 | 意味 |
|---|---|
| `available`／`request` | 勤務可能性／休み希望という別の入力 |
| L／`load` | 一人ごとの勤務日数の配列 |
| V／`violations` | 希望位置で勤務した回数の合計 |
| F／`spread` | 全員の日数の最大と最小の差 |
| J／`objective` | 重み付きの評価値 |
| `max(load)`{.minizinc}／`min(load)`{.minizinc} | 配列内の最大値／最小値 |

重みを上限だと思う、希望を勤務不可へ書き換える、最大化と最大値の式を取り違える、古い`solve`{.minizinc}を残す、といった点を確認する。数式だけでなく、その式がどの表を許し、何を比べるかで読み直すと原因を見つけやすい。

MiniZincの配列・集計・目的指定は[公式チュートリアル](https://docs.minizinc.dev/en/stable/modelling2.html)と[モデルと最適化の説明](https://docs.minizinc.dev/en/stable/modelling.html)で確認できる。今回の操作に必要なファイル一覧は手引きにまとめてある。
