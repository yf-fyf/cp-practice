## この回の目標

この回を終えると、次のことができる。

- モデル（`.mzn`）と入力データ（`.dzn`）を分け、モデルを書き換えずに盤面を差し替えられる

## 今回解く問題

第03回のモデルには、初期値がモデルの中に直接書いてあった。

```{.minizinc filename="第03回の sudoku4.mzn（抜粋）"}
int: n = 4;
array[ROWS, COLS] of int: given =
  [| 1, 0, 3, 0
   | 0, 0, 0, 2
   | 2, 0, 0, 0
   | 0, 3, 0, 1 |];
```

この形だと、別の盤面を解くたびにモデルそのものを書き換えることになる。
9×9 に広げれば `n` も `b` も変わる。**問題が変わっていないのに、モデルが変わる。**

この回で解く問題は2つある。

1. **同じモデルのまま、複数の 9×9 盤面を解く。**
   モデルは「数独とはどういう問題か」だけを書き、
   盤面は入力データとして外から渡す。
2. **その盤面の解が一つだけかどうかを確かめる。**
   数独として出題されるパズルは、答えが一つに定まっていることになっている。
   本当に一つなのかを、実行結果で調べる。

使う盤面は次の3つである。いずれもこの科目のために作った架空の問題である。

| ファイル | 盤面 | 何に使うか |
|---|---|---|
| `puzzle-a.dzn` | 9×9 | 必須演習・標準演習 |
| `puzzle-b.dzn` | 9×9。盤面Aから初期値を1つ減らしたもの | 標準演習 |
| `puzzle-solved.dzn` | 9×9。空きマスが無い完成済みの盤面 | 既知例による検証 |

## 変数・定義域・制約・目的へ分解

第03回で決めた分解は、盤面が 9×9 になっても**そのまま**である。

| 語 | 数独では | 4×4 のとき | 9×9 のとき |
|---|---|---|---|
| 変数 | 各マスに入る数字 | 16 個 | 81 個 |
| 定義域 | $1$ から $n$ まで | 1〜4 | 1〜9 |
| 制約 | 行・列・ブロックの相異なり、初期値の一致 | 同じ形 | 同じ形 |
| 目的 | なし | — | — |

変わったのは**個数だけ**で、制約の形は変わっていない。
第03回のモデルを `n` と `b` で書いておけば、盤面の大きさは数字を差し替えるだけで済む。

ここから、次の考え方が出てくる。

::: {.term}
[**モデルとデータの分離**](../references/glossary.md#model_data_separation)とは、
問題の**構造**（どんな変数があり、どんな制約が成り立つか）と、
個々の**インスタンス**（今回の盤面はどれか）を別々のファイルに持つことである。

- **モデル**（`.mzn`）: 「数独とはこういう問題である」
- **データ**（`.dzn`）: 「今回解くのはこの盤面である」

同じモデルに違うデータを渡せば、違う問題が解ける。
:::

この分け方は数独だけの話ではない。第07回の希望順位、[第08回](08-roster-hard.md)の勤務規則、
自由課題の入力データも、すべて同じ形で分ける。

## 概念と構文

### 値を書かずに宣言する

`.dzn` から値を受け取るパラメータは、モデル側では**宣言だけ**にする。

```{.minizinc filename="モデル側（値を書かない）"}
int: n;                                  % 値は .dzn から受け取る
int: b;
array[ROWS, COLS] of int: given;
```

```{.dzn filename="データ側（値を書く）"}
n = 9;
b = 3;

given = [| 0, 6, 0, 8, 3, 0, 0, 9, 0
         | 0, 3, 0, 0, 0, 1, 0, 7, 0
         %  … 以下同様 …
         | 0, 4, 0, 6, 0, 9, 0, 3, 0 |];
```

::: {.warning}
モデル側に `int: n = 4;` と**値まで書いてしまうと**、`.dzn` から上書きできない。
実行すると `multiple assignment to the same variable`（同じ変数に二重の代入）と出る。
差し替えたいパラメータは `int: n;` と宣言だけにする。
:::

`.dzn` の2次元データには2通りの書き方がある。どちらでも同じ意味である。
書き方の一覧は [MiniZinc 早見表](../references/minizinc-cheatsheet.md)にある。

```{.dzn filename="書き方2: array2d で畳む"}
given = array2d(1..9, 1..9, [ 0, 6, 0, 8, 3, 0, 0, 9, 0,
                              0, 3, 0, 0, 0, 1, 0, 7, 0,
                              %  … 以下同様 …
                              0, 4, 0, 6, 0, 9, 0, 3, 0 ]);
```

### Playground でモデルとデータを渡す

Playground はファイルを追加してタブを増やせる。モデルのタブに `.mzn` を、
データのタブに `.dzn` を置き、実行時に使うデータファイルを選ぶ。

::: {.warning}
**Playground の画面と操作名は予告なく変わる。**
ファイルを追加するボタンやデータファイルを選ぶ画面が見つからないときは、
`.dzn` の中身を**モデルの末尾にそのまま貼り足す**。
`n = 9;` のような代入は、モデルの中に書いても同じように働く。

この回で確かめたいのは「モデルの制約の部分を書き換えずに盤面を差し替えられる」ことなので、
2つのファイルに分かれているかどうかは本質ではない。
貼り足す場合も、**制約の部分には指を触れない**ようにする。
:::

### 二つ目の解を探す

`solve satisfy;` は解を1つ返して止まる。したがって、

::: {.important}
**解が1つ表示されたことは、「解が1つしか無い」という意味ではない。**
「少なくとも1つある」という意味でしかない。
:::

[解が一つだけである](../references/glossary.md#solution_uniqueness)ことを確かめるには、
**二つ目の解があるかどうか**を見ればよい。全部を数え上げる必要は無い。

| 二つ目を探した結果 | 分かること |
|---|---|
| 別の盤面が出た | 解は2つ以上ある。一つではない |
| `=====UNSATISFIABLE=====` | 一つ目以外に解は無い。解は一つだけである |

やり方は2通りある。

**方法1: 全部の解を出させる。**
Playground のソルバー設定で「すべての解を出す」を選ぶと、解が次々に表示される。
`==========` が出れば、それで打ち止めという意味である。

::: {.warning}
この設定の名前と場所も、Playground の画面によって変わる。
見つからない場合は方法2を使う。方法2はモデルの側だけで完結するので、
どの実行環境でも同じように動く。
:::

**方法2: 見つかった解を制約で除外して、もう一度解かせる。**
「一つ目の解とは違う盤面」だけを探すように制約を1つ足す。

```{.minizinc filename="一つ目の解を除外する"}
array[ROWS, COLS] of int: found;      % 一つ目の解を .dzn から受け取る

constraint exists(r in ROWS, c in COLS)( x[r, c] != found[r, c] );
```

`exists` は `forall` の相棒である。

| 書き方 | 読み | 数式 |
|---|---|---|
| `forall(r in ROWS)( 条件 )` | すべての `r` について条件が成り立つ | $\forall$ |
| `exists(r in ROWS)( 条件 )` | 条件が成り立つ `r` が少なくとも1つある | $\exists$ |

上の制約は「`found` と値が違うマスが**少なくとも1つある**」と読む。
つまり「`found` と完全に同じ盤面は解として認めない」という意味になる。

::: {.note}
`x[r, c] != found[r, c]` を `forall` で書くと、
「**すべての**マスが違う」というまったく別の条件になってしまう。
盤面がまるごと違うものだけを探すことになるので、
本当は存在する二つ目の解を見落とすことがある。
:::

`found` に一つ目の解を書き写すのは骨が折れるので、
`sudoku.mzn` は解のあとに `.dzn` へそのまま貼れる形も出すようにしてある。

## 小さな実行例

まず、答えが分かっている例でモデルを試す。これが
[**既知例による検証**](../references/glossary.md#known_example_validation)である。

`puzzle-solved.dzn` は、空きマスがまったく無い完成済みの盤面である。

```{.dzn filename="puzzle-solved.dzn（抜粋）"}
n = 9;
b = 3;

given = [| 1, 2, 3, 4, 5, 6, 7, 8, 9
         | 4, 5, 6, 7, 8, 9, 1, 2, 3
         | 7, 8, 9, 1, 2, 3, 4, 5, 6
         %  … 以下同様 …
         | 9, 1, 2, 3, 4, 5, 6, 7, 8 |];
```

規則的に並べただけの盤面なので、数独として正しいことは目で確かめられる。
このデータをモデルに渡すと、次が出る。

```solver
1 2 3  4 5 6  7 8 9
4 5 6  7 8 9  1 2 3
7 8 9  1 2 3  4 5 6

2 3 4  5 6 7  8 9 1
5 6 7  8 9 1  2 3 4
8 9 1  2 3 4  5 6 7

3 4 5  6 7 8  9 1 2
6 7 8  9 1 2  3 4 5
9 1 2  3 4 5  6 7 8

% 第2解を調べるときは、ここから下を .dzn へ写す
found = [| 1, 2, 3, 4, 5, 6, 7, 8, 9
         …
----------
```

盤面のあとに続く `found = ...` は、標準演習で使うためのものである
（`%` の行から下は `check_sudoku.py` も読み飛ばす）。いまは気にしなくてよい。

与えた盤面がそのまま返ってきた。空きマスが無いので、
モデルは「初期値を守れ」という制約だけで盤面を決めきったことになる。

::: {.check}
既知例の検証で見るのは次の2点である。

- **返ってきた盤面が、与えた盤面と一致しているか。**
  一致しなければ、初期値の制約が効いていない。
- **解が一つだけか。**
  空きマスが無いのに二つ目が出るなら、変数と初期値の対応がどこかで壊れている。
:::

::: {.note}
既知例が通っても、モデルが正しいとは限らない。
たとえば行の制約を丸ごと書き忘れていても、この既知例は通ってしまう
（初期値だけで盤面が決まるため）。
**既知例は「間違いを見つける」ためのもので、「正しさを証明する」ものではない。**
:::

## 予想してから試す

::: {.predict}
`puzzle-a.dzn` の盤面をモデルに渡して実行し、解が出たとする。
続けて、その解を `found` として除外し、もう一度実行する。何が起きると思うか。

1. 一つ目とよく似た別の盤面が出る
2. 一つ目とまったく違う盤面が出る
3. `=====UNSATISFIABLE=====` が出る
4. エラーになって止まる

同じことを `puzzle-b.dzn`（盤面Aから初期値を1つ減らしたもの）でやったらどうなるか。
盤面Aの場合と同じか、違うか。理由と一緒に書き出してから実行する。
:::

盤面Bで二つ目の解が出た場合、一つ目とどれくらい違うかも見ておく。
**盤面がまるごと入れ替わるのか、それとも数マスだけが入れ替わるのか。**

`puzzle-a.dzn` の盤面を解く。

**完了条件**: 9×9 の盤面が1つ表示され、その盤面が

```console
$ python3 ../03-minizinc-sudoku/check_sudoku.py --given puzzle-a.dzn board.txt
```

`board.txt` は、Playground の出力の**盤面の部分**を保存したファイルである。
貼り付けて渡すなら、ファイル名を書かずに実行して Ctrl-D
（Windows は Ctrl-Z のあと Enter）を押す。

続けて、モデルを1文字も変えずに `puzzle-solved.dzn` に差し替えて実行し、
与えた盤面がそのまま返ることを確かめる。

::: {.hint summary="ヒント1: 何を消すのか"}
`int: n = 4;` は「`n` は整数で、その値は 4 である」と2つのことを言っている。
`.dzn` から値をもらうには、後半だけを取り下げればよい。

`given` も同じである。`array[ROWS, COLS] of int: given` までが宣言で、
`= [| ... |]` から先が値である。
:::

::: {.hint summary="ヒント2: 直したのに動かないとき"}
- `multiple assignment to the same variable` → まだモデル側に値が残っている。
  `= 4` や `= [| ... |]` を消し忘れていないか。
- `variable 'n' must be defined (did you forget to specify a data file?)`
  → データファイルが渡っていない。実行時にデータファイルを選ぶか、
  `.dzn` の中身をモデルの末尾に貼り足す。
- 4×4 の盤面が出る → 古いモデルのままである。貼り直す。
:::

::: {.hint summary="ヒント3: 解答"}
```{.minizinc filename="sudoku.mzn（TODO(1) と TODO(2)）"}
% TODO(1) 盤面の大きさ
int: n;
int: b;

% TODO(2) 初期値
array[ROWS, COLS] of int: given;
```

宣言の行はそのまま残し、`=` から後ろだけを消す。
`set of int: DIGITS = 1..n;` のように、`n` から**導かれる**定義は消さない。
これらは `.dzn` から受け取る値ではなく、モデルの中で決まるものである。
:::

## 標準演習

::: {.exercise level=standard}
### 二つの盤面について、解が一つだけかを判定する

`puzzle-a.dzn` と `puzzle-b.dzn` のそれぞれについて、
一つ目の解を求めたあと、二つ目の解があるかどうかを調べる。

`sudoku.mzn` の末尾近くにある「第2解の探索」の2行のコメントを外し、
一つ目の解を `found` として `.dzn` に足してから、もう一度実行する。
実行結果を次の形で記録する。

| 盤面 | 初期値の個数 | 二つ目を探した結果 | 解は一つか |
|---|---|---|---|
| `puzzle-a.dzn` | | | |
| `puzzle-b.dzn` | | | |

**完了条件**: 2つの盤面について上の表が埋まっていて、
「解が一つだと言える／言えない」の判断の根拠を、実行結果と対応させて説明できる。

二つ目の解が出た盤面については、一つ目と**どのマスが違うか**も書き出す。

考えどころは2つある。

- 「二つ目が無い」ことをどうやって知ったのか。
  ソルバーは何を調べて `=====UNSATISFIABLE=====` と答えたのか。
- 初期値を1つ減らしただけで結果が変わるのはなぜか。
  減らした初期値は、どのマスの候補を絞っていたのか。
:::

::: {.hint summary="ヒント1: found の書き方"}
`found` はパラメータ（値が決まっているもの）なので、`var` は付かない。
`given` とまったく同じ形の2次元データである。

一つ目の解を実行したときの出力の後半に、
`found = [| ... |];` の行がそのまま出ている。それを `.dzn` へ貼る。
:::

::: {.hint summary="ヒント2: 結果の読み方"}
`=====UNSATISFIABLE=====` はエラーではない。
「一つ目の解を除いたら、条件を満たす盤面は無くなった」という**答え**である。
除外する前は解が出ていたのだから、モデルが壊れたわけではない。

逆に別の盤面が出たなら、その盤面も**すべての制約を満たしている**。
`check_sudoku.py` に通せば確かめられる。
:::

::: {.hint summary="ヒント3: 違うマスを見つける"}
2つの盤面を並べて1マスずつ見比べる。
数独で解が2つあるとき、違いはたいてい**盤面全体には広がらない**。
いくつかのマスで数字が入れ替わっているだけである。
入れ替わっているマスに丸を付けて、その形を見る。
:::

## 発展演習

::: {.exercise level=advanced}
### いずれか1つを選ぶ

**A. 一意性が失われる境界を調べる**

`puzzle-a.dzn` から初期値を1つずつ消していき、
どこで解が一つでなくなるかを調べる。

- 消す初期値を変えると、結果は変わるか。
  「消しても一つのまま」の初期値と、「消したとたんに2つ以上になる」初期値があるか。
- 消したときに解が増えやすいのはどんな位置か。予想を立ててから確かめる。
- 自分で盤面を作り、それが一意解を持つかどうかを同じ方法で確かめる。
  作った盤面の解は、必ず `check_sudoku.py --given` で独立に照合する。

一意解を持つ盤面を作るのは、解くよりずっと難しい。
うまくいかなくてよいので、**どこが難しいのか**を書き残す。

**B. Killer Sudoku の追加制約を設計する**

盤面の一部を枠で囲み、「枠の中の数字の合計」を条件として与える形の数独である。
枠の合計を制約として書き足し、初期値をいくつか消しても解が一つのままにできるか試す。

合計を書く道具は [MiniZinc 早見表](../references/minizinc-cheatsheet.md)の
「集計と数え上げ」にある（本格的に使うのは第07回である）。
まずは3マス程度の枠を1つか2つ足すところから始める。
:::

## よくある誤り

| 症状 | 原因 | 直し方 |
|---|---|---|
| `multiple assignment to the same variable` | モデル側にも `.dzn` 側にも値が書いてある | モデル側を宣言だけにする（`int: n;`） |
| `variable 'n' must be defined (did you forget to specify a data file?)` | データファイルが渡っていない | 実行時にデータファイルを選ぶ。または `.dzn` の中身をモデルの末尾へ貼る |
| 盤面が 4×4 のまま出る | 古いモデルが Playground に残っている | 全部消してから貼り直す |
| `=====UNSATISFIABLE=====` が最初から出る | 初期値が数独として成立していない（同じ行に同じ数字があるなど） | データを見直す。写し間違いが多い |
| 二つ目を探すと必ず `UNSATISFIABLE` になる | `exists` を `forall` と書いている | 「1マスでも違えばよい」ので `exists` である |
| 二つ目を探すと一つ目と同じ盤面が出る | `found` が一つ目の解と食い違っている | 出力の `found = ...` を貼り直す。手で打ち直さない |
| `check_sudoku.py` が「正方形にならない」と言う | 盤面以外の数字を一緒に渡している | 出力の盤面の部分だけを渡す。`%` から下は読み飛ばされる |

::: {.warning}
**一つの解が出たことと、その盤面が良い問題であることは別である。**
数独として出題するなら解は一つでなければならないが、
ソルバーはそんなことは気にせず、条件を満たす盤面を1つ返すだけである。
「解が一つか」は、**こちらから聞かないと分からない**。
:::

## 扱わないこと

- **解を全部数え上げること** → この回では二つ目の有無しか見ない。
  一意かどうかを知るのに全部を数える必要は無く、盤面によっては解が非常に多い
- **一意解を持つ数独の自動生成** → 自由課題のテーマ候補。
  最少ヒント数のような理論は、この科目の範囲ではない
- **実行時間の測定と性能比較** → [第10回](10-roster-verification.md)。
  この回では「解けるかどうか」だけを見る
- **最適化**（`minimize` / `maximize`） → [第07回](07-theme-assignment.md)。
  数独には目的が無い
- **モデルとは独立した検証の本格的な話** → [第10回](10-roster-verification.md)。
  この回では配布済みの `check_sudoku.py` を使うところまでにする
- **`.dzn` の全書式**（集合・列挙型のデータなど） →
  [MiniZinc 早見表](../references/minizinc-cheatsheet.md)。
  この回で使うのは整数と2次元配列だけである

## 次回への接続

第05回からは道具が変わる。Python から **Z3** を呼び出して、
真偽（入れる／入れない）の組合せで表す問題を解く。
数独の盤面のように数字が並ぶのではなく、
「このパッケージを入れるか、入れないか」を1つずつ決めていく問題である。

::: {.important}
**第05回の前に、Python から Z3 を呼び出せる状態にしておくこと。**
導入そのもの（Python と `z3-solver` を入れるところ）は事前の自習課題である。
手順は [Z3 実行環境の使い方](../references/setup-z3.md)にある。
:::

### この回の末尾10分: Z3 の最小動作確認

**結果確認の枠（末尾10分）を、Z3 が動くことの確認に充てる。**
第05回の演習は Z3 が動くことを前提にしているので、
「動かない」が判明するのを第05回の当日まで遅らせない。

その場で行うのは次の3つだけである。

1. 仮想環境を有効にして `python -c "import z3; print(z3.get_version_string())"` を実行し、
   `5.1.0` が出ることを見る。
2. [Z3 実行環境の使い方](../references/setup-z3.md)の「最小動作確認」の
   `hello_z3.py` を実行し、`sat` と割り当てが出た**画面を教員が見る**。
3. 出なかった人は、**詰まった場所と画面に出た文字**をその場で控える。

まだ導入していない人は、この10分で入れ始めてよい。
その場で終わらなくても、**どこで止まるかが分かれば十分**である。
うまくいかないときの手当ては
[Z3 実行環境の使い方](../references/setup-z3.md)の「動かないときの逃げ道」にある。

::: {.note}
**自由課題に向けて**: 自分が考えている問題について、
「毎回変わるもの（データ）」と「変わらないもの（モデル）」に分けてみる。
どちらに入れるか迷うものが出てきたら、それが設計の分かれ目である。
:::
