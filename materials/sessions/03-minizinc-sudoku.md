## 今回解く問題

4×4 の数独を解く。

盤面は 4 行 4 列の 16 マスからなる。マスには 1 から 4 の数字が1つずつ入る。
2×2 のブロックが4つあり、次の条件をすべて満たさなければならない。

- **行**: どの行にも 1〜4 が1回ずつ現れる
- **列**: どの列にも 1〜4 が1回ずつ現れる
- **ブロック**: どの 2×2 ブロックにも 1〜4 が1回ずつ現れる
- **初期値**: 最初から数字が書かれているマスは、その数字のまま動かさない

今回の初期値は次のとおりである（`.` は空きマス）。

```text
1 . | 3 .
. . | . 2
----+----
2 . | . .
. 3 | . 1
```

9×9 ではなく 4×4 から始めるのは、**手作業でも答えを確かめられる**大きさだからである。
ソルバーが返した盤面が正しいかどうかを自分の目で判定できないと、
モデルの誤りに気づけない。

## 変数・定義域・制約・目的へ分解

制約プログラミングでは、どの問題も同じ順序で書き下す。この科目では最後まで
この順序を使うので、ここで語彙を固定する。

::: {.term}
- **変数**（decision variable）: ソルバーに値を決めてもらうもの
- **定義域**（domain）: 各変数が取り得る値の範囲
- **制約**（constraint）: 変数の値の組が満たさなければならない条件
- **割当て**（assignment）: すべての変数に値を1つずつ決めたもの
- **解**（solution）: すべての制約を満たす割当て
- **充足**: 制約をすべて満たしている状態

「解が1つでもあるか」を問う問題を**制約充足問題**（CSP）という。
数独もグラフ彩色もこの形をしている。
:::

数独を4語に当てはめると次のようになる。

| 語 | 数独では | 個数 |
|---|---|---|
| 変数 | 各マスに入る数字 | 16 個（4行 × 4列） |
| 定義域 | 1, 2, 3, 4 | 各変数について4通り |
| 制約 | 行・列・ブロックの相異なり、初期値の一致 | 行4本 + 列4本 + ブロック4個 + 初期値6か所 |
| 目的 | なし（1つ見つかればよい） | — |

変数を $x_{r,c}$（$r$ 行 $c$ 列のマスに入る数字）と書くと、行の制約は
**「すべての行 $r$ について、その行に並ぶ4個の値は互いに異なる」**の一文になる。
このあと見るとおり、MiniZinc の書き方はこの一文とほとんど同じ形をしている。

::: {.note}
上の一文を数学の記号で書くと次のようになる。**読めなくてよい。**
$\forall$ は「すべての〜について」、$\{\, \cdots \mid \cdots \,\}$ は
「〜であるもの全部の集まり」と読む。

$$\forall r \in \{1,2,3,4\}: \quad \operatorname{alldifferent}\bigl(\{\, x_{r,c} \mid c \in \{1,2,3,4\} \,\}\bigr)$$

この科目では、以降この記法を使わない。条件は日本語か MiniZinc・Z3 の式で書く。
$\forall$ の読み方をもう少し知りたい人は、番外の自習ページ
[論理の入門(1)](../references/logic-intro.md#forall-exists)を見るとよい。
:::

::: {.important}
**目的が無いこと**は、この回の重要な特徴である。
「なるべく良い解」ではなく「条件を満たす解」を探している。
目的を持つ問題（最適化）は第07回で扱う。
:::

## 概念と構文

MiniZinc のモデルは、次の4種類の宣言でできている。上から順に書く決まりはないが、
読む人のために「パラメータ → 決定変数 → 制約 → 解き方の指定」の順で並べる。

### パラメータと決定変数

**パラメータ**は、モデルを書く時点で分かっている値である。
**決定変数**は、ソルバーに決めてもらう値である。`var` が付くかどうかで区別する。

```{.minizinc filename="書き方の対比"}
int: n = 4;                 % パラメータ。4 という値が決まっている
var 1..4: y;                % 決定変数。1〜4 のどれかだが、まだ決まっていない
```

決定変数の宣言に書いた `1..4` が**定義域**である。
定義域を書いておけば「5 は入らない」という制約を別に書かなくてよい。

::: {.warning}
`var` を書き忘れると、ソルバーが決める値のつもりだったものがパラメータになり、
「値が与えられていない」というエラーになる。逆にパラメータに `var` を付けると、
モデルは動くが探索空間が無駄に広がる。
:::

### 2次元配列

盤面のように「行と列で位置が決まる変数の並び」は2次元配列で書く。

```{.minizinc filename="2次元配列の宣言"}
set of int: ROWS = 1..4;
set of int: COLS = 1..4;
array[ROWS, COLS] of var 1..4: x;   % x[r, c] で (r 行 c 列) のマスを指す
```

`array[ROWS, COLS]` の `ROWS`・`COLS` は**添字集合**であり、
「どの範囲の番号で要素を指すか」を表す。`1..4` と直接書いてもよいが、
名前を付けておくと `n` を変えるときに1か所だけ直せばよくなる。

### `forall` と配列内包表記

同じ形の制約を繰り返し書くための道具が2つある。

```{.minizinc filename="繰り返しの2つの道具"}
forall(r in ROWS)( ... )        % すべての r について ... が成り立つ
[ x[r, c] | c in COLS ]         % c を動かして作った配列（配列内包表記）
```

配列内包表記 `[ 式 | 変数 in 集合 ]` は「集合の各要素について式を計算して並べた配列」を作る。
Python のリスト内包表記と同じ考え方である。

### 大域制約 `all_different`

`all_different(配列)` は「配列の要素が互いに異なる」という制約である。
このように、よく使う条件にまとめて名前が付いているものを**大域制約**という。

```{.minizinc filename="大域制約を使う"}
include "globals.mzn";          % 大域制約を使うときは先頭でこれを読み込む

constraint all_different([ 1, y, 3 ]);   % y は 1 でも 3 でもない
```

第02回では「4つの値を重複なく並べる」ことを、順列を生成する手順を書いて保証していた。
`all_different` を使えば、**条件をそのまま1行で書ける**。
どう探すかはソルバーが決める。

### モデル全体の形

```{.minizinc filename="モデルの骨格"}
include "globals.mzn";

int: n = 4;                                  % パラメータ
array[1..n, 1..n] of var 1..n: x;            % 決定変数と定義域

constraint forall(r in 1..n)(                % 制約
  all_different([ x[r, c] | c in 1..n ])
);

solve satisfy;                               % 解き方の指定（1つ見つければよい）

output [ show(x[r, c]) ++ " " | r in 1..n, c in 1..n ];   % 出力の整形
```

`solve satisfy;` は「制約を満たす割当てを1つ見つけよ」という指示である。
`output` は解の見せ方を整えるだけで、解の中身には関係しない。

## 小さな実行例

数独に入る前に、第02回で Prolog を使って解いた**グラフ彩色**を MiniZinc で書き直す。
同じ問題を別の言い方で書くとどうなるかを先に見ておく。

問題は、隣り合う地区に違う色を塗ることである。地区は5つ、使える色は3色とする
（この科目のために作った架空の地図である）。**第02回とまったく同じ地図**を使う。

![架空の5地区（北区・南区・東区・西区・中央区）の隣接関係と、3色で塗り分けた解の一例。中央区は他の4地区すべてと隣り合い、外側は北・東・南・西の順に環になっていて、辺は全部で8本ある。左は問題で、辺で結ばれた2地区が隣り合っていることを表す。右は解の一例で、どの辺の両端も異なる色になっている。](figures/graph-5districts.svg)

モデルは次のとおりである（`workbook/sessions/03-minizinc-sudoku/coloring5.mzn`）。

```{.minizinc filename="coloring5.mzn（抜粋）"}
int: nd = 5;                       % 地区の数
int: nc = 3;                       % 使える色の数
set of int: DISTRICTS = 1..nd;     % 添字集合
set of int: COLORS    = 1..nc;

int: ne = 8;                       % 隣接している組の数
array[1..ne, 1..2] of int: edge =  % 入力データ
  [| 1, 5      % 北区 - 中央区
   | 2, 5      % 南区 - 中央区
   | 3, 5      % 東区 - 中央区
   | 4, 5      % 西区 - 中央区
   | 1, 3      % 北区 - 東区
   | 3, 2      % 東区 - 南区
   | 2, 4      % 南区 - 西区
   | 4, 1 |];  % 西区 - 北区

array[DISTRICTS] of var COLORS: paint;  % 決定変数: 各地区に塗る色

constraint forall(e in 1..ne)( paint[edge[e, 1]] != paint[edge[e, 2]] );

solve satisfy;
```

`edge` の 8 行は、第02回の `coloring.pl` に並んでいた 8 本の `\=` と1対1に対応する。
**同じ問題である。**変わったのは書き方だけである。

Playground で実行すると、次の結果が出る。

```solver
北区: 色3
南区: 色3
東区: 色2
西区: 色2
中央区: 色1
----------
```

末尾の `----------` は「解を1つ出し終えた」という区切りである。

::: {.note}
この出力は、Playground が最初から選んでいるソルバー（Gecode）で実行したものである。
**3色での塗り分けは1通りではない。**
ソルバーを切り替えると、条件を満たす別の塗り分けが返ることがある。
どれが返っても正しい。確かめるべきなのは
「どの辺の両端も色が違うか」であって、色の名前そのものではない。
:::

第02回の Prolog 版と並べると、書いたものと書かなかったものがはっきりする。

| 見るところ | 第02回（Prolog） | この回（MiniZinc） | 何が変わったか |
|---|---|---|---|
| 変数の宣言 | 変数はリストの要素として暗黙に現れる | `array[DISTRICTS] of var COLORS: paint;` と明示する | 定義域を宣言で書けるようになった |
| 定義域 | `color(red).` などの事実を並べて候補を与える | `COLORS = 1..nc` と範囲で書く | 候補を並べる手間が消えた |
| 制約 | 8本の `\=` を1行ずつ並べる | `edge` のデータ1つと `constraint` 1本にまとまる | 隣接関係がデータになった |
| 探索の順序 | 述語を書く順序が探索順序を決める | 書かない（ソルバーが決める） | 手順の記述が消えた |
| 解の個数 | 「次の解」を押して次の解を出す | `solve satisfy` は1つ返す（列挙は第04回） | 使い方が変わった |

::: {.discuss}
Prolog 版で書いていて MiniZinc 版で書かなくなったものは何か。
それは「消えた」のか、「別のところへ移った」のか。
:::

## 予想してから試す

::: {.predict}
`coloring5.mzn` の `nc` を `3` から `2` に変えて実行すると、どうなると思うか。
次のどれかを選び、理由も一緒に書き出してから実行する。

1. 何かしらの塗り分けが出る
2. 「解が無い」と表示される
3. エラーになって止まる
4. いつまでも終わらない

実行すると、次のように表示される。

```solver

```

これは「制約をすべて満たす割当ては存在しない」という意味である。
モデルが壊れているのではなく、**問題そのものに解が無い**ことを

ここまでで、次を確認しておく。

- `nc = 3` では解が出て、`nc = 2` では `UNSATISFIABLE` になった
- `UNSATISFIABLE` はエラーメッセージではないと説明できる
:::

## 必須演習

::: {.exercise level=required}
### 4×4数独の行制約と列制約を書く

`workbook/sessions/03-minizinc-sudoku/sudoku4.mzn` を Playground で開き、
`% TODO(1)`（行制約）と `% TODO(2)`（列制約）の2か所を埋める。

**完了条件**: 実行して盤面が1つ表示され、その盤面のどの行にも、
どの列にも 1〜4 が1回ずつ現れている。

この段階では初期値もブロックも制約に入れていないので、
表示される盤面は最初の初期値と一致しないし、ブロックの中で数字が重複していてよい。
それでよい。**制約を書いた分だけが守られる**ことを、目で確かめるのがこの演習である。
:::

::: {.hint summary="ヒント1: 行制約は「何を固定して何を動かす」か"}
1つの行を取り出すというのは、行番号 `r` を固定して、列番号 `c` を 1 から 4 まで
動かすということである。動かす側を配列内包表記で並べ、固定する側を `forall` で回す。

```{.minizinc}
constraint forall(r in ROWS)( all_different([ x[r, ?] | ? in COLS ]) );
```
:::

::: {.hint summary="ヒント2: 列制約は行制約と何が違うか"}
行制約では `r` を固定して `c` を動かした。列制約はその逆である。
`forall` で回す変数と、配列内包表記で動かす変数を入れ替える。
`x[?, ?]` の添字の順序（行が先、列が後）は変わらないことに注意する。
:::

::: {.hint summary="ヒント3: 解答"}
```{.minizinc filename="sudoku4.mzn（TODO(1) と TODO(2)）"}
% TODO(1) 行制約
constraint forall(r in ROWS)( all_different([ x[r, c] | c in COLS ]) );

% TODO(2) 列制約
constraint forall(c in COLS)( all_different([ x[r, c] | r in ROWS ]) );
```

`forall(r in ROWS)` の `r` と、内包表記の `| c in COLS` の `c` は
それぞれ別の役割を持つ。どちらを外に出すかで行と列が入れ替わる。
:::

## 標準演習

::: {.exercise level=standard}
### ブロック制約と初期値を足して、完全なモデルにする

`sudoku4.mzn` の `% TODO(3)`（ブロック制約）と `% TODO(4)`（初期値の固定）を埋め、
この回の初期値どおりの盤面が求まるようにする。

**完了条件**: 実行して出た盤面を `check_sudoku.py` に通し、
「行・列・ブロック・初期値 のすべての条件を満たしている」と表示される。

```console
$ python3 check_sudoku.py
```

起動したら Playground の出力を貼り付け、Ctrl-D を押す
（Windows は Ctrl-Z のあと Enter）。次のように表示されれば通っている。

```solver
1 2 3 4
3 4 1 2
2 1 4 3
4 3 2 1

行・列・ブロック・初期値 のすべての条件を満たしている。
```

考えどころは2つある。

- ブロックには**行方向・列方向にそれぞれ `b` 個**の並びがある。
  ブロックの位置を `br`・`bc`（どちらも `0..b-1`）で表し、
  1つのブロックの `b × b` マスを配列内包表記でどう並べるか。
- 初期値は「0 でないマスだけ」に効かせたい。
  `given[r, c] != 0` が成り立つときだけ `x[r, c] = given[r, c]` を要求する。
  MiniZinc では `A -> B`（A ならば B）という書き方ができる。
:::

::: {.hint summary="ヒント1: ブロックを指す添字の作り方"}
ブロックを行方向に `br` 個、列方向に `bc` 個ずらした位置にあるものとする
（`br`・`bc` はどちらも `0..b-1`。4×4 なら `0` か `1`）。
そのブロックの中のマスは、ブロック内の位置を `i`・`j`（どちらも `1..b`）として

```{.minizinc}
x[br * b + i, bc * b + j]
```

で指せる。`br = 0, bc = 0, i = 1, j = 1` が盤面の左上 `x[1, 1]` になる。

配列内包表記は `|` の右に複数の変数を書けるので、`i` と `j` を同時に動かせる。
`forall` のほうも `forall(br in 0..b-1, bc in 0..b-1)( ... )` と2つ同時に回せる。
:::

::: {.hint summary="ヒント2: 初期値をどう書くか"}
「0 でないマスだけ」を選ぶ書き方は2通りある。
`->` を使って条件付きで要求する書き方と、
配列内包表記の `where` で対象のマスだけを選ぶ書き方である。
どちらでも同じ結果になる。まず `->` で書いてみる。
:::

## 発展演習

::: {.exercise level=advanced}
### いずれか1つを選ぶ

**A. 盤面サイズのパラメータ化**

`n` と `b` を `.mzn` に固定せず、外から与えられるようにして、
同じモデルで 4×4 と 9×9 の両方を解けるようにする。
`workbook/sessions/03-minizinc-sudoku/` に `puzzle01.dzn`（4×4）と
`puzzle09.dzn`（9×9）を置いてあるので、動作確認に使える。
モデルとデータを分ける書き方そのものは第04回で扱うので、
ここでは「モデルの中に 4 という数字を何か所書いたか」を数えるところから始める。

**B. 対角線数独**

左上から右下への対角線と、右上から左下への対角線でも
数字が重複しないという制約を足す。制約を足す前と後で、
解が変わるか・無くなるかを予想してから実行する。
:::

## よくある誤り

| 症状 | 原因 | 直し方 |
|---|---|---|
| `undefined identifier: all_different` | `include "globals.mzn";` が無い | モデルの先頭に書く |
| `x[c, r]` と書いて行と列が入れ替わる | 添字の順序は宣言 `array[ROWS, COLS]` の順（行が先） | `x[行, 列]` に直す |
| `index out of bounds` | 添字が `0` になっている（`x[0, 0]` を指した）。行と列の番号は `1` から始まる | ブロック制約なら `x[br * b + i, bc * b + j]` の `i`・`j` を `1..b` で回す。`0..b-1` で回すのは `br`・`bc` のほうである |
| 制約を書いたのに反映されない | `constraint` を付け忘れて、ただの式になっている | 行頭に `constraint` を付け、末尾に `;` を置く |
| `=====UNSATISFIABLE=====` が出る | 制約が矛盾している（初期値が数独として成立していない等） | 制約を1つずつコメントアウトして、どれを外すと解が出るかを見る |
| 解は出るが盤面が数独になっていない | 制約が足りない | 足りていない条件を `check_sudoku.py` が名指しするので、その条件を書く |
| `=` と `==` を書き間違える | 制約の中の等号は `=` でよい（`==` も同じ意味） | どちらでも動く。混ぜずにどちらかに揃える |

::: {.warning}
**ソルバーが解を返したことは、モデルが正しいことを意味しない。**
制約を1つ書き忘れていても、ソルバーはその条件を無視した「解」を平気で返す。
だから `check_sudoku.py` のような、モデルとは独立した確認手段を使う。
この考え方は[第10回](10-roster-verification.md)（勤務表の検証）で本格的に扱う。
:::

## 扱わないこと

- **モデルと入力データの分離**（`.mzn` と `.dzn`） → [第04回](04-sudoku-data-uniqueness.md)。
  この回では初期値をモデルの中に直接書いた
  （書き方だけなら [MiniZinc 早見表](../references/minizinc-cheatsheet.md)にある）
- **複数解の列挙と一意性の確認** → [第04回](04-sudoku-data-uniqueness.md)。
  `solve satisfy` は解を1つ返すだけである
- **最適化**（`minimize` / `maximize`） → [第07回](07-theme-assignment.md)。
  この回の問題には目的が無い
- **探索の指定**（探索アノテーション、ソルバーの選択） → この科目では扱わない。
  「どう探すか」をソルバーに任せることが、この書き方の要点である
- **`output` の凝った整形** →
  [MiniZinc 早見表](../references/minizinc-cheatsheet.md)。
  解の中身には関係しないので、読みやすければよい
- **`all_different` の内部の仕組み** → 使えれば足りる。
  仕組みに興味があれば MiniZinc の[公式ドキュメント](https://docs.minizinc.dev/)を見る
- **Prolog 版と MiniZinc 版の詳しい対応** →
  [グラフ彩色の3つの表現](../references/graph-coloring.md)。
  [第05回](05-sat-dependencies.md)で Z3 の Boolean 符号化を足して3つ揃う

## 次回への接続

この回のモデルは、初期値を `sudoku4.mzn` の中に直接書いた。
別の盤面を解こうとすると、モデルそのものを書き換えることになる。

第04回では、盤面を 9×9 に広げたうえで、モデル（`.mzn`）と入力データ（`.dzn`）を分ける。
同じモデルのまま盤面だけを差し替えられるようにし、
さらに「その盤面の解は本当に1つだけか」を確かめる方法を扱う。

::: {.note}
**自由課題に向けて**: 自分が興味を持っている問題を1つ思い浮かべ、
「変数・定義域・制約」の3点だけで書き出してみる。
うまく書けなくてよい。どこで詰まったかが、第11回の企画で使える材料になる。
:::
