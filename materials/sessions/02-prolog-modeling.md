## この回の目標

この回を終えると、次のことができる。

- リストから `member` で候補を選び、条件で絞り込む形（**生成とテスト**）を書ける
- 日本語で書かれた手掛かりを、Prolog の条件へ変換できる
- 論理グリッドを一問通して解き、「次の解」で解が他に無いことを確かめられる
- 失敗したときにどこへ戻って何を試し直すのか（**バックトラック**）を、
  コードの位置と対応付けて説明できる

## 今回解く問題

第01回では名簿の表が最初から与えられていた。今回は**表が無い**。
代わりに、手掛かりが9個ある。ここから表を復元する。これを論理グリッドパズルという。

登場するのは4人で、それぞれが飲み物・サークル・通学手段を1つずつ持つ。
**同じ属性の値が2人に重なることはない。**

| 属性 | 取り得る値 |
|---|---|
| 名前 | aoi, hikaru, tsubasa, kaede |
| 飲み物 | coffee, tea, cocoa, juice |
| サークル | tennis, brass_band, photo, art |
| 通学手段 | train, bicycle, walk, bus |

手掛かりは次の9個である。

| # | 手掛かり |
|---|---|
| 1 | hikaru は電車で通う |
| 2 | コーヒーを飲む人はテニス部にいる |
| 3 | 写真部の人は徒歩で通う |
| 4 | aoi は写真部ではない |
| 5 | 吹奏楽部の人は紅茶を飲む |
| 6 | kaede はバスで通う |
| 7 | tsubasa はココアを飲まない |
| 8 | 美術部の人は自転車で通う |
| 9 | kaede はテニス部ではない |

::: note
登場する名前・サークル・属性はすべてこの科目のために作った架空のものである。
:::

この9個をすべて満たす表は**ちょうど1通りしかない**。それを見つけるのが今回の目標である。

## 変数・定義域・制約・目的へ分解

第01回では「まだ決まっていないもの」が無かった。今回はある。

| 分けかた | この問題では | 個数 |
|---|---|---|
| まだ決まっていないもの | 4人それぞれの飲み物・サークル・通学手段 | 12 |
| 各々が取り得る値 | 属性ごとに4通り | — |
| 満たすべき条件 | 手掛かり9個 + 「同じ属性の値は重ならない」 | — |
| 目的 | なし（1つ見つかればよい） | — |

**「重ならない」も条件である**ことに注意する。手掛かりには書かれていないが、
これを入れないと「4人全員がコーヒー」のような表も答えになってしまう。

::: {.term}
試す可能性のある候補の全体を
[**探索空間**](../references/glossary.md#search_space)という。

**「重ならない」を候補の作り方に織り込むだけで、探索空間は3桁小さくなる。**
実際に数えるとどうなるかは[用語集](../references/glossary.md#search_space)にある。
:::

第03回では、この分けかたを「変数・定義域・制約・目的」という語彙で呼び直す。
いまはその中身を先に体験しておく。

## 概念と構文

### リスト

候補を並べるにはリストを使う。`[` と `]` で囲み、カンマで区切る。

```{.prolog filename="リスト"}
[coffee, tea, cocoa, juice]
```

::: {.term}
[**リスト**](../references/glossary.md#list)は値を順に並べたものである。
中身の型は揃っていなくてもよい。
:::

### `member` で候補を選ぶ

`member(X, リスト)` は「`X` はリストの要素である」を表す。
`X` が決まっていないときは、**要素を1つずつ `X` に入れて返す**。

```{.prolog filename="候補を1つ選ぶ規則"}
:- use_module(library(lists)).

drink(D) :- member(D, [coffee, tea, cocoa]).
```

`drink(X)` を実行して「次の解」を押すと、`coffee` → `tea` → `cocoa` と順に出る。

::: warning
`member` や `permutation` は `lists` ライブラリの述語である。
使うときはプログラムの先頭に `:- use_module(library(lists)).` を書く。
書き忘れると `existence_error(procedure, member/2)` になる。

（実行ページはこの宣言が無いときだけ自動で補うが、
自分で書く癖を付けておくほうがよい。）
:::

`member` がどう定義されているかは、この科目では読まない。
**使えれば足りる。** 気になる場合は
[Prolog 早見表](../references/prolog-cheatsheet.md)から辿る。

### 生成とテスト

候補を作る部分と、条件で落とす部分を並べて書く。これが今回の中心の形である。

```{.prolog filename="生成してから絞り込む"}
pair(D, C) :-
    drink(D),          % 生成: 飲み物の候補を1つ選ぶ
    club(C),           % 生成: サークルの候補を1つ選ぶ
    D \= tea,          % テスト: 紅茶は除く
    C \= tennis.       % テスト: テニス部は除く
```

::: {.term}
候補を作ってから条件で落とす2段構えの書き方を
[**生成とテスト**](../references/glossary.md#generate_and_test)という。
「どう探すか」ではなく「候補は何で、条件は何か」だけを書いている点で、
第01回からの延長線上にある。
:::

### 非等号 `\=`

```{.prolog filename="等しくない"}
D \= tea
```

::: {.term}
[**非等号**](../references/glossary.md#disequality) `\=` は
「両辺が等しくない」を表す。
手掛かりが「〜ではない」の形のとき（手掛かり4・7・9）に使う。
:::

これが第01回の宿題の答えである。`ride_together(X, Y)` に `X \= Y` を足せば、
同じ人どうしの組は出なくなる。

::: warning
`\=` は**両辺の値が決まってから**判定する。
まだ値が入っていない変数に対して使うと、意図と違う結果になる。
「先に生成、あとでテスト」の順序を守る。
:::

### 単一化の要点

`X = cocoa` は Python の代入とは違う。

::: {.term}
[**単一化**](../references/glossary.md#unification)とは、
両辺が同じ形になるように変数へ値を結びつける操作である。
「代入する」のではなく「**等しくできるか調べて、できるなら結びつける**」。

- `X = cocoa` … `X` が空なら結びつく。すでに `tea` なら失敗する
- `p(aoi, D) = p(aoi, cocoa)` … 形が同じなので `D` に `cocoa` が結びつく
- `p(aoi, D) = p(hikaru, cocoa)` … 第1引数が合わないので失敗する

**一度結びついた変数は、バックトラックで戻るまで変わらない。**
:::

形式的な定義はこの科目では扱わない。要点は
[用語集](../references/glossary.md#unification)にまとめてある。
「規則の変数を1つの値に読み替える操作」という見方は、番外の自習ページ
[論理の入門(1)](../references/logic-intro.md#unification-and-variables)にある。

### バックトラック

条件が満たせなかったとき、Prolog は**直前の選択まで戻って次の候補を試す**。

::: {.term}
これを [**バックトラック**](../references/glossary.md#backtracking)という。
「次の解」を押したときにも同じことが起きる。
:::

上の `pair/2` で何が起きるかを追う。

```text
drink(D) が coffee を選ぶ
  club(C) が tennis を選ぶ
    D \= tea      coffee は tea ではない  → 成功
    C \= tennis   tennis は tennis である → 失敗
  ← ここで club(C) の選択まで戻る（バックトラック）
  club(C) が brass_band を選ぶ
    D \= tea      → 成功
    C \= tennis   → 成功
                                          → 解 1: D = coffee, C = brass_band
```

**戻る先は「直前の、まだ試していない候補が残っている選択」**である。
`D \= tea` で失敗したときも、戻る先はまず直前の `club(C)` である。
残る `brass_band`・`photo` を試しても `D \= tea` は失敗し続け、
`club(C)` の候補が尽きてはじめて `drink(D)` まで戻る。
実行ページには途中の失敗は表示されないので、`drink(D)` が進んだようにしか見えない。
どの選択が「直前」になるかは、候補を選ぶ条件を書いた順序で決まる。

### 相異なりを `permutation` で保証する

「4人に4種類の飲み物を1つずつ、重複なく」を書きたい。
`member` を4回使って `D1 \= D2, D1 \= D3, ...` と書くこともできるが、
組み合わせの数だけ行が要る。**そうは書かない。**

```{.prolog filename="並べ替えとして生成する"}
:- use_module(library(lists)).

permutation([coffee, tea, cocoa, juice], [D1, D2, D3, D4])
```

`permutation(A, B)` は「`B` は `A` の並べ替えである」を表す。
`[D1, D2, D3, D4]` が空なら、24通りの並べ方を1つずつ返す。

こう書けば、**「同じ飲み物が2人に当たらない」を条件として書かなくてよい**。
候補の作り方そのものが保証する。

::: important
**表現が保証してくれる性質は、書かなくてよい。**
この考え方は第03回以降でも繰り返し出てくる。
どこまでを表現に任せ、どこからを制約として書くかの判断が、モデル化の要点である。
:::

### 1人分の情報を1つにまとめる

名前・飲み物・サークル・通学手段を別々の変数で持つと、対応関係が追えなくなる。
そこで1人分を1つの**項**にまとめる。

::: {.term}
[**項**](../references/glossary.md#prolog_term)（term）とは、Prolog が扱う**値の単位**である。
`aoi` のようなアトム、`3` のような数、`D1` のような変数のほか、
`p(aoi, D1, C1, T1)` のように**それらを名前と括弧でまとめたもの**も1つの項である。

第01回で書いた事実 `drinks(aoi, tea).` の `aoi` も `tea` も項だった。
今回は「まとめた項」を値として持ち回る。
:::

```{.prolog filename="1人分をまとめた項"}
p(aoi, D1, C1, T1)
```

`p` は関係の名前ではなく、**入れ物としての名前**である（何でもよい）。
4人分をリストに並べれば、名簿全体が1つの値になる。

```{.prolog filename="名簿全体"}
People = [p(aoi,     D1, C1, T1),
          p(hikaru,  D2, C2, T2),
          p(tsubasa, D3, C3, T3),
          p(kaede,   D4, C4, T4)]
```

こうしておくと、手掛かりを `member` で書ける。
たとえば「コーヒーを飲む人はテニス部」は次のようになる。

```{.prolog filename="手掛かりの書き方"}
member(p(_, coffee, tennis, _), People)
```

「名前と通学手段は何でもよく、飲み物が `coffee` でサークルが `tennis` である行が、
`People` の中に1つはある」と読む。**単一化が照合を担っている。**

## 小さな実行例

### 候補を選んで絞り込む

実行ページで
[リストと `member` のサンプルを開く](../../tools/prolog/?example=member)。
次のプログラムが入っている。

```{.prolog filename="member サンプル"}
:- use_module(library(lists)).

drink(D) :- member(D, [coffee, tea, cocoa]).
club(C) :- member(C, [tennis, brass_band, photo]).

pair(D, C) :-
    drink(D),
    club(C),
    D \= tea,
    C \= tennis.
```

`drink(X)` を実行して「次の解」を押すと、3つの候補が順に出る。

```text
解 1: X = coffee.
解 2: X = tea.
解 3: X = cocoa.
false.
```

## 予想してから試す

::: {.predict}
`member` サンプルの `pair(D, C)` を実行し、`false.` になるまで
「次の解」を押し続けると、解はいくつ出ると思うか。
数を予想し、その根拠も書き出してから実行する。

飲み物の候補は3つ、サークルの候補は3つ、テストは `D \= tea` と `C \= tennis` である。
:::

答えは4である。`tea` を除いた飲み物2通り × `tennis` を除いたサークル2通りで、
$2 \times 2 = 4$ になる。

```text
解 1: D = coffee, C = brass_band.
解 2: D = coffee, C = photo.
解 3: D = cocoa, C = brass_band.
解 4: D = cocoa, C = photo.
false.
```

::: {.term}
条件を満たす答えが2つ以上あることを
[**複数解**](../references/glossary.md#multiple_solutions)という。
実行ページでは「次の解」を押すたびに1つずつ出る。

「全部でいくつあるか」を数え上げて**解が1つだけだと確かめる**手順は、
この回では扱わない（第04回で MiniZinc を使って扱う）。
この回では「押しても次が出ない＝他に無い」というところまでで足りる。
:::

出る順序にも注目する。`coffee` を固定したまま `brass_band` → `photo` と動き、
サークルが尽きてから飲み物が `cocoa` に進んでいる。
**後ろに書いた選択ほど先に動く。** これがバックトラックの動きである。

::: {.check}
ここまでで、次を確認しておく。

- `drink(X)` で候補が1つずつ出ることを見た
- `pair(D, C)` の解の個数を予想して、実行結果と突き合わせた
- どちらの変数が先に動くかを、コードの並び順と対応付けられる
:::

::: {.hint summary="ヒント1: 候補を選ぶ規則の形"}
「候補を選ぶ」は `member` そのものである。
本文の `drink(D) :- member(D, [coffee, tea, cocoa]).` と同じ形で書く。

`not_train/1` は生成とテストの2段になる。
まず候補を選び、次に `\=` で落とす。条件は `,` でつなぐ。
:::

::: {.hint summary="ヒント2: 手掛かりを条件に直す3つの型"}
手掛かりには3つの型があり、書き方が決まっている。

| 型 | 例 | 書き方 |
|---|---|---|
| 肯定形（誰かの属性が分かる） | 「hikaru は電車で通う」 | `member(p(hikaru, _, _, train), People)` |
| 対応形（2つの属性が結び付く） | 「コーヒーの人はテニス部」 | `member(p(_, coffee, tennis, _), People)` |
| 否定形（〜ではない） | 「aoi は写真部ではない」 | 変数で取り出してから `\=` で落とす |

否定形は1行では書けない。**まず変数に取り出し、次に `\=` で条件を付ける**。

```{.prolog}
member(p(aoi, _, AoiClub, _), People),
AoiClub \= photo
```

項は `p(名前, 飲み物, サークル, 通学手段)` の**4引数**である。
`_` の個数が足りないと `existence_error` ではなく、静かに `false.` になる。
書いたら必ず `_` の数を数える。
:::

::: {.hint summary="ヒント3: 解答"}
```{.prolog filename="choose.pl（TODO(1)〜(5)）"}
% TODO(1)
drink(D) :- member(D, [coffee, tea, cocoa, juice]).

% TODO(2)
not_train(T) :-
    member(T, [train, bicycle, walk, bus]),
    T \= train.

% TODO(3) 「hikaru はテニス部にいる」
clue_a(People) :- member(p(hikaru, _, tennis, _), People).

% TODO(4) 「コーヒーを飲む人はテニス部にいる」
clue_b(People) :- member(p(_, coffee, tennis, _), People).

% TODO(5) 「aoi は紅茶を飲まない」
clue_c(People) :-
    member(p(aoi, AoiDrink, _, _), People),
    AoiDrink \= tea.
```

`TODO(2)` は `member(T, [bicycle, walk, bus])` と書いても同じ答えになるが、
それでは「候補から落とす」練習にならない。
手掛かりが増えたときに効いてくるのは `\=` の書き方のほうである。

**`clue_a`・`clue_b`・`clue_c` は、標準演習の `grid.pl` でそのまま使える。**
`clue_b` は手掛かり2そのものである。残る2つも、名前と属性を差し替えれば
手掛かり1・6（肯定形）と手掛かり4・7・9（否定形）の形になる。
:::

## 標準演習

::: {.exercise level=standard}
### 論理グリッドを解き切る

`workbook/sessions/02-prolog-modeling/grid.pl` には、名簿の形と3つの `permutation`
まで書いてある。ここに**9個の手掛かりをすべて**書き足し、解を求める。

```{.prolog filename="grid.pl（抜粋）"}
solve(People) :-
    People = [p(aoi,     D1, C1, T1),
              p(hikaru,  D2, C2, T2),
              p(tsubasa, D3, C3, T3),
              p(kaede,   D4, C4, T4)],
    permutation([coffee, tea, cocoa, juice],      [D1, D2, D3, D4]),
    permutation([tennis, brass_band, photo, art], [C1, C2, C3, C4]),
    permutation([train, bicycle, walk, bus],      [T1, T2, T3, T4]),

    % TODO 「今回解く問題」の手掛かり1〜9をここに書く
    true.
```

書き終えたら `solve(People)` を実行する。解が出るまでに数秒かかる。

続けて**「次の解」を押す**。ここが今回の山場である。
`false.` が出れば、9個の手掛かりを満たす表は他に無い。
別の解が出てしまったら、手掛かりのどれかが正しく書けていない。

**完了条件**: 次の3つを満たす。

1. `solve(People)` が解を1つ返す
2. 「次の解」を押すと `false.` になる（解が1つだけである）
3. 得られた表の4人それぞれについて、9個の手掛かりを1つずつ照合できる

3 を飛ばさない。**ソルバーが答えを返したことは、その答えが正しいことを意味しない。**
手掛かりを1つ書き忘れていても、Prolog はその条件を無視した「解」を平気で返す。
:::

::: {.hint summary="ヒント1: 最後の true. をどうするか"}
`grid.pl` の末尾に置いてある `true.` は、
「手掛かりを1つも書いていない状態でも構文エラーにならない」ようにするための仮置きである。

手掛かりを書き足すときは、各行の終わりを `,` にして `true.` の前に並べる。
`true.` はそのまま残しておいてよい（常に成功するので結果は変わらない）。
全部書き終えてから消して、最後の手掛かりの `,` を `.` に変えてもよい。
:::

::: {.hint summary="ヒント2: どの手掛かりから書くか"}
9個を一度に書かない。**1つ書くたびに実行する。**

まず手掛かり1と6（肯定形で、名前と通学手段が直接分かるもの）だけを書いて実行する。
解が何通りも出るはずである。「次の解」を数回押して、
候補が絞られていない状態を見ておく。

そこから1つずつ足していき、`false.` が出るまで押しても2つ目が出なくなったら完成である。
**途中で `solve(People)` がすぐ `false.` になったら、直前に足した手掛かりの書き方が誤っている。**
:::

::: {.hint summary="ヒント3: 否定形の手掛かりで詰まったら"}
手掛かり4・7・9は「〜ではない」の形である。必須演習のヒント2の表を見直す。

```{.prolog}
member(p(kaede, _, KaeClub, _), People),
KaeClub \= tennis
```

変数名は自由だが、**手掛かりごとに違う名前**にする。
同じ名前を使い回すと「2つの属性が等しい」という書いていない条件が入ってしまう。
:::

::: {.hint summary="どうしても動かないとき: 完成した例を見る"}
実行ページのサンプルに、この問題を解いた形が入っている。

[論理グリッドのサンプルを読み込んだ状態で実行ページを開く](../../tools/prolog/?example=logic-grid)

**先に自分で書いてから開く。** 開いてしまうと、
どの手掛かりの変換で詰まっていたのかが分からなくなる。
開いた場合は、自分の書いたものと1行ずつ見比べて、
**違っていた行がなぜ違っていたか**を説明できるようにする。
:::

## 発展演習

::: {.exercise level=advanced}
### いずれか1つを選ぶ

**A. 手掛かりを減らすと解はいくつ増えるか**

完成した `grid.pl` から手掛かりを1つだけコメントアウトして `solve(People)` を実行し、
`false.` が出るまで「次の解」を押して解の数を数える。
これを9個それぞれについて繰り返し、表にする。

- どの手掛かりを外したときに解が最も増えるか
- 解の数が最も増えにくい手掛かりは、他とどこが違うか

外す手掛かりによって、解の数は2通りから10通りの範囲で変わる。
自分の数えた値がこの範囲に入っていなければ、どこかで押し忘れているか、
手掛かりの書き方が誤っている。

**B. 手掛かりを置く位置で実行時間がどれだけ変わるか**

`grid.pl` は3つの `permutation` をすべて先に置き、手掛かりをその後ろにまとめてある。
これを次のように書き換える。

1. 飲み物の `permutation` を置く
2. **飲み物だけで判定できる手掛かり**（7）をその直後に置く
3. サークルの `permutation` を置く
4. 飲み物とサークルで判定できる手掛かり（2・5・4・9）をその直後に置く
5. 通学手段の `permutation` を置く
6. 残りの手掛かり（1・3・6・8）を置く

**答えは変わらない。変わるのは実行時間だけである。** どれくらい変わるかを測る。
実行ページの状態表示に経過時間が出る。

そのうえで、実行ページの
[5人・4属性のサンプル](../../tools/prolog/?example=logic-grid-5)を開く。
これは最初からこの順序で書いてある。数秒で解ける。

注意: この5人・4属性のサンプルを「まとめて生成してから絞り込む」形に書き換えると、
**2分以上待っても解が出ない**。候補が $120^4$ 通りになるためである。
試すなら、先に「中断」ボタンで止められることを確かめてから実行する。

なぜ順序でこれほど変わるのかを、バックトラックの動きで説明できるようにする。

**C. 頂点を増やして彩色する**

先に、この回の末尾の
[グラフ彩色: 同じ形の別の問題](#graph-coloring-demo)を読む。

`workbook/sessions/02-prolog-modeling/coloring.pl` の5地区を7地区に増やす。
隣接関係は次のとおりとする（近畿地方の7府県の隣接を使う）。

| 地域 | 隣り合う地域 |
|---|---|
| mie | shiga, kyoto, nara, wakayama |
| shiga | mie, kyoto |
| kyoto | shiga, mie, osaka, hyogo, nara |
| osaka | kyoto, hyogo, nara, wakayama |
| hyogo | kyoto, osaka |
| nara | kyoto, mie, osaka, wakayama |
| wakayama | mie, nara, osaka |

3色で塗り分けられるか。解はいくつあるか。2色ではどうか。
5地区のときと比べて実行時間はどう変わったか。

**頂点が増えても速いままである。** 論理グリッドとの違いがどこから来るのかを考える。
:::

## よくある誤り

| 症状 | 原因 | 直し方 |
|---|---|---|
| `existence_error(procedure, member/2)` | `:- use_module(library(lists)).` が無い | プログラムの先頭に書く |
| `existence_error(procedure, permutation/2)` | 同上 | 同上 |
| 手掛かりを書いたのに `solve(People)` がすぐ `false.` | 項の引数の個数が違う（`_` を書き落とした） | 項は `p(名前, 飲み物, サークル, 通学手段)` の4引数。`member(p(...), People)` の中の項目を数える |
| `syntax_error(...)` が出て読み込めない | 否定形の手掛かりを `member(p(aoi, _, \= photo, _), ...)` のように1行で書いた（`\=` は引数の位置に書けない） | 変数に取り出してから `\=` を別の条件として書く |
| 解が2つ以上出る | 手掛かりの書き漏れ、または肯定形を否定形として書いた | 出てきた解を手掛かりと1つずつ照合し、違反している手掛かりを探す |
| 解が出るが手掛かりに合わない | 属性の位置（第2引数が飲み物、第3引数がサークル…）を取り違えた | `People = [...]` の並びと `member(p(...))` の並びを見比べる |
| いつまでも終わらない | 生成をすべて先に置いた／`permutation` の第2引数の要素数が合わない | 「中断」を押す。発展演習 B の順序に書き換える |
| `\=` が効いていないように見える | 値が決まる前に `\=` を書いた | 生成のあとにテストを置く |
| 変数名を使い回して解が消えた | 別の手掛かりで同じ変数名を使い、意図しない一致を要求した | 手掛かりごとに違う変数名にする |

::: warning
**`false.` は2種類ある。**
「条件が厳しすぎて解が無い」場合と、「手掛かりの書き方が誤っていて、
本来の解まで落としてしまった」場合である。どちらも同じ `false.` が出る。

見分けるには、**手掛かりを1つずつコメントアウトして、どれを外すと解が出るか**を見る。
外した瞬間に解が出るなら、その手掛かりの書き方を疑う。
:::

## グラフ彩色: 同じ形の別の問題（時間があれば） {#graph-coloring-demo}

::: {.note}
**この節は回の終わりに5分で読む読み物である。**
演習が終わっていないなら、先に演習を進めてよい。
同じ図と同じ問題を[第03回](03-minizinc-sudoku.md)の冒頭でもう一度使うので、
ここで読み切れなくても困らない。
:::

論理グリッドと**まったく同じ形**で書ける問題がある。
架空の市に5つの地区があり、隣り合う地区が同じ色にならないように3色で塗り分ける。

![架空の5地区（北区・南区・東区・西区・中央区）の隣接関係と、3色で塗り分けた解の一例。中央区は他の4地区すべてと隣り合い、外側は北・東・南・西の順に環になっていて、辺は全部で8本ある。左は問題で、辺で結ばれた2地区が隣り合っていることを表す。右は解の一例で、どの辺の両端も異なる色になっている。](figures/graph-5districts.svg)

::: {.term}
頂点と、頂点を結ぶ辺の集まりを [**グラフ**](../references/glossary.md#graph)という。
辺で結ばれた2つの頂点が同じ色にならないように色を割り当てる問題を
[**彩色問題**](../references/glossary.md#graph_coloring)という。
:::

```{.prolog filename="coloring.pl"}
% 架空の市の5地区を3色で塗り分ける
color(red).
color(green).
color(blue).

% 中央区は北区・南区・東区・西区のすべてと隣り合う
% 外側は 北 - 東 - 南 - 西 - 北 の順に隣り合う
paint(Kita, Minami, Higashi, Nishi, Chuo) :-
    color(Kita), color(Minami), color(Higashi), color(Nishi), color(Chuo),
    Kita    \= Chuo,
    Minami  \= Chuo,
    Higashi \= Chuo,
    Nishi   \= Chuo,
    Kita    \= Higashi,
    Higashi \= Minami,
    Minami  \= Nishi,
    Nishi   \= Kita.
```

クエリ `paint(Kita, Minami, Higashi, Nishi, Chuo)` を実行する。

```text
解 1: Kita = red, Minami = red, Higashi = green, Nishi = green, Chuo = blue.
```

5つの `color(...)` が生成、8つの `\=` がテストである。
**論理グリッドと構造が同じ**であることを見ておく。
候補を並べて、条件に合わないものを落とす。それだけである。

[グラフ彩色のサンプルを読み込んだ状態で実行ページを開く](../../tools/prolog/?example=graph-coloring)
:::

同じ彩色問題を MiniZinc（第03回）と Z3（第05回）で書いたものを並べたページがある。
この回が終わってからでよいので、
[グラフ彩色の3つの表現](../references/graph-coloring.md)に一度目を通しておくと、

## 次回への接続

この回で Prolog は終わりである。第03回からは使わない。

やってみて分かったことが2つあるはずである。

1. 条件だけを書けば、探すのは処理系がやってくれる
2. ただし、**候補の作り方と条件を置く順序は自分で決めている**。
   発展演習 B で見たとおり、それが実行時間を決めてしまう

第03回では MiniZinc を使う。そこでは
「候補をどう作るか」も「どの順で試すか」も**書かない**。
書くのは「各変数が取り得る値の範囲」と「満たすべき条件」だけである。
`permutation` を並べて相異なりを作る代わりに、
`all_different` と1行書けば済むようになる。

同時に、この回で中身だけを扱った分けかたに
**変数・定義域・制約・解**という正式な名前を付ける。
題材は数独で、まず 4×4 の盤面から始める。

::: note
**自由課題に向けて**: 「候補を並べて、条件に合わないものを落とす」の形で
書けそうな問題を1つ考えてみる。
座席の割り当て、当番表、時間割の一部などが当てはまりやすい。
第11回の題材選びで使える。
:::
